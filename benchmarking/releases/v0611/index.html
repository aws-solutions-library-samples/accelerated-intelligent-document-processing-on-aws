Benchmark: v0.6.11 vs v0.6.10

v0.6.11 vs v0.6.10 (published) — release benchmark audit

Section titled “v0.6.11 vs v0.6.10 (published) — release benchmark audit”

Verdict: flat, and flat is the correct result for this release. The release A/B over 342 runs reports 0 regressions and 0 improvements: grid cost moved +0.4% and wall −2.9%, both inside run-to-run spread, and 17 of 19 cells are identical to three decimal places on both recall and cell accuracy.

That is what 0.6.11 should look like. Its product changes are error-path fixes — the agentic read timeout, the retry ladder’s duplicated cachePoint, and the throttling backoff — and they only engage after a transient Bedrock error. The corefast documents never hit one, so a release that moved accuracy or cost here would be the surprising outcome, not this.

The expensive half of this refresh (the configuration matrix, the scaling study, the model sweeps) is reported below the A/B and is where this release’s new information is: Claude Haiku 5.5 now has a measured accuracy and completeness figure, which its CHANGELOG entry explicitly said it did not.

⚠️ Its cost, however, is a lower bound rather than a measurement. Anthropic prices this model in two prompt-length bands — 5× on every token type above 100,000 input tokens — while pricing.yaml holds one flat rate per model. 105 of its 129 completed runs exceed that threshold (median 543,675 input tokens, maximum 10.96M), so the reported $0.155/doc is a floor; at the full 5× it would be ~$0.77/doc against Sonnet 5’s $0.587. No cost ratio for Haiku 5.5 is quoted. Resolving it needs per-request token capture in the harness or a two-band entry in pricing.yaml.

The bedrock_llm OCR backend result (inconclusive)

Section titled “The bedrock_llm OCR backend result (inconclusive)”

core-llm-simple-sep is the only cell outside noise on recall: 1.000 → 0.958, driven by one document (small_narrow) at −0.127. aggregate.py --compare reports it INCONCLUSIVE — the paired per-document spread for that cell is ±0.380, so a −0.042 mean sits well inside it.

Two things make it worth a line anyway rather than silence. Cell accuracy barely moves (1.000 → 0.993) while row recall drops, which is the signature of rows going missing rather than values coming back wrong. And this is the third release in which this one backend is the only cell to move: v0.6.6 root-caused an apparent recall drop here to the backend corrupting fixed-width identifiers, and v0.6.9 recorded a deterministic scalar regression on it. Its wall time also fell 22% in the same comparison.

This is a standing caveat on ocr.backend: bedrock_llm — the least stable OCR option in the matrix — rather than a 0.6.11 regression.

Cost by processing step

Section titled “Cost by processing step”

The grid total’s +0.4% is not hiding a composition change: no phase moved more than its own spread, and the two nominal cost rises (core-tl-adv-sep +4%, restate-on +2%) are inside the per-cell spread.

⚠️ The pooled cost-CV warnings aggregate.py prints for this suite are not instability. corefast pools three documents of very different size into one cell statistic, so a cell CV of ~0.6 measures document-size spread. Measured within a single (cell, document) pair across repeats, cost CV has a median of 0.005 and a maximum of 0.465 over n=3. Quote per-document cost, never the pooled cell CV.

Integrated confidence in advanced mode fails with Sonnet 4.6

Section titled “Integrated confidence in advanced mode fails with Sonnet 4.6”

In the cost suite, cell core-tt-adv-int (extraction_mode: advanced, assessment: integrated, extraction_model: sonnet46) failed 5 of 5 attempts on med_narrow, at wall times of 1014.8–1021.6 s — a spread of ±7 s, i.e. a fixed structure rather than model latency. For contrast:

  • the same cell with assessment: separate completes in 111–127 s;
  • the same cell at extraction_model: sonnet5 completed 25/25.

Mechanism, from the shard runtime’s own log:

Extraction succeeds first — the same log records Extraction complete for shard 1 (pages 1-5): 239 transactions captured ... All data validated successfully. What exceeds the budget is the per-field assessment tool output, emitted inline in the same agent loop, on shards holding ~240 rows. Sonnet 5 survives because its output budget is far larger.

Guidance: integrated confidence in advanced mode needs a large-output extraction model. At the shipped control model it fails deterministically on a mid-size document, which is not a capacity case. med_narrow is 10 pages.

Reproduce

Section titled “Reproduce”

Note the argument order: --compare takes the new summary and --baseline the older one. Reversed, the signs invert and the one inconclusive cell reads +0.042 instead of −0.042.

baseline.json is not promoted by this release. It still holds v0.6.8 (meta.stack_version), because neither 0.6.9 nor 0.6.10 promoted it; promoting it from here would skip two releases’ worth of drift in one step without a record in between.

Prerelease measurements (2026-09-27, a private build of 3ca2dcc4d)

Section titled “Prerelease measurements (2026-09-27, a private build of 3ca2dcc4d)”

The same corefast A/B was run before publication, against a private build of the release commit, and reached the same verdict: 0 regressions, 0 improvements. Those measurements are retained below for continuity. They cover the A/B only — the guidance refresh above is the first for this release — and the configuration-matrix figures they cite are superseded by it.

Summary

Section titled “Summary”

0 regressions, 0 improvements, 0 cell-level regressions, 0 cell-level improvements. Three inconclusive movements, all on one cell, all inside run-to-run spread.

That is the correct result for this release rather than a weak one, and the reason is the size of the change. git diff v0.6.10..3ca2dcc4d touches exactly two files of product code — idp_common/extraction/agentic_idp.py and idp_common/utils/bedrock_utils.py — and both changes are on error paths: a retried Advanced-mode extraction now resumes the conversation the failed attempt started instead of re-sending the prompt, and the Bedrock backoff ladder now stops when its allowance is spent instead of clamping every remaining sleep to zero. A document that never hits a transient Bedrock error enters neither. corefast runs healthy documents, so it should not move, and it does not.

The corollary matters for anyone reading this as evidence: this grid does not exercise what 0.6.11 fixed. Confirming the fixes themselves requires inducing throttling or a transient error, which no suite in benchmarks/ does.

⚠️ Limitations of this entry

Section titled “⚠️ Limitations of this entry”

Cost is not comparable at cell level on this suite. corefast’s cost CV is 0.50 to 1.02 across all 19 cells at n=9 on both sides. That is variance across the three different documents inside each cell — tiny_form and longdesc_100 differ by more than an order of magnitude — not run-to-run noise. A cell’s cost mean here is an average over unlike documents. Cost claims for this release would have to come from the cost suite (n ≥ 5 on one 400-row document), and that suite did not complete in this pass.

Wall-time is not comparable between the sides. They ran on different stacks: the 0.6.10 side on an existing v0.6.10 stack, reused rather than newly deployed to conserve IAM role headroom, and the 0.6.11 side on the stack the release-validation upgrade tier had just upgraded in place. Accuracy, completeness and cost are comparable, because the configuration was byte-identical — generated once by make_configs.py and not regenerated between sides, with --native-upload bypassing idp-cli’s migration on both.

baseline.json is deliberately not promoted. Nothing moved, so there is nothing to promote, and promoting a grid whose cost axis is unusable at cell level would make the next release’s --compare diff against a baseline this entry has told the reader not to trust.

⚠️ Configuration-guidance refresh (tier F) not completed

Section titled “⚠️ Configuration-guidance refresh (tier F) not completed”

The release-validation battery plans a full guidance-paper refresh alongside the A/B, at 2,148 runs. This pass completed the A/B (342) plus intconf (8) and was then stopped.

LanePlannedOutcome

The three partial lanes are deliberately left unscored. aggregate.py will score a partial run and write a summary that looks complete, so leaving them unscored is the only signal a later reader gets that they are partial.

Consequence, stated by name: every paper under docs/benchmarking/ still carries data from an earlier release. config-guidance.md, index.md, classification-confidence.md, prompt-caching.md and feature-multi-instance.md were not regenerated, and config-guidance.md’s header still names an earlier release. In particular there is no measured model-selection verdict for 0.6.11 — the premium and lightweight model sweeps did not run, so the guide cannot say on this release which cheap model is at ceiling for a given document profile or whether a premium model earns its price.

One part of the refresh would have been empty regardless: 0.6.11 changed no configuration knob. The §7 one-knob A/Bs had nothing to re-measure, and running them would have measured nothing about this release.
