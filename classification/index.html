Customizing Classification

Section titled “Customizing Classification”

Document classification is a key component of the GenAIIDP solution that categorizes each page and section of a document into predefined classes. This guide explains how to customize classification to best suit your document processing needs.

How the classification settings are organised

Section titled “How the classification settings are organised”

Classification does two jobs: it splits the document into sections, and it classifies each one. Strategy decides whether those are one model call or two, and every other setting sits inside the call that uses it, so a block the selected strategy does not run is not shown in the configuration editor and has no effect.

The model settings are the same block in every call: a model, its parameters, modality (send page text, send page images) and the image size. The two calls that assign a class — the combined call, and split-then-classify’s section classification — add validation and class confidence. Splitting has neither, because it returns page ranges and never a class.

Two of those settings are substituted rather than used as written when they cannot be. An empty model is not “no model” — every call needs a model id to send — so it falls back to the default classification model, which is the same us.amazon.nova-2-lite-v1:0 the defaults put on all three calls, with a line in the log. And a reasoning_effort outside the levels listed in the editor is replaced with medium, also with a line in the log, because the value is forwarded to the provider as written and a misspelled one either fails the request or is silently ignored by a model family that has no effort control.

What each setting costs

Section titled “What each setting costs”
  • granularity: packet saves the repeated prefix and the per-page output. A page-level call re-sends the instructions, the class list, every class description and every few-shot example on every page, and asks for roughly 150–350 output tokens of reasoning each time. A packet call pays all of that once.
  • It does not reduce image tokens. A page’s image costs the same whether it arrives in its own call or alongside nineteen others. So packet + modality.images: false is the large cost lever, and packet with images on is mainly an accuracy change — it is the only way the model ever sees the whole packet when deciding where sections start.
  • Images are usually the largest single input cost per page, roughly 1.1K–4.8K tokens depending on the model and the image size, against a few hundred output tokens. Each call’s image.target_width / target_height and modality.images: false are the two levers on that.
  • contextPagesCount is the most expensive setting per unit of change. Each call carries up to 2k+1 pages: ×3 at k=1 and ×5 at k=2, in both text and image tokens.
  • strategy: split_then_classify drops the class vocabulary from every splitting call and classifies once per section instead of once per page. A clear win on long documents with few sections; roughly a wash on single-page documents, where it adds a second call to save a prefix that was only paid once. Each call can use its own model, so splitting can run on a cheap model and classification on a stronger one.
  • A declared document shape skips the boundary work. Under sectionSplitting: disabled or page, split-then-classify makes no splitting calls: the segments are known, so it goes straight to section classification.
  • The model choice outweighs all of it. On the benchmark suite Nova 2 Lite, Claude Haiku 4.5 and Claude Sonnet 5 reached the same classification accuracy at $0.007, $0.047 and $0.189 per document respectively — see benchmarking/config-guidance.md §5.3. With Sonnet 5 as the classifier, classification reached 67% of total document cost on a 9-page benchmark row.

Combinations refused when you save

Section titled “Combinations refused when you save”
  • modality.text: false and modality.images: false on any call — nothing left to classify.
  • ocr.backend: none with modality.images: false on a call the selected strategy makes — no OCR text is produced and no images are sent, so classification would be working from the literal string [No text content for page N]. A packet call in that state would go out anyway and return a confident class derived from nothing; it fails instead, with a message naming both remedies.
  • packet.overlap_pages greater than or equal to packet.window_pages — each window would cover no new pages, so a long packet would cost one call per page while claiming to be the cost-saving granularity.
  • A model ID that is not a known Bedrock model, or a max_tokens above the model’s output limit, on a call the selected strategy makes. Each is named by its path, for example classification.split_then_classify.section_classification.llm.model.

Page granularity with sequence segmentation (default)

Section titled “Page granularity with sequence segmentation (default)”
  • Classifies each page independently using both text and image data
  • Uses sequence segmentation with BIO-like tagging for section boundary detection
  • Each page receives both a class and a boundary indicator (“start” or “continue”)

Sequence Segmentation Approach
Section titled “Sequence Segmentation Approach”

Page granularity implements a sophisticated sequence segmentation approach similar to BIO (Begin-Inside-Outside) tagging commonly used in NLP. This enables accurate splitting of packets into sections, where a single document may contain several distinct sections.

How It Works:

Each page receives two pieces of information during classification:

  1. Class: The classification label (e.g., “invoice”, “letter”, “financial_statement”)
  2. Section Boundary (document_boundary): A boundary indicator that signals section transitions:
    • "start": Indicates the beginning of a new section (similar to “Begin” in BIO)
    • "continue": Indicates continuation of the current section (similar to “Inside” in BIO)

Benefits of Sequence Segmentation:

  • Packet Support: Accurately splits packets into their sections
  • Type-Aware Boundaries: Detects when a new section of the same class begins
  • Automatic Section Creation: Pages are grouped into sections based on both type and boundaries
  • Improved Accuracy: Context-aware classification that considers document flow
  • No Manual Splitting Required: Eliminates the need to manually split packets before processing

Page Context for Classification
Section titled “Page Context for Classification”

Page granularity supports including surrounding pages as context to improve classification accuracy. This is particularly useful when a single page doesn’t contain enough information to determine its class or boundary status.

Configuration:

Splitting at page granularity, under split-then-classify, has the same setting at classification.split_then_classify.splitting.llm.page.contextPagesCount.

How It Works:

When contextPagesCount is set to a value greater than 0, the classification prompt includes surrounding pages as additional context:

  • contextPagesCount: 1: Includes 1 page before and 1 page after the target page
  • contextPagesCount: 2: Includes 2 pages before and 2 pages after the target page
  • Edge handling: At the start and end of the document, only available pages are included (e.g., first page has no “before” pages)

  • Improved Boundary Detection: Context helps the LLM identify section transitions

  • Document packages with varying page layouts
  • Cases where LLM boundary detection has been unreliable

Considerations:

  • Increases token usage proportionally to the number of context pages
  • May increase latency due to larger prompts
  • Works best when surrounding pages provide meaningful classification hints

How the model is asked to decide it
Section titled “How the model is asked to decide it”

Each page is classified in an independent LLM call that sees only that page (plus any neighbours from contextPagesCount) and is never told its position in the packet. So “does this continue the previous document?” is a question the model often cannot answer from what it was given — and the prompt used to ask exactly that. Failing runs said so in their own reasoning: “Since no prior page 1 has been established in this sequence, this is treated as the start of the document.” The result was intermittent over-splitting of multi-page documents (#653).

The combined page prompt, classification.combined.page.task_prompt, carries a <boundary-detection-rules> block that asks a question a single page can answer — is this page a first page? — from its own evidence, in priority order: pagination (Page 2 of 2 ⇒ continue), then the presence of an opening identity block, then table continuation — a page of table rows whose column headings repeat at the top is a continuation page, because repeated column headings are not a document title — then other continuation evidence. The table-continuation rule was added for #726: on a single-class config the classifier called the second or third page of a three-page bank statement start in about half of the runs, because the reprinted Date | Description | Amount heading row looked like a heading. Measured with the real OCR and classification services (Nova 2 Lite, temperature 0) on the benchmark fixtures: the unpaginated 3-page statement went from 8/15 to 15/15 correct section counts, with the two-documents (5/5) and paginated (5/5) fixtures unchanged. Confirmed end to end on a deployed stack with a same-stack A/B (boundaryab suite, the frozen v0.6.7 prompt as the control, 5 repeats): the unpaginated statement scored 1/5 under the v0.6.7 prompt and 5/5 under the new rules, the two-documents and paginated fixtures 5/5 under both, and the running-header fixture 0/5 under both. Note that an upgrade delivers the new rules to Config#default (and to a CustomConfigPath config, which is re-resolved from S3) but not to a configuration profile you saved yourself — a saved profile is an independent snapshot that keeps whatever page task prompt it was saved with. Re-apply the block or reset the prompt to the default in such a profile. Two clauses in the block are a matched pair and must not be removed independently:

ClausePrevents
no preceding page shown — absence of page 1 in the input says nothing about the documentover-splitting (every page reported as start)
consecutive documents of the same type — a genuine first page is start even when the previous page has the same classover-merging (back-to-back copies of one form collapsing into one section)

The block sits before <<CACHEPOINT>>, so it is part of the cacheable prefix and is not re-billed per page.

contextPagesCount: 1 is not a substitute. It fixes the simple two-page case but biases the model toward continue, which then merges genuinely separate back-to-back sections — trading over-splitting for over-merging. Measured on a 4-page packet holding two copies of one form, contextPagesCount: 1 on its own scores 0/5 — it merges all four pages. It remains the right answer for one case the rules cannot cover: pages scanned out of order, where a page has no way to know it is physically second.

Measured effect
Section titled “Measured effect”

On DocSplit-Poly-Seq — 500 packets, 7,330 pages, 2,027 sections, 5,000 packet-runs — split accuracy on multi-section packets, rules vs. the prior prompt:

ModelΔ split accuracy
Qwen3-VL+0.117p<0.05

Paired bootstrap + Wilcoxon; no model regresses. Under-split rate is 0.000 in all ten cells, so the over-merge guard holds. Page-level class accuracy moves at most 0.015 — the rules affect boundaries only, not classification. On #653’s reported two-page form, Sonnet 5 goes from 6/24 to 10/10.

Two limits worth knowing before you rely on this:

  • It leans on pagination markers. Corpora whose scans mostly lack them (for example RVL-CDIP) see much less benefit — the header-block and continuation heuristics are softer signals than Page 2 of 3.
  • llm_determined over-splits 1.5×–2.3× on real-world packets regardless of prompt. That is a separate and larger problem than the one these rules fix; the rules narrow the gap, they do not close it. If exact section counts matter to you, measure on your own documents.
Known failure mode: repeating running headers
Section titled “Known failure mode: repeating running headers”

The rules are wrong on one common document shape, and the fix is a per-class setting rather than a change to the rules (#750).

A long table — a fund/distribution schedule, a brokerage or transaction statement — typically reprints its title, logo and column headers on every page and paginates with a bare page number (7), not Page 7 of 17. That combination defeats the priority order above:

  • rules 1–2 never fire, because a lone 7 matches none of the pagination patterns the model is given;
  • rule 3 (opening header block ⇒ start) is evaluated before rules 4–5 (table / other continuation evidence ⇒ continue), and the repeated running header satisfies it — especially when the reprinted column headers themselves carry a date (NAV as of 10/31/2024), which rule 3 lists as page-1 evidence. Rule 4 (added for #726) only clears a page whose repeated content is the table’s column headings; a reprinted title and account block still reads as an opening block, so a synthetic 3-page statement with that running header and no pagination scores 0/5 before and after the #726 change, on Nova 2 Lite and on Claude Haiku 4.5 alike;
  • contextPagesCount: 0 (the default) means the continuation rules have no preceding page to compare against — rule 4 judges the page’s own table rows and rule 5’s “running balance or subtotal carried forward” is a within-page clue.

The model says so in its own reasoning: “The page number ‘15’ at the top right indicates this is part of a multi-page document, but the presence of the full title and structured data table confirms this is the start of the document’s content.”

It is silent: each fragment is still 100% complete and the document still reaches COMPLETED. Only the section count changes — so a downstream consumer that reads one section sees a truncated list and blames extraction.

The supported fix is the PRECEDENCE clause: put the boundary rule in the class description. A document type’s own boundary instructions override the generic rules, which is exactly what this shape needs:

Name "start" and "continue" explicitly — those are the values document_boundary takes, and a paraphrase leaves the mapping to the model.

Enforcing a Valid Class Vocabulary (Validation + Retry)
Section titled “Enforcing a Valid Class Vocabulary (Validation + Retry)”

With a fixed set of classes, a language model can occasionally return a label that is not in your configured list (for example predicting receipt when only invoice, w2, and check are valid). Smaller / cheaper models are especially prone to this. Every call that assigns a class — the combined call at page or packet granularity, and split-then-classify’s section classification — includes a deterministic validation + retry guardrail to prevent out-of-vocabulary classifications:

  1. After the model returns a class, it is validated against the configured class vocabulary.

  2. If the class is not valid, the model is re-prompted — the original request content is re-sent with an appended correction message that lists the allowed classes. (This matters: on a model that honors it, classification runs at temperature=0, so re-sending an identical request would return the identical invalid answer. The correction changes the input and steers the model back to the allowed set.)

    temperature=0 is not universal. Claude Opus 4.7/4.8, Opus 5, Opus 5.5 and Sonnet 5 reject temperature/top_p/top_k (HTTP 400), so idp_common strips them before the request (_CLAUDE_4_7_BASE_NAMES in idp_common/bedrock/client.py). On those models classification samples, and identical inputs can return different answers run to run. Assuming the parameter applies everywhere is what makes #653 — intermittent page-boundary misdetection — look like a model defect rather than a prompt one.

  3. The retry repeats up to maxValidationRetries times.

  4. If all retries are exhausted, the page is assigned fallback_class (default unclassified) and a warning-severity classification_invalid_class_fallback processing issue is recorded on the section that holds the page, naming the class the model returned. The document continues processing — there is no hard failure, but the stored class is not the model’s answer and the section says so. See Pages classification could not classify.

SettingDefaultDescription
validation.enforceValidClassestrueWhen true, validate the predicted class and re-prompt on out-of-vocabulary results. When false, an invalid class is logged and used as-is.
validation.maxValidationRetries2Maximum number of re-prompts. 0 disables retries (a single invalid prediction goes straight to the fallback).
fallback_classunclassifiedClass assigned when retries are exhausted. Not validated against your class list — any string is stored, so a typo becomes a class name no extraction schema matches. Use one of your defined classes, or the built-in unclassified; clearing it gives unclassified. One setting for the whole classification step; extraction reads it too.

Catch-all class: if you want an explicit “other”/“unknown” bucket, define it as one of your classes — the model will then be able to select it legitimately, and it counts as a valid prediction.

Packet granularity: a reply that names an invalid class for any segment re-prompts the whole window, and a segment still invalid after the retries is given the fallback class.

Section titled “Packet granularity: images, few-shot examples and windowing”

Page images. Every page’s image is attached, each labelled with its ordinal in the call so the model can say which image it is looking at — layout is most of what tells you where a section starts. Subject to the call’s modality.images.

Sending no examples is part of what makes the splitting call cheap, so a splitting template that references {FEW_SHOT_EXAMPLES} gets nothing rather than an error. See which placeholders a stage is allowed to render.

Windowing. A packet larger than one window is split into overlapping windows whose results are merged:

Splitting at packet granularity, under split-then-classify, has the same window settings at classification.split_then_classify.splitting.llm.packet.

The default of 20 is where Bedrock starts downscaling: above 20 image blocks in one request every image is shrunk to 2,000px, so a wider window with images on silently halves its own page resolution.

The overlap exists so the window after a junction can see the pages before its own first page — a boundary landing on a window’s first page would otherwise have to be judged with no preceding context, which is precisely the weakness packet granularity exists to fix. The overlapping pages’ own verdicts are taken from the earlier window, which is the one that had their preceding context. Windows are merged by projecting each window’s segments onto per-page verdicts and re-running the same fold page-level classification uses, so a windowed packet and a page-level document cannot disagree about how verdicts become segments. A single window (the common case) uses the model’s segments directly.

One window failing does not discard the others, so a transient throttle on a long packet costs that window’s boundaries rather than the whole document’s.

How to pick the two numbers.

  • Keep window_pages at 20 or below whenever images are on, so a request stays under the 20-image-block threshold above which Bedrock downscales every image. Raising it to get fewer calls costs page resolution on every call.
  • Keep it no smaller than your longest single section. A section that straddles two windows has its boundary judged twice from two partial views, which is the main way windowing loses accuracy. If your longest section is longer than 20 pages and images matter, prefer page granularity over a wide window.
  • 0 means never window: one call for the whole packet, which fails outright above the model’s context window rather than degrading. Use it when you need the old single-call behaviour and your packets are bounded.
  • overlap_pages must be strictly smaller than window_pages or the save is refused. It should cover the longest run of continuation pages you expect before a boundary cue appears — 2 is enough when first pages are clearly marked, more when a section opens with a cover sheet or a table that runs on. Each additional window costs overlap_pages extra pages of input, so the cost is roughly overlap / (window - overlap) on top of the un-overlapped page count.

The number of calls over N pages is 1 when window_pages is 0 or N fits in one window, and otherwise `ceil((N - window_pages) / (window_pages - overlap_pages))

  • 1`.
Limitations of packet-level classification
Section titled “Limitations of packet-level classification”

Despite its strengths in handling full-document context, this granularity has several limitations:

Context & Model Constraints::

  • Long documents can exceed the context window of smaller models. Set the call’s packet.window_pages to split them; with window_pages: 0 the request fails outright.
  • Lengthy inputs may dilute the model’s focus, leading to inaccurate or inconsistent classifications.
  • Requires high-context models. A 1-million-token input window is reached two different ways, and only one of them is a :1m id. The extended-context Claude variants — us.anthropic.claude-sonnet-4-6:1m, us.anthropic.claude-sonnet-5:1m and the :1m Opus variants — opt into it; us.anthropic.claude-sonnet-5-5 and us.anthropic.claude-haiku-5-5 have it by default and have no :1m id at all, so looking for one rules out two models that already qualify. Every other base Claude 4.x/5 model carries 200K and the Nova family ~300K. Smaller models are not suitable for this method. config_library/model_config_limits.yaml is the authority for which id gets which window.
  • For more details on supported models and their context limits, refer to the Amazon Bedrock Supported Models documentation.

Scalability Challenges: Not ideal for very large or visually complex document sets. In such cases, page granularity is more appropriate.

Available Values

Section titled “Available Values”

1. disabled - No Splitting (Entire Document = One Section)

Section titled “1. disabled - No Splitting (Entire Document = One Section)”

Behavior:

  • All pages are assigned to a single section
  • Uses a page-weighted vote across the segments that were detected to determine the document class: each segment casts as many votes as it has pages, and the class with the most votes wins
  • Excludes segments whose class is not one of the configured classes, so unclassifiable and blank pages do not affect the result
  • If there’s a tie, uses the class of the earliest segment carrying a tied class, for determinism
  • Ignores the detected boundaries when building sections — it still reads them to weight the vote
  • With a single-class configuration, sends no page to the model: every page is given that class with confidence 1.0. Under llm_determined, a multi-page document in such a configuration still goes to the model for its section boundaries: page by page at page granularity, and in one call for the whole document at packet granularity
  • Under split-then-classify, makes no splitting call: the whole document is one segment, given its class by one section classification call

Use Cases:

  • Documents known to be single-type with no internal divisions
  • Simplified processing where granular section splitting isn’t needed
  • When you want to force all pages to be treated as one cohesive section
  • Documents with occasional blank or unclassifiable pages (these won’t affect the final classification)

Configuration Example:

Voting Behavior:

The disabled value votes on the document classification, which provides robust handling of edge cases. The same rule runs at both granularities and under both strategies — what differs is only how the segments it counts were produced:

  1. Config-Driven Voting: Only segments whose class matches a document type defined in your configuration are eligible to vote. This automatically excludes:

    • Blank pages (unclassifiable_blank_page, blank, etc.)
    • Error states (error (backoff/retry), unclassified)
    • LLM hallucinations or typos that don’t match any defined class

  2. Pages, Not Segments, Are The Weight: each eligible segment contributes one vote per page it covers, so a 5-page segment outweighs a 1-page one. The class with the most page-votes becomes the document classification.

  3. Tie-Breaking: If two classes have the same weight, the class of the earliest segment carrying a tied class is used for determinism.

  4. Fallback: If no segment carries a configured class, the first segment’s class is used, with a warning in the log.

⚠️ One disagreeing page leaves the section unscored. A page whose own verdict was a class other than the winner has its confidence cleared, and a section’s confidence is the aggregate over all its pages, which is None as soon as any page is unscored. A page that produced no verdict of its own inherits its segment’s class and confidence, so silence does not count as disagreement — see Not scored vs. scored 1.0.

What decides the choice

Section titled “What decides the choice”

⚠️ disabled and page are assertions, not preferences. They do not ask the model to lean one way; they replace boundary detection with a claim about the document, and nothing downstream can recover from the claim being wrong. A packet of eight forms declared disabled returns one section, with one extraction over eight forms’ worth of pages. That is why these two sit under document_shape — what you already know about this document — rather than beside the strategy.

So the choice is really a question about your input, not about accuracy:

  • You know every document holds exactly one section → disabled. This is the common case for a single-document intake pipeline, and it is the only value that enables maxPagesForClassification.
  • You know every document is a run of one-page sections, or a packet holds same-type forms back to back and you would rather over-split than merge them → page. This is the deterministic answer to the multiple-W-2 problem below.
  • You do not know, or documents vary → llm_determined, the default. Pay for the boundary decision.

Three further properties worth knowing:

  • disabled and page are the only values that let a multi-page document skip the model entirely. With a single-class configuration, or a document-name regex match that already fixes the class, there is nothing left to decide and no call is made. Under llm_determined the model is still called in both of those cases when the document has more than one page, on purpose: the class may be known but the boundaries are not, and silently skipping the call would collapse every packet into one section. A single-page document skips the call under llm_determined too, because one page cannot be split.
  • document_shape applies identically under both strategies. Under split_then_classify a declared shape skips the splitting call outright, leaving one section classification call per asserted section.
  • split_then_classify with sectionSplitting: page is strictly dominated. It makes one classification call per page with no splitting call, which on a measured 3-page document cost the same requests and essentially the same input tokens as combined at page granularity (3 calls, 1,545 against 1,527 input tokens) — the same price for a configuration that cannot return a per-page boundary verdict. If you want one section per page, combined is the simpler spelling.

Pages Classification Could Not Classify

Section titled “Pages Classification Could Not Classify”

A page can come out of classification without a usable class. When that happens the page is labelled unclassified (or fallback_class, which defaults to the same), and because no class of that name exists in configuration it has no extraction schema — so extraction skips the model for its section and the section completes holding no data. A document in that state still completes normally, and that is the right behaviour: one unreadable page should not discard the rest of a packet.

What it must not do is complete without saying so. Classification records a processing issue on the section that holds the page, which is where the Sections panel renders it and where ProcessingIssueCount on the document counts it. The severity says how much attention the case deserves:

Scope: the combined strategy at page granularity only. These issues are recorded from the page-level path. Packet granularity and split-then-classify make one decision per segment rather than per page and record none of them; at packet granularity a page the model places in no segment is appended to no section at all, so it produces neither data nor a record. Extending this to the segment-level paths is tracked as follow-up work.

Why two of them are warnings and not errors. Every fleet-level alarm in this solution is paired with a threshold parameter a deployer tunes, and none of these three has an established base rate to set one from; an unalarmed metric would only add cost. The issues reach the Sections panel, the document’s ProcessingIssueCount and the processing-issues index, which is what a document-level query reads.

Downstream. The confidence pass does not also report an unclassified section as unscored. It has no confidence to be missing that this page’s issues do not already explain, and a root_cause written from the Assessment step would point the operator at Extraction, where nothing is wrong. A section whose class is a named class missing from configuration is a different case and is reported from both Extraction and Assessment — see Monitoring.

Excluding Static Pages (e.g. Instructions, Legal Boilerplate)

Section titled “Excluding Static Pages (e.g. Instructions, Legal Boilerplate)”

Many forms packages bundle several pages of static content alongside the pages that actually carry dynamic, applicant-specific data. Think of the first four pages of a DS-11 U.S. Passport Application (WARNING notice, fee instructions, FEDERAL TAX LAW disclosure, ACTS OR CONDITIONS affidavit) — they are identical across every applicant and carry no fields to extract.

You can mark a class as excluded so that downstream stages (extraction, assessment, summarization, rule validation, evaluation) will skip sections classified as that class, avoiding wasted LLM calls, tokens, and noise in accuracy metrics.

How classification decides a section is “excluded”

Section titled “How classification decides a section is “excluded””

The primary mechanism is the LLM classifier using each class’s description field. Mark the class as excluded via x-aws-idp-exclude-from-processing: true; the multimodal page-level classifier then picks the class by description like any other class, and the excluded flag propagates onto the resulting Section. This is the canonical, robust path — tolerant of form revisions, OCR quirks, wording differences, and visual-only pages.

The optional x-aws-idp-document-page-content-regex extension is just a tokens-saving fast-path for pages whose OCR text reliably matches a known stable boilerplate phrase; if the regex misses, the LLM still classifies the page correctly via the description. Regex alone is not a substitute for a well-written class description.

The split-then-classify strategy

Section titled “The split-then-classify strategy”

strategy: split_then_classify (Split first, then classify each section in the editor) splits the two jobs into two calls: a splitting call, then section classification. combined stays the default.

A combined call does two different jobs at once, and pays for it in two ways. Every boundary decision carries the whole class vocabulary — the class list, every description and every few-shot example — although finding a boundary does not depend on any of it; at page granularity that prefix is paid once per page. And classifying scales with pages rather than sections: a 40-page statement is classified forty times to produce one answer.

The splitting call has its own granularity, page and packet settings, prompts and model settings — the same call shape as the combined call, asked a smaller question. At packet granularity it is one call (or one per window) asking for page ranges; at page granularity it is one call per page asking only start or continue, which still makes N calls but drops the prefix from each. It has no validation or class confidence, because it returns no class.

⚠️ Writing a custom splitting prompt: the vocabulary placeholders render empty there. {CLASS_NAMES_AND_DESCRIPTIONS}, {CLASS_AND_ATTRIBUTE_NAMES_AND_DESCRIPTIONS} and {FEW_SHOT_EXAMPLES} are all substituted with nothing in a splitting prompt, at either granularity and whatever contextPagesCount is set to — that absence is the dropped prefix, so referencing one gets you silence rather than an error. boundary_hints: class_names is the supported way to put the class names into this call; it renders a short {BOUNDARY_HINTS} block, which in turn is empty in every call other than splitting, because it tells the model to report no class. See which placeholders a stage is allowed to render.

Section classification is one call per segment, over the pages pages selects. first_k is the default because a section’s identity is almost always on its opening pages, while all makes classifying a long segment cost what page-level classification cost. It has its own prompts, modality, image size, validation and class confidence.

Setting boundary_hints

Section titled “Setting boundary_hints”

boundary_hints decides whether the splitting prompt is told your class names. Leave it at none by default: withholding the vocabulary from the splitting call is the saving split-then-classify exists for, and a boundary is a question about where a section ends rather than about what kind it is.

Reach for class_names when boundary_accuracy is the metric that is failing — not label_accuracy — and your class names are the kind of string that appears on a first page: a form number (form_1040, w2), a document title, an institution’s own name for a statement. Those give the model a literal token to look for at the top of a page. If your class names are internal labels (type_a, customer_doc_3), class_names sends tokens that match nothing and costs the saving for no signal. On the over-split fixture measured above, class_names changed nothing, which is the expected result when the ambiguity is about extent rather than identity. class_names sends names only, never descriptions or examples.

Setting pages and k

Section titled “Setting pages and k”

pages decides how much of each section the classifying call sees, and it is the only split-then-classify setting whose cost grows with section length:

  • first_k with k: 2 is the default and covers the opening identity block of nearly every form — a cover page plus the first content page.
  • first is the cheapest. Use it when every class is identifiable from its very first page, which is usually true of forms and statements.
  • all makes a long section cost roughly what page-level classification would have cost, which removes most of split-then-classify’s advantage. It is the right answer only when a class is genuinely not identifiable from its opening pages.
  • Raise k above 2 only for classes whose distinguishing content sits past the cover page — a bundle whose first page is a generic transmittal sheet, or two classes that share an opening page and differ later.

Cost is roughly linear in the pages sent. Measured on one 6-page section (Nova 2 Lite, section classification input tokens only): first sent 1 page for 1,317 input tokens, first_k with k: 2 sent 2 pages for 2,777, and all sent 6 for 6,599.

⚠️ pages and k are section classification settings and cannot change the boundaries — if your sections are wrong, this is not the axis to tune.

Four things worth knowing:

  • Each call names its own model. That is most of the point: splitting may want a capable multimodal model looking at a whole packet, while classifying a clean segment is often a much easier problem a cheaper model answers just as well. A custom or fine-tuned classification model (CustomClassificationModelARN, or Create configuration version on a fine-tuning job) is written to section classification.
  • The halves are metered separately, as Splitting/... and SectionClassification/... in the cost table and the reporting database, while the combined strategy keeps Classification/.... That split is what makes “is this actually cheaper on my documents?” answerable from the cost table rather than from arithmetic.
  • A document-name regex match skips section classification entirely. The name already asserts the class, so a name-matched 40-page packet costs its splitting calls and no classification calls at all.
  • A declared document shape skips splitting entirely. Under document_shape.sectionSplitting: disabled the whole document is one segment, and under page every page is one, so no splitting call is made.

A segment whose section classification call fails keeps no class and is reported in the document’s errors. Its boundaries are still good, and an invented class would propagate into extraction as though it had been decided.

splitting.method and section_classification.method ship with one value, llm. A boundary-detection model, embeddings-based classification and external classifier endpoints (SageMaker, a Bedrock custom model, or a Lambda adapter in front of anything else) are described in issue #1329; each needs measurement on real documents before its defaults can be set honestly. Their settings blocks (splitting.boundary_model, section_classification.embeddings, decision_model and low_confidence) are declared so adding a method later needs no configuration migration, and are ignored until their method exists.

Telling a wrong boundary from a wrong label

Section titled “Telling a wrong boundary from a wrong label”

split_accuracy_without_order requires a predicted section to match on both its page set and its class, so a wrong boundary and a wrong label are reported as the same failure — and those two call for different fixes. The evaluation report now also carries the two halves:

MetricMeans
boundary_accuracyGround-truth sections whose exact page set a predicted section matched, ignoring class
label_accuracyOf those, the fraction whose class also matched

The decomposition is exact: split_accuracy_without_order = boundary_accuracy × label_accuracy. label_accuracy is reported as not scored rather than 0.0 when no section’s boundaries matched — “we never got far enough to judge the labels” is a different fact from “every label was wrong”, and that is the pair of readings the split exists to keep apart. Both are computed for the combined strategy too.

Choosing granularity, modality and strategy

Section titled “Choosing granularity, modality and strategy”

Granularity and modality are per call: the combined call has one of each, and split-then-classify sets them separately on splitting and on section classification (which has modality only — it is always one call per section).

Use granularity: packet when

Section titled “Use granularity: packet when”
  • Boundaries depend on seeing the packet, not on each page in isolation — continuing narratives, numbered sections, a cover sheet whose role is only clear from what follows it.
  • Classification cost is a large share of the bill. Packet granularity pays the prefix and the output once instead of per page, which matters most on long packets with few sections.
  • The packet fits the window you set, or you are happy to window it. Set the call’s packet.window_pages rather than relying on a model’s context size.

Use granularity: page when

Section titled “Use granularity: page when”
  • Packets contain several sections of the same class and the boundary cue is a per-page detail (a restarting page number, a repeated header) that a per-page verdict catches reliably.
  • Processing speed matters: pages are classified in parallel, so a long packet’s wall-clock cost is roughly one call rather than N.
  • You want a per-page confidence score. Packet granularity scores per segment, which is a coarser signal for HITL routing.

Modality

Section titled “Modality”
  • Both on (the default) is the right starting point: layout and text each carry boundary and class evidence the other does not.
  • images: false is the lever for image-dominated cost, and the one to reach for first — it is usually a far larger saving than anything else here. Measure the accuracy cost on your own documents; on clean text documents it is often nil.
  • text: false suits scans whose OCR is poor enough to mislead, and requires a real OCR backend only if you still want the page-content regex shortcut (which reads the text even when it is not sent).

Page versus packet granularity: opposite failure modes

Section titled “Page versus packet granularity: opposite failure modes”

The hardest boundary case is a reprinted identity block: a multi-page document whose header, account number and address appear again on every page. Read one page at a time, every page looks like a first page. Read the packet at once, two adjacent sections of the same class look like one. Those are the same ambiguity seen from the two available vantage points, and the two granularities fail on opposite sides of it.

Measured on a matched pair of generated bank-statement fixtures, Nova 2 Lite, expected section counts from exact ground truth:

FixtureShapegranularity: pagegranularity: packet
one 3-page statement, identity header reprinted on every pageexpect 1 section3 — wrong1 — right
two 3-page statements, header on each first pageexpect 2 sections2 — right1 — wrong

Page granularity split a single statement into one section per page; packet granularity merged two adjacent statements into one. Both results held under strategy: combined and strategy: split_then_classify, so this is a property of the granularity rather than of the strategy. Choose by which error your corpus can afford. A corpus of long single-section documents is safer at packet granularity; a corpus of back-to-back same-type forms is safer at page granularity.

Two levers were measured on the over-split case and neither solves it:

  • boundary_hints: class_names left it at 3 sections. Putting the class names into the boundary prompt does not help when the ambiguity is about where one section ends, not about what kind it is.
  • contextPagesCount: 1 improved it from 3 sections to 2 — a real improvement, not a fix — and on the other fixture the same setting moved a correct 3-section answer to 2. That is the over-merge trade this page warns about, measured in both directions on one pair of fixtures: showing a page its neighbours makes continuation pages easier to recognise and makes two back-to-back sections of the same class easier to confuse.

If neither error is acceptable, assert the shape instead of detecting it: document_shape.sectionSplitting: disabled gives a document known to hold a single section exactly one section, and page gives a document of one-page sections exactly one section each. Both are assertions, so they are only right when you know the shape — see Section Splitting.

Strategy

Section titled “Strategy”
  • Combined (combined) for single-page documents and short packets, where split-then-classify adds a call to save a prefix that was only paid once.
  • Split-then-classify (split_then_classify) for long documents with few sections, when you want a different model for classifying than for splitting, or when you need to know whether your section errors are boundary errors or label errors.

Why the prefix saving is smaller than it looks

Section titled “Why the prefix saving is smaller than it looks”

The argument for split-then-classify above is that a combined boundary decision carries the class vocabulary it does not need. That is true, and it is not worth the list price of those tokens, because the prefix is cached. The default classification model, us.amazon.nova-2-lite-v1:0, is in CACHEPOINT_SUPPORTED_MODELS in lib/idp_common_pkg/idp_common/bedrock/client.py, the shipped combined prompts put the class list, the descriptions and the few-shot examples before <<CACHEPOINT>>, and config_library/pricing.yaml prices that model’s cacheReadInputTokens at a quarter of its inputTokens with cacheWriteInputTokens at zero. So from the second page of a run onward the prefix the combined strategy “wastes” is billed at 25% of list and was free to write. Split-then-classify can therefore recover at most three quarters of the prefix on a cache-hit page — and it spends a whole extra request per section to do it.

Which way that nets out depends on how many pages each section has, so measure it rather than reasoning about it. ⚠️ The figures below are one regime, and it is the regime least favourable to split-then-classify — a 3-page document holding three 1-page sections, a 2-class vocabulary with short descriptions, Nova 2 Lite, classification Bedrock tokens only. One page per section means the per-section second call is a whole extra request against a prefix that was small to begin with. Do not read it as a general result:

At each granularity split-then-classify cost about twice the fresh input tokens and twice the requests. Section counts were correct in all four cells, so this is a cost difference and not an accuracy trade. (Cache-read volumes are omitted deliberately: they depend on what else had recently run against the same prefix, so single runs are not comparable on that column.)

The durable reasons to pick split-then-classify are not the prefix:

  • One classification call per section instead of per page. This is the one that scales, and it is the opposite of the regime measured above: on a 40-page statement, the combined strategy makes 40 classification calls to produce one answer and split-then-classify makes one splitting pass plus one classification call. The longer your sections, the better split-then-classify looks.
  • A different model per call. Splitting and classification are different problems and the cheapest model that is good at one is often not the other. The combined strategy has a single model field for both.
  • The boundary_accuracy / label_accuracy decomposition, which tells you which half to fix. See Telling a wrong boundary from a wrong label.

Measure on your own corpus. The two calls are metered separately (Splitting/ and SectionClassification/, against the combined strategy’s Classification/), so the cost table answers the question directly.

Schema-walking rules

Section titled “Schema-walking rules”
  • Flat scalar properties surface by their property name (e.g. appraised_value).
  • Nested object properties are flattened to dotted paths (e.g. borrower.address.zip).
  • Arrays of objects are unwrapped — each item-property is rendered as parent.child (no [] indexing).
  • Arrays of scalars (or arrays without item properties) surface by their parent name only.
  • Subschemas declared as a local $ref into the class’s $defs — which is what the Web UI’s schema editor emits for every group and list-item shape — are dereferenced first, so a $ref group renders exactly like an equivalent inline group (Signatures.Signature-of-taxpayer1, not a bare Signatures). $ref chains are followed; a $ref that cannot be resolved (dangling or remote) surfaces by its property name only rather than failing the classification. A recursive definition is walked normally and only stops where it re-enters itself — a Node with a child: {"$ref": "#/$defs/Node"} member yields root.label, root.child and root.kids, with child/kids as leaves.
  • Very deeply nested schemas are truncated. Because a $defs definition may be referenced from many sibling branches, dereferencing can expand a small schema into a very large attribute list, so the walk stops at 500 names and logs a warning. Prefer flatter schemas if you hit it.
  • Classes that have no JSON Schema render <attributes>(no schema)</attributes> so the absence is obvious for debugging.

Soft cap and token-cost guardrails

Section titled “Soft cap and token-cost guardrails”

To prevent pathologically large schemas from bloating the classification prompt, the rendered attribute list per class is soft-capped at 50 field names (ClassificationService.MAX_ATTRIBUTES_PER_CLASS). When a class exceeds the cap, the rendered list is truncated and a ...(+N more) suffix is appended; a WARNING log line is emitted for visibility.

If you have a class with hundreds of attributes, prefer:

  1. Writing a richer class description that captures distinguishing characteristics, or
  2. Adding few-shot classification examples for that class.

Classification Confidence

Section titled “Classification Confidence”

Classification can report how confident it is in the class it chose, per page and per section. This is separate from the per-field confidence that extraction produces (see extraction-and-confidence.md); this one is about the class, not the extracted values.

Both confidence and classification_reason are read and persisted. A prompt that asks for either — including a hand-written one — has the value stored on the page or section and surfaced in the Web UI, the document JSON and the reporting database. Releases before #673 discarded them, so a prompt carrying them starts producing scores on upgrade.

Where a score comes from

Section titled “Where a score comes from”

There is no separate confidence inference for classification: the value comes out of the same response as the class. Each class-assigning call’s confidence.mode (classification.combined.llm.confidence.mode, and the same under split_then_classify.section_classification.llm) composes the instruction into the prompt for you — it is on by default — and a custom prompt that asks for confidence or candidates itself is honoured either way, because the response parser is not gated on the setting.

Editable in the Web UI under Configuration → Classification → Class confidence, or in YAML:

ModeWhat the model is asked forNotes
topk (default)ranked candidate classes with probabilitiesBest calibrated, and it answers “what else could this have been?”
verbalizedone self-reported 0-1 numberCheapest and the most overconfident.
offnothing extraCosts nothing at all.

topk is the default for a measured reason. Asking for a single number gets ~0.95 on everything; making the model enumerate and rank alternatives forces it to distribute probability mass instead (Tian et al., Just Ask for Calibration, EMNLP 2023 — the same reasoning behind extraction’s G1/P1 confidence path). It produces exactly the “80 % W-2, 15 % 1099” shape, and the runner-ups are stored and shown in the UI.

What it costs: measured over 298 pages of a 13-class corpus, topk added +17 % to the classification step — which is only ~3 % of total document cost on the default model, so ~0.5 % of the bill, inside normal run-to-run variance. It changed classification accuracy by nothing consistent (+0.013 on Nova 2 Lite, −0.007 on Haiku 4.5, opposite signs, single runs). Page-level classification is one inference per page, so if you process very large packets and want none of this, off costs exactly nothing. See the classification-confidence benchmark.

A page is scored on the probability of the class actually stored, not simply the highest probability in the list — those differ when the model’s class disagrees with its own ranking, and the top probability would then describe a class the page was not given. Candidate classes outside your configured vocabulary are dropped (they cannot be stored, so they cannot be reported), and probabilities are rescaled only if they sum to more than 1.0; mass left unassigned below 1.0 legitimately means “possibly some other class”.

The instruction block is spliced in before the document content so it stays inside the prompt-cache prefix, and it is skipped for a prompt that already carries a <class-confidence> block. Both blocks are editable config (confidence.task_prompt_topk / task_prompt_verbalized), like every other prompt here. At combined packet granularity the per-segment variants, task_prompt_topk_packet / task_prompt_verbalized_packet, are spliced instead, because that call returns a segment list rather than one object per page.

Writing it into your own prompt works too:

The parse is tolerant: 0.95, "0.95", 95, and "95%" all read as 0.95. A string with a percent sign is always divided by 100, so "0.9%" reads as 0.009. A value that is unparseable or out of range is ignored (the page is simply unscored) rather than failing the classification.

BDA’s matched-blueprint confidence is read the same way, except that a percentage string is unscored rather than rescaled. An unscored blueprint is held for review in both legacy HITL and review-queue mode.

⚠️ Confidence multiplies output tokens per PAGE. Page-level classification runs one inference per page, so anything added to its output format is paid for on every page of every document — unlike extraction’s confidence, which is per section. Reasoning text in particular is not free.

Not scored vs. scored 1.0

Section titled “Not scored vs. scored 1.0”

An absent confidence means NOT SCORED, and it is stored as null, not as a number. Nothing invents a value:

SituationConfidence

Prompt asks for no confidence (mode: off, or a custom prompt that asks for none)not scored

SageMaker/UDOP backendnot scored (the endpoint returns no score)
Page classification errored0.0

⚠️ The disabled row is the one that catches people out, because it makes a whole section unscored from a single disagreeing page. Under sectionSplitting: disabled every page takes the voted class, and a page that predicted something else keeps no confidence — combined with the minimum rule below, one disagreement leaves the entire document’s section unscored. A page that produced no verdict of its own is different: it inherits its segment’s class and its confidence, so silence does not count as disagreement.

This distinction matters because the aggregated value reaches the reporting lake as section_confidence: a fabricated 1.0 there would be indistinguishable from a genuinely confident classification and would silently corrupt any analysis of it.

Section confidence is the lowest page confidence

Section titled “Section confidence is the lowest page confidence”

A section’s confidence is the minimum across its pages, and not scored if any of its pages is unscored. A mean would hide the one page the classifier was unsure about — which is the page a reviewer needs — and a section’s class cannot be more certain than its least certain page.

Where it shows up

Section titled “Where it shows up”

  • Web UI — a Class Confidence column in the Document Pages table on the document detail page, beside Class/Type rather than inside it. It sorts, so you can put the least-confident pages first — which is how you find the ones worth a second look. The percentage is a link: click it for “Why this class?”, the model’s own reasoning plus the ranked alternatives it considered with their probabilities. A page the model scored but did not explain shows the number as plain text; an unscored page shows —, never 0%.

    The Document Sections table deliberately does not show a section’s class confidence. It is an aggregate (the minimum across the section’s pages) of numbers already listed per page in the table directly below, and two extra columns squeezed that table until its own headers wrapped. Section.Confidence is still on the API and still lands in the reporting lake as section_confidence. The Low Confidence Fields column there is a different measurement entirely — per-extracted-field confidence, not the class.

    The number is deliberately shown the same way at every value. There is no configured classification confidence threshold (unlike extraction fields), so a green/amber/red band would assert a pass/fail the system has not defined — and on a classifier that answers ~0.95 for most pages it would paint a coarse flag as a calibrated traffic light.

  • API — Page.ClassConfidence, Page.ClassReason, Page.ClassCandidates and Section.Confidence on getDocument and getDocumentVersion. The UI keeps these fresh by polling those queries; there is no document subscription. Named ClassConfidence on a page because TextConfidenceUri there is OCR confidence — a different measurement.

  • Reporting / analytics — the existing section_confidence column, which now carries a real value when one exists and null when it does not.

  • Document JSON — pages.<id>.confidence, pages.<id>.classification_reason and sections[].confidence, each omitted when absent.

Calibration: measure it before you act on it

Section titled “Calibration: measure it before you act on it”

A single self-reported confidence is usually poorly calibrated — models asked “how sure are you?” answer ~0.95 almost everywhere, which is worse than no score because it invites automated escalation on noise. Smaller models are the most overconfident, and the default classification model is a small one. That is why the shipped mode is topk rather than verbalized: ranking alternatives against each other is what makes the number carry information, where a single self-reported figure mostly does not. off is for a deployment that will not act on the score — it is the only setting that saves the output tokens.

This is measured, not asserted. On 298 pages of a deliberately confusable 13-class corpus, in topk mode (full study):

Calibration separation+0.044+0.207

Equally accurate; not equally informative. Nova 2 Lite answered 0.95 for 90 % of pages including half its own errors, so its score is a coarse triage flag at best. Haiku 4.5’s is actionable — and costs 6.4× more per page. Decide that trade deliberately; do not assume the number is useful because it exists.

You can measure this directly, and you should before wiring it to anything automatic. With ground truth available, the evaluation report’s per-page classification details now record the classifier’s own confidence next to whether the class was correct:

The number that matters is the separation: mean confidence on correctly classified pages minus mean confidence on incorrectly classified ones. A healthy signal separates them clearly; near zero means the model is equally confident when it is right and when it is wrong, and the score should not be used to route work no matter how reasonable the individual values look. The benchmark harness reports this as class_calibration_separation alongside class_accuracy and n_class_scored_pages, and treats a drop of 0.03 as a regression.

Two cheap signals are already reliable and cost nothing extra:

  • a page whose class came back invalid and needed a re-prompt (or fell back to fallback_class) — the classifier demonstrably struggled;
  • a page classified as unclassified or a blank-page class.

Regex-Based Classification for Performance Optimization

Section titled “Regex-Based Classification for Performance Optimization”

Pipeline mode supports optional regex-based classification that can provide significant performance improvements and cost savings by bypassing LLM calls when document patterns are recognized.

Document Name Regex (All Pages Same Class)

Section titled “Document Name Regex (All Pages Same Class)”

When you want all pages of a document to be classified as the same class, you can use document name regex to instantly classify entire documents based on their filename or ID:

Benefits:

  • Deterministic class: every page of a matched document gets the matching class, and the model’s own class output is never used for it
  • No inference when no boundary decision is needed: a single-page document, or any document under sectionSplitting: disabled or page, is classified without any model call and uses no tokens

When document ID matches the pattern:

  • All pages are classified as the matching class
  • Sections follow sectionSplitting: disabled creates one section over all pages, page creates one section per page, and llm_determined (the default) on a single-page document creates one section — in all three cases no backend call is made
  • Under llm_determined, a multi-page document still calls the model, because the name says what the document is but not where each section starts. With the combined strategy the model supplies the boundaries and its class output is replaced by the matched class; with split_then_classify only the splitting call runs and section classification is skipped. Set sectionSplitting: disabled to keep multi-page matches at zero inference when one file is always one document
  • Info logging confirms the regex match

Page Content Regex (Page Granularity)

Section titled “Page Content Regex (Page Granularity)”

For multi-class configurations using the combined strategy at page granularity (classification.combined.granularity: page), you can use page content regex to classify individual pages based on text patterns:

Benefits:

  • Selective Performance Gains: Pages matching patterns are classified instantly
  • Mixed Processing: Some pages use regex, others fall back to LLM
  • Cost Optimization: Reduced token usage proportional to regex matches
  • Maintained Accuracy: LLM fallback ensures all pages are properly classified

How it works:

  • Each page’s text content is checked against all class regex patterns
  • First matching pattern wins and classifies the page instantly
  • Pages with no matches use standard LLM classification
  • A matched page is recorded with a continue boundary, so under sectionSplitting: llm_determined it joins the preceding section whenever that section has the same class: consecutive pages of one class form a single section, whether each was matched by the regex or classified by the model

Best Practices for Classification

Section titled “Best Practices for Classification”
  1. Provide Clear Class Descriptions: Include distinctive features and common elements
  2. Use Few Shot Examples: Include 2-3 diverse examples per class
  3. Choose the Right Granularity: Use page granularity with sequence segmentation for packets, packet granularity for context-dependent documents
  4. Balance Class Coverage: Ensure all expected document types have classes
  5. Monitor and Refine: Use the evaluation framework to track classification accuracy
  6. Consider Visual Elements: Describe visual layout and design patterns in class descriptions
  7. Test with Real Documents: Validate classification against actual document samples
  8. Optimize Image Dimensions: Configure appropriate image sizes based on document complexity and processing requirements
  9. Balance Quality vs Performance: Higher resolution images provide better accuracy but consume more resources
  10. Consider Output Format: Use YAML prompts for token efficiency, especially with complex nested responses
  11. Leverage Format Flexibility: Take advantage of automatic format detection to optimize prompts for different use cases
  12. Understand Boundary Indicators: Review the document_boundary metadata to understand how the document is being split into sections
  13. Handle Packets: Use sequence segmentation when processing documents containing several sections of the same class
  14. Test Segmentation Logic: Verify that sections are correctly separated by reviewing section boundaries in the results
  15. Consider Document Flow: Ensure your document classes account for typical document structures (headers, body, footers)
  16. Leverage BIO-like Tagging: Take advantage of the automatic boundary detection to eliminate manual packet splitting
  17. Use Regex for Known Patterns: Add regex patterns for document types with predictable content or naming conventions
  18. Test Regex Thoroughly: Validate regex patterns against diverse document samples before production use
  19. Balance Regex Specificity: Make patterns specific enough to avoid false matches but flexible enough to catch variations
  20. Monitor Regex Performance: Track how often regex patterns match vs fall back to LLM classification
