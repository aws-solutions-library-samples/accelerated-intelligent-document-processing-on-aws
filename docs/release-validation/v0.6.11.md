## Verdict

✅ **Ship** — the published artifact deploys in every shipped configuration, upgrades cleanly
from 0.6.10 without changing extracted values, and shows no accuracy or cost regression. **7
of 8 tiers pass; tier G (browser UX) is NOT RUN**, for want of a browser on the validation
host. **No finding is attributable to this release.**

**Tier G's scope is the whole web UI, not one flow.** `git diff v0.6.10..64e95c7d2 --
src/ui/` is **28 files, +1,902 / −356**: Test Studio's sortable columns and
classification-errors panel, the Document panel's cost calculation, the configuration
revision-history panel, and the issue-form links. The compensating coverage is the **UI unit
suite — 105 files, 1,215 tests, all passing** — which runs in neither `make test` nor
`make lint-cicd` and was invoked separately (`make ui-test`). Unit coverage is not a person
completing a flow.

**The release's own changes are error-path fixes**, so the healthy-document benchmark
correctly shows no movement: the A/B over 342 runs reports **0 regressions and 0
improvements**, grid cost +0.4% and wall −2.9%. A release that fixes what happens *after* a
transient Bedrock error should not move accuracy on documents that never hit one, and it does
not. Step 8 of the nightly SDLC suite — agentic extraction with large tables, the path
`#1310`/`#1014` repair — passed on the byte-identical tree, which is the end-to-end
confirmation the A/B cannot give.

**Eighteen findings, none introduced by 0.6.11.** Four are in shipped product code and all
four pre-date this release (Findings 1, 2, 11, 12). The rest are gate, test, harness or
documentation issues — including three controls that exist but do not run where it matters
(Finding 13), two reporting limits that make a published figure unsafe (Findings 15, 16), and
a vacuous pass that a completion count hides (Finding 14). Findings 11–18 are from the
published-artifact pass; 1–10 are the prerelease pass's, retained unchanged.

**Two findings from the first validation are fixed in the released code**: the library
integration tier went from **15 failures of 23 selected to 1 of 19**. Commit `5310684a3`
added credential reconciliation to `tests/conftest.py`, *corrected*
the wrong `assert "output" in response` assertions rather than deleting them, and re-homed the
`MagicMock` test to `tests/unit/`. The one remaining failure reproduces identically at
`v0.6.10`.

### Upgrade — what it changed in extracted values: nothing detectable

Fresh stack from the published 0.6.10 template → document → `update-stack` with
`UsePreviousValue` on all 90 parameters → same document. `UPDATE_COMPLETE`, zero
`ROLLBACK`/`FAILED` events, and both `UpdateSchemaConfig` and `UpdateDefaultConfig` custom
resources returned SUCCESS — the step where upgrades deadlock.

**Parameter-set diff:** 90 both sides, 0 added, 0 removed, 0 newly required, 0 default
changes. One `AllowedValues` narrowing: `KnowledgeBaseModelId` drops the two Sonnet 4 entries.
The default is unchanged (`us.amazon.nova-pro-v1:0`) and this stack held it, so the rejection
the CHANGELOG warns about was not triggered; a stack **explicitly pinned to Sonnet 4** is
refused before any resource changes.

**Output diff:** 1,934 leaf fields over 6 sections, 76 value differences — of which only **8**
are extracted business data (`inference_result`); 33 are `explainability_info`, 29 metadata or
timings, 6 `processing_report`.

**A same-version control settles those 8 as noise.** Running the identical document a third
time on the already-upgraded stack gives **15** `inference_result` differences — *more* than
the upgrade produced — and flips the same Payslip tax `Period` fields back. So the upgrade
changed nothing detectable; the 8 sit below a measured noise floor of 15. Product observation,
present at 0.6.10 too: those `Period` fields hold a monetary amount whose **sign is bistable**
across repeat runs of identical code, and casing is unstable (`JOHN` / `John`).

the UI vitest suite (tier A) and ZAP DAST against the UI host (tier B, High = 0).

## Findings

Ordered by how much they matter. **None was introduced by 0.6.11.**

### 1. The TestSet resolver answers 500 where 404 and 400 are correct — product, pre-existing

`nested/api-resolvers/src/lambda/test_set_resolver/index.py` raises bare `Exception` and
`KeyError` for not-found and missing-argument conditions, which the dispatcher renders as HTTP
500:

```
Exception: Test set '__nope__' not found        → should be 404, is 500
KeyError: 'testSetId' / 'id' / 'fileName'      → should be 400, is 500
```

The security consequence is not an authorization hole but a hole in what the authorization
tests can prove: **25 of the 460 positive authorization assertions are unproven rather than
passed**, because a 500 establishes nothing about the authorization decision that would have
been reached. Affected operations: `getTestSetDocuments`, `getAnnotationQueue`,
`getDraftLabelJob`, `estimateReviewEffort`, `openTestSetAnnotationDraft`,
`updateTestSetDocumentSections`, `reextractTestSetDocument`, `resetTestSetLabels`,
`clearDraftLabels`, `removeDocumentsFromTestSet`, `createEmptyTestSet`,
`addDocumentsToTestSet`, `getFeatureLaunchUrl`, `subscribeFeature`, `unsubscribeFeature`.

This is the same class of change 0.6.10 already made deliberately elsewhere — moving
`getFileContents`/`getFilePresignedUrl` off 500 and onto 403/400/400 — applied to the
instance and not the class.

### 2. Rule-discovery defaults produce rules the shipped validator rejects — product, pre-existing

`test_rules_discovery_with_defaults_against_medicare_sample` makes a real Bedrock call
(`global.anthropic.claude-sonnet-4-6`) against `samples/rule-validation/medicare_respiratory_pa_packet.pdf`,
gets `status: SUCCESS` with at least one rule class, and those rules then **fail the
production validator** `RulesDiscovery._validate_rules_response`:

```
Rule class 0: Missing required field: x-aws-idp-rule-type
```

So `config_library`'s `base-rule-discovery.yaml` defaults, on a real document, produce output
the code that consumes it refuses. **Reproduced on an independent second run** (95.8 s), so it
is not model non-determinism. Nothing in `discovery/` or `config_library/` changed in 0.6.11.

A second observation from the same run, minor but in the same defaults: `Failed to convert
max_tokens value '' to int. Not using max_tokens.` — the rule-discovery configuration carries
an empty `max_tokens`.

### 3. Orphaned CloudFront policies accumulate until they block every deploy — product, pre-existing

Tier C's Jobs API variant rolled back on:

```
Limit exceeded for resource of type 'AWS::CloudFront::ResponseHeadersPolicy'.
Reason: Account's Response Headers Policies limit reached. … ServiceLimitExceeded
```

The quota is `L-CF0D4FC5`, **20 per account**, adjustable, and the account sits at exactly 20.
(The `MaxItems: 100` in the `list-response-headers-policies` reply is the page size, not the
quota — easy to misread as headroom.) Thirteen of the twenty are IDP
`<stack>-security-headers-policy` entries, several belonging to stacks long deleted. The
variants that passed all set `WebUIHosting=APIGateway` and create no CloudFront distribution;
Jobs API uses the default CloudFront hosting and so hit the wall.

**Why they accumulate** — `lib/idp_sdk/idp_sdk/_core/stack.py:2199` calls

```python
cloudfront_client.delete_response_headers_policy(Id=policy_id)
```

with no `IfMatch=`. CloudFront requires the current ETag there, so **every** call fails
`InvalidIfMatchVersion` and the failure is swallowed into a `logger.warning`. That teardown
path has therefore never deleted a single orphaned policy; one run logged twelve such
warnings. The sibling implementation is correct —
`lib/idp_sdk/idp_sdk/_core/cleanup_orphaned.py:880-889` does
`get_response_headers_policy` → read `ETag` → `delete_response_headers_policy(Id, IfMatch=etag)`.

**And the test cannot catch it.** The teardown suite's fake is
`tests/unit/test_stack_deployer_teardown.py:2110`, `"delete_response_headers_policy": lambda Id, **_k:`
— a signature that accepts the missing `IfMatch` silently. The orphaned-cleanup suite's fake
declares `delete_response_headers_policy(self, Id: str, IfMatch: str)` and would have failed.

A quota increase to 100 was requested rather than deleting policies, because three of the
twenty belong to unrelated stacks in the same account.

### 4. Two tests cannot pass on a host with a managed git hooks path — test tooling

`scripts/tests/test_ai_mr_review.py::test_the_instruction_file_set_is_derived_not_authored` and
`::test_the_review_criteria_come_from_the_target_branch_not_the_mr` both build a throwaway
repository and commit to it as `t@example.invalid`. Where `/etc/gitconfig` sets a system-wide
`core.hooksPath` pointing at a corporate commit-scanning tool, that tool aborts any commit
whose author email is not the developer's registered one, so `git commit` exits 1 and the
fixture raises `CalledProcessError`.

Proven rather than inferred: `GIT_CONFIG_NOSYSTEM=1 pytest scripts/tests/test_ai_mr_review.py`
gives **38 passed, 1 skipped**. The fixture should commit with `git -c core.hooksPath= commit`.

This is the same hazard `CLAUDE.md` already documents for `make install-git-hooks`, which
deliberately writes to `--git-common-dir` rather than honouring `core.hooksPath` for exactly
this reason — again, handled at one site and not the other.

### 5. The coverage ratchet checks one of nine trees in both CIs — gate tooling

`make check-coverage-debt` runs in both CI configurations, immediately after
`make test-cicd -C lib/idp_common_pkg`. That step writes **only** the `idp_common` coverage
report. The other eight trees have no report, are correctly reported as "not checked", and
that is **not a failure** as long as something was checked — which is documented behaviour
(#1190). Neither CI passes `--require-tree`, and **nothing in either CI runs `coverage-all`**.

So the ratchet is green in CI while reading one ninth of what it is written to read. Finding 7
is what that permits in practice.

### 6. The curated SRT verdict disagrees with the gate that produced it — gate tooling

The published snapshot reads `SRT — FAIL ❌ (5 open/reopened HIGH)` for a release whose
security gate is green. The five are exactly Bandit `B105` ×2 and `B106` ×3 — the checks that
match an *identifier's name* against a password wordlist — in test code that no deployment
artifact is built from. `make srt-scan` carries that scope decision;
`scripts/security/curate_results.py` implements no equivalent.

**This record reports the gate's verdict** (PASS) and notes the snapshot's disagreement. This
is a known open issue, already described in the release-validation skill; it recurred exactly
as written.

### 7. Two modules have been measured but unratcheted for days — coverage

`idp_cli/parameters.py` and `idp_feature_sdk/parameters.py` are measured but absent from
`scripts/coverage_debt.json`, so their coverage is unratcheted. Both arrived in `9bcdc0d60` on
2026-09-24, three days before this run, and passed through seven green CI runs — because of
Finding 5, neither tree is read by the ratchet in CI.

No file in any of the nine trees **lost** coverage.

### 8. Six integration tests contradict the API's documented return shape — test tooling

Every test in `tests/integration/test_bedrock_service_tier_integration.py` asserts
`"output" in response`, but `BedrockClient.invoke_model` documents and returns
`{"response": …, "metering": …}` — `output` lives at `response["response"]["output"]`. The
Bedrock calls all **succeeded** (HTTP 200, tokens metered); only the assertion is wrong.

It became visible only in the 0.6.10 cycle: `4ae05dfab` (#1129, 2026-09-23) moved the
assertion out of a `try/except Exception` that had been converting the `AssertionError` into a
`pytest.skip` — which reads as green. So #1129 did its job, and this is the residue it
exposed.

### 9. The integration tier cannot run as documented — test tooling

`make test-integration` is `pytest -m "integration"` over the whole tree, but only
`tests/integration/conftest.py` reconciles the sentinel credentials that
`tests/conftest.py` injects (`os.environ.setdefault("AWS_ACCESS_KEY_ID", "testing")`).
Integration-marked tests living under `tests/unit/` therefore run with the sentinel key and
cannot reach AWS — `InvalidClientTokenId`, `InvalidAccessKeyId`. Two of the seven files
carrying `@pytest.mark.integration` are under `tests/unit/`, accounting for 6 of the 15
failures.

Separately, `tests/integration/test_discovery_config_integration.py` (2 failures) passes a
`MagicMock` configuration into a real code path, so `model_id` arrives as the repr of a mock
object and the production guard correctly rejects it; it also names a nonexistent
`test-bucket`.

### 10. The release-validation skill's model-axis copy is stale — documentation

The skill's F3 table names three values for the `classification_model` axis (`nova_2_lite`,
`sonnet5`, `haiku45`). The live axis in `benchmarks/matrices/config_matrix.yaml` holds **two**
— `haiku45` is not in it. The skill instructs the reader to read the axis rather than trust
the copy, which is what was done here, so the stale copy cost nothing this time; it is exactly
the failure mode the skill warns about for the `extraction_model` axis.

### 11. A whole-document request over ~300 s can never succeed, and burns the invocation — product, pre-existing

Non-streaming `converse` runs with `read_timeout = CONFIDENCE_READ_TIMEOUT_SECONDS = 300.0`
and `DEFAULT_MAX_RETRIES = 7`, inside a 900 s Lambda, and **nothing checks the remaining
invocation before starting an attempt** — `grep` finds no pre-attempt budget check in
`bedrock/client.py`, and the deadline logic that does exist says in its own comment that it
"CLAMPS a sleep; it never converts one into a failure". Measured: attempt 1 dies at ~300 s,
attempt 2 at ~606 s, attempt 3 **starts at +610.8 s with 289 s left** and is killed at 900 s;
Step Functions retries once and the `ProcessSections` map discards the document.

Consequence on the model axis: **Claude Opus 5.5 cannot complete an 800-row document in
simple mode at all** (0 of 13 cells), while Sonnet 5 and Sonnet 5 `:1m` completed all 13 of
the same cells in the same window on the same stack — so this is a per-request limit, not
contention. **Advanced (sharded) mode is a complete remedy: all six swept models return
800/800 rows, 6/6.**

**Pre-existing, not 0.6.11.** The constant is unchanged at `v0.6.10`; 0.6.11 raised the
*streamed agentic* read timeout to 600 s and added a ladder guard **on that path only**.

### 12. Integrated confidence in advanced mode fails deterministically at the control model — product, pre-existing

`cost` / `core-tt-adv-int` (`advanced` + `integrated`, extraction `sonnet46`): **5 of 5
attempts failed** on a 10-page document, wall 1014.8–1021.6 s (spread ±7 s — a fixed
structure, not model latency). The same cell with `assessment: separate` completes in
**111–127 s**; the same cell at `extraction_model: sonnet5` completed **25/25**.

From `ShardRuntimeFunction`:

```
tool_name=<provide_field_assessment> | replacing with error message due to max_tokens truncation.
MaxTokensReachedException: Agent has reached an unrecoverable state due to max_tokens limit
```

Extraction **succeeds first** — the same log records `Extraction complete for shard 1
(pages 1-5): 239 transactions captured ... All data validated successfully`. What exceeds the
budget is the per-field assessment tool output, emitted inline in the same agent loop, on
shards of ~240 rows. Sonnet 5 survives because its output budget is larger.

Related and separately measured: **26 `Runtime.OutOfMemory` failures in `AssessmentFunction`**,
killed at its 4,096 MB ceiling where every *successful* assessment peaks at **267–318 MB**. One
invocation issued **55 Bedrock calls** at ~80k input tokens each after a single
12-row → 6+6 split.

### 13. Three gates exist but do not run where it matters — gate tooling

* **The UI vitest suite runs in neither `make test` nor `make lint-cicd`.** It is a separate
  `make ui-test` target (Makefile:1181). It passes — 105 files, 1,215 tests — but only
  because this pass invoked it by hand, and it is the *only* coverage in this battery for the
  28 changed UI files.
* **`make test-integration` pins no first-party `PYTHONPATH`.** It is a bare
  `$(PYTHON) -m pytest -m "integration"`, not `$(PYTEST_HERMETIC)` — correctly, since
  `HERMETIC_AWS` strips the credentials integration tests need, but it loses the
  `FIRST_PARTY_PYTHONPATH` pin with it, so the run can measure another checkout. Still true
  on `develop` at the time of writing.
* **The coverage ratchet's three unratcheted files are still unratcheted on `develop`**, 178
  commits later. The CI half that would make it fail
  ([#1292](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/pull/1292))
  is open.

### 14. The `forcing` axis is a vacuous pass for Opus 5.5 — test tooling, now measured

Its `force-on` cells reach `COMPLETED`, which is why a completion count must not be read as a
result: `forced_tool_attempted = 0`, `forced_tool_honored_rate = None`, and
`forced_tool_skips` carries Bedrock's refusal verbatim — `tool_choice: type "tool" and "any"
are not supported for this model`. The cells ran with `toolChoice: auto`. **Every other arm
honoured forcing at rate 1.00** (`core` 224/224 across 138 cells; all eleven sweep arms 7/7 or
8/8), and that identity is what makes the axis's neutrality finding meaningful at all. v0.6.11
upgrades this from a model-card claim to an observed API refusal.

### 15. Two cost figures in the guidance are lower bounds, not measurements — reporting

`pricing.yaml` holds one flat rate per model and cannot express a usage-dependent band, but
two swept models have one: **Haiku 5.5** is billed 5× on every token type above 100,000 input
tokens, and **GPT-6 Astra** moves to a long-context band above 272,000. Both are crossed in
practice — **105 of Haiku 5.5's 129 completed runs exceed 100,000 input tokens** (median
543,675, max 10.96M). At the full 5× its $0.149/doc becomes ~$0.77 against Sonnet 5's $0.571,
so the **sign** of the comparison is unresolved. No cost *ratio* for either model is published;
both are labelled in-table. Closing it needs per-request token capture in the harness or a
two-band `pricing.yaml` entry. Same class as the `:1m` premium that once inflated an arm from
$68.82 to $125.42 (#899).

### 16. The reference corpora produced cost but no accuracy — harness

All **2,280** corpus rows (`realkie` 1,140, `ocr_bench` 1,140, 20 documents each) reached
`COMPLETED` with **0 failures**, and carry cost ($0.1932 and $0.0395 per document) and
latency. But `cells_compared` is **0** and `scalar_accuracy` / `cell_accuracy` /
`completeness_recall` are all `nan` — nothing was scored against ground truth. So
**`config-guidance.md` §2.3's real-corpus accuracy tables could not be refreshed** and keep
their v0.6.9 numbers; their first sentence says so. Cost and latency for the corpora *are*
new. Cause not yet established — the per-class truth wiring is the obvious suspect, since
these runs score per `sub_doc` where the synthetic documents score per `doc`.

### 17. Typed accuracy is unobtainable from this corpus — harness scope

`typed_accuracy` is `None` on **all 4,704 completed rows** in every scored set.
`analyze.py` populates it "only for truth files that declare `fields_typed`", and of the 24
truth files in `benchmarks/corpus/docs` exactly **one** does (`kv_form.pdf`, 8 fields) — every
other carries `rows_typed`, which feeds `cell_accuracy`. The F3 model table therefore **omits
the typed-accuracy column with that reason stated**, rather than printing blanks that read as
zero. `cell_accuracy` is the per-value metric here and is populated for all 23 sets (~62,000
compared cells per arm).

### 18. Four stale claims in the benchmarking documentation — documentation

None is a product defect. All four are corrected in the accompanying benchmark PR:

1. `config-guidance.md` was headed **v0.6.9** and attributed §2–§4 and §7 to "Sonnet 5 (the
   shipped default)". Those sections are measured at **Sonnet 4.6, the cross-version
   control** — so every number in them was attributed to the wrong model.
2. `index.md` listed the classification axis as four models including **Haiku 4.5**; the live
   axis is three and `config_matrix.yaml` states Haiku 4.5 is deliberately not swept.
3. Both **Opus 5.5** and **Haiku 5.5** were marked ❌ *not yet measured*.
4. The release-validation skill's own copy of `sweeps.extraction_model` lists **7** models;
   the axis holds **8**. A sweep driven from the copy runs one model short. Finding 10 is a
   separate instance of the same drift, on a different axis.

`index.md` now states the rule that prevents it: **read the axis in `config_matrix.yaml`,
not a prose list of it.**

## What was NOT validated

Six gaps the prerelease pass listed are now closed: the published artifact, the Jobs API
variant, the guidance-paper refresh (2,628 runs), the `cost` suite, the A/B wall-time
comparison (both sides ran alone on the same stack), and `dd0b7ecdf`.

The following remain unvalidated:

- **The web UI, in a browser.** Tier G did not run on either pass. No flow was driven by a
  person or an agent. This matters more than the prerelease pass concluded, because **28 UI
  files changed between the two passes** — Test Studio sorting and its classification-errors
  panel, the Document panel's cost calculation, the configuration revision-history panel, and
  the issue-form links. Adjacent coverage that *did* run: the UI vitest suite (1,215 tests),
  ZAP DAST against the UI host (High = 0), and the nightly SDLC suite's Test Studio
  evaluation step. None of those is a person completing a flow.
- **Real GovCloud.** The `--govcloud` tier ran in `us-west-2` on the **commercial partition**
  with commercial credentials. It proves the CloudFront-free, API-Gateway-hosted template
  deploys and processes a document. It proves **nothing** about partition ARNs, GovCloud model
  availability or the BDA project rejection. The Knowledge Base was **disabled** in that run
  (`DocumentKnowledgeBase=DISABLED`, the runner default).
- **Real-corpus accuracy.** The 2,280 reference-corpus runs produced cost and latency but no
  scored accuracy (Finding 16), so `config-guidance.md` §2.3 keeps its v0.6.9 numbers.
- **Typed accuracy.** Unobtainable from this corpus — one truth file of 24 declares
  `fields_typed` (Finding 17).
- **Confidence discrimination.** Not estimable at this corpus's 0.08–0.10% error rate; the
  harness marks `calibration_reliable` false on 104 of 129 runs per arm. The AUROC column is
  omitted from §5.4 rather than quoted.
- **`idp_cli` integration tests.** Zero exist — 1,347 collected, 1,347 deselected. An empty
  suite, not a pass.
- **The seller positive path.** A token issued and verified needs `--entitled-profile`.
- **Coverage of `src/lambda` and `nested/api-resolvers`** (145 files between them). Outside
  the nine-tree coverage gate; not measured here.
- **An upgrade from a stack pinned to Sonnet 4.** The `KnowledgeBaseModelId` rejection the
  CHANGELOG documents was not triggered, because the test stack held the default. Verified
  statically from the template diff, not by a failed update.
- **Whether advanced mode rescues the assessment OOM** (Finding 12's second half) and
  **whether the integrated-confidence failure reproduces at other document sizes**.
