## Verdict

✅ **Ship as measured** — 6 tiers pass, 1 not run, 1 partially run, with no finding
attributable to this release.

**The single most useful fact about 0.6.11 is how small it is.** `git diff v0.6.10..3ca2dcc4d`
touches exactly two files of product code — `idp_common/extraction/agentic_idp.py` (+97) and
`idp_common/utils/bedrock_utils.py` (+162) — plus one CLI line, six version bumps, one README
and three test files. Nothing in `discovery/`, `config_library/`, `nested/`, `patterns/` or
`src/`. That bounds what this release could have regressed, and it is the basis on which every
pre-existing finding below is attributed to an earlier release rather than to this one.

**Both changes are error-path fixes**, so the healthy-document benchmark correctly shows no
movement: the release A/B over 342 runs reports **0 regressions and 0 improvements**. A
release that fixes what happens after a transient Bedrock error should not move accuracy on
documents that never hit one, and it does not.

**Nine findings, none of them introduced by 0.6.11.** Two are in shipped product code and both
pre-date this release (Findings 1 and 2). Six are in test or gate tooling, and two of those
describe controls that exist but cannot fire (Findings 5 and 7) — the defect class this
repository documents most often. One is an account quota that blocked a deploy variant
(Finding 3).

## Findings

Ordered by how much they matter. **None was introduced by 0.6.11.**

### 1. The TestSet resolver answers 500 where 404 and 400 are correct — product, pre-existing

`nested/api-resolvers/src/lambda/test_set_resolver/index.py` raises bare `Exception` and
`KeyError` for not-found and missing-argument conditions, which the dispatcher renders as HTTP
500:

```
Exception: Test set '__nope__' not found        → should be 404, is 500
KeyError: 'testSetId' / 'id' / 'fileName'      → should be 400, is 500
```

The security consequence is not an authorization hole but a hole in what the authorization
tests can prove: **25 of the 460 positive authorization assertions are unproven rather than
passed**, because a 500 establishes nothing about the authorization decision that would have
been reached. Affected operations: `getTestSetDocuments`, `getAnnotationQueue`,
`getDraftLabelJob`, `estimateReviewEffort`, `openTestSetAnnotationDraft`,
`updateTestSetDocumentSections`, `reextractTestSetDocument`, `resetTestSetLabels`,
`clearDraftLabels`, `removeDocumentsFromTestSet`, `createEmptyTestSet`,
`addDocumentsToTestSet`, `getFeatureLaunchUrl`, `subscribeFeature`, `unsubscribeFeature`.

This is the same class of change 0.6.10 already made deliberately elsewhere — moving
`getFileContents`/`getFilePresignedUrl` off 500 and onto 403/400/400 — applied to the
instance and not the class.

### 2. Rule-discovery defaults produce rules the shipped validator rejects — product, pre-existing

`test_rules_discovery_with_defaults_against_medicare_sample` makes a real Bedrock call
(`global.anthropic.claude-sonnet-4-6`) against `samples/rule-validation/medicare_respiratory_pa_packet.pdf`,
gets `status: SUCCESS` with at least one rule class, and those rules then **fail the
production validator** `RulesDiscovery._validate_rules_response`:

```
Rule class 0: Missing required field: x-aws-idp-rule-type
```

So `config_library`'s `base-rule-discovery.yaml` defaults, on a real document, produce output
the code that consumes it refuses. **Reproduced on an independent second run** (95.8 s), so it
is not model non-determinism. Nothing in `discovery/` or `config_library/` changed in 0.6.11.

A second observation from the same run, minor but in the same defaults: `Failed to convert
max_tokens value '' to int. Not using max_tokens.` — the rule-discovery configuration carries
an empty `max_tokens`.

### 3. Orphaned CloudFront policies accumulate until they block every deploy — product, pre-existing

Tier C's Jobs API variant rolled back on:

```
Limit exceeded for resource of type 'AWS::CloudFront::ResponseHeadersPolicy'.
Reason: Account's Response Headers Policies limit reached. … ServiceLimitExceeded
```

The quota is `L-CF0D4FC5`, **20 per account**, adjustable, and the account sits at exactly 20.
(The `MaxItems: 100` in the `list-response-headers-policies` reply is the page size, not the
quota — easy to misread as headroom.) Thirteen of the twenty are IDP
`<stack>-security-headers-policy` entries, several belonging to stacks long deleted. The
variants that passed all set `WebUIHosting=APIGateway` and create no CloudFront distribution;
Jobs API uses the default CloudFront hosting and so hit the wall.

**Why they accumulate** — `lib/idp_sdk/idp_sdk/_core/stack.py:2199` calls

```python
cloudfront_client.delete_response_headers_policy(Id=policy_id)
```

with no `IfMatch=`. CloudFront requires the current ETag there, so **every** call fails
`InvalidIfMatchVersion` and the failure is swallowed into a `logger.warning`. That teardown
path has therefore never deleted a single orphaned policy; one run logged twelve such
warnings. The sibling implementation is correct —
`lib/idp_sdk/idp_sdk/_core/cleanup_orphaned.py:880-889` does
`get_response_headers_policy` → read `ETag` → `delete_response_headers_policy(Id, IfMatch=etag)`.

**And the test cannot catch it.** The teardown suite's fake is
`tests/unit/test_stack_deployer_teardown.py:2110`, `"delete_response_headers_policy": lambda Id, **_k:`
— a signature that accepts the missing `IfMatch` silently. The orphaned-cleanup suite's fake
declares `delete_response_headers_policy(self, Id: str, IfMatch: str)` and would have failed.

A quota increase to 100 was requested rather than deleting policies, because three of the
twenty belong to unrelated stacks in the same account.

### 4. Two tests cannot pass on a host with a managed git hooks path — test tooling

`scripts/tests/test_ai_mr_review.py::test_the_instruction_file_set_is_derived_not_authored` and
`::test_the_review_criteria_come_from_the_target_branch_not_the_mr` both build a throwaway
repository and commit to it as `t@example.invalid`. Where `/etc/gitconfig` sets a system-wide
`core.hooksPath` pointing at a corporate commit-scanning tool, that tool aborts any commit
whose author email is not the developer's registered one, so `git commit` exits 1 and the
fixture raises `CalledProcessError`.

Proven rather than inferred: `GIT_CONFIG_NOSYSTEM=1 pytest scripts/tests/test_ai_mr_review.py`
gives **38 passed, 1 skipped**. The fixture should commit with `git -c core.hooksPath= commit`.

This is the same hazard `CLAUDE.md` already documents for `make install-git-hooks`, which
deliberately writes to `--git-common-dir` rather than honouring `core.hooksPath` for exactly
this reason — again, handled at one site and not the other.

### 5. The coverage ratchet checks one of nine trees in both CIs — gate tooling

`make check-coverage-debt` runs in both CI configurations, immediately after
`make test-cicd -C lib/idp_common_pkg`. That step writes **only** the `idp_common` coverage
report. The other eight trees have no report, are correctly reported as "not checked", and
that is **not a failure** as long as something was checked — which is documented behaviour
(#1190). Neither CI passes `--require-tree`, and **nothing in either CI runs `coverage-all`**.

So the ratchet is green in CI while reading one ninth of what it is written to read. Finding 7
is what that permits in practice.

### 6. The curated SRT verdict disagrees with the gate that produced it — gate tooling

The published snapshot reads `SRT — FAIL ❌ (5 open/reopened HIGH)` for a release whose
security gate is green. The five are exactly Bandit `B105` ×2 and `B106` ×3 — the checks that
match an *identifier's name* against a password wordlist — in test code that no deployment
artifact is built from. `make srt-scan` carries that scope decision;
`scripts/security/curate_results.py` implements no equivalent.

**This record reports the gate's verdict** (PASS) and notes the snapshot's disagreement. This
is a known open issue, already described in the release-validation skill; it recurred exactly
as written.

### 7. Two modules have been measured but unratcheted for days — coverage

`idp_cli/parameters.py` and `idp_feature_sdk/parameters.py` are measured but absent from
`scripts/coverage_debt.json`, so their coverage is unratcheted. Both arrived in `9bcdc0d60` on
2026-09-24, three days before this run, and passed through seven green CI runs — because of
Finding 5, neither tree is read by the ratchet in CI.

No file in any of the nine trees **lost** coverage.

### 8. Six integration tests contradict the API's documented return shape — test tooling

Every test in `tests/integration/test_bedrock_service_tier_integration.py` asserts
`"output" in response`, but `BedrockClient.invoke_model` documents and returns
`{"response": …, "metering": …}` — `output` lives at `response["response"]["output"]`. The
Bedrock calls all **succeeded** (HTTP 200, tokens metered); only the assertion is wrong.

It became visible only in the 0.6.10 cycle: `4ae05dfab` (#1129, 2026-09-23) moved the
assertion out of a `try/except Exception` that had been converting the `AssertionError` into a
`pytest.skip` — which reads as green. So #1129 did its job, and this is the residue it
exposed.

### 9. The integration tier cannot run as documented — test tooling

`make test-integration` is `pytest -m "integration"` over the whole tree, but only
`tests/integration/conftest.py` reconciles the sentinel credentials that
`tests/conftest.py` injects (`os.environ.setdefault("AWS_ACCESS_KEY_ID", "testing")`).
Integration-marked tests living under `tests/unit/` therefore run with the sentinel key and
cannot reach AWS — `InvalidClientTokenId`, `InvalidAccessKeyId`. Two of the seven files
carrying `@pytest.mark.integration` are under `tests/unit/`, accounting for 6 of the 15
failures.

Separately, `tests/integration/test_discovery_config_integration.py` (2 failures) passes a
`MagicMock` configuration into a real code path, so `model_id` arrives as the repr of a mock
object and the production guard correctly rejects it; it also names a nonexistent
`test-bucket`.

### 10. The release-validation skill's model-axis copy is stale — documentation

The skill's F3 table names three values for the `classification_model` axis (`nova_2_lite`,
`sonnet5`, `haiku45`). The live axis in `benchmarks/matrices/config_matrix.yaml` holds **two**
— `haiku45` is not in it. The skill instructs the reader to read the axis rather than trust
the copy, which is what was done here, so the stale copy cost nothing this time; it is exactly
the failure mode the skill warns about for the `extraction_model` axis.
