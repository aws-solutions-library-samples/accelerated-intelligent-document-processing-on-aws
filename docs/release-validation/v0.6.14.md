## Verdict

✅ **Ship.** The published artifact deploys in all six shipped configurations, including the
new `TenantIsolationMode=Strict` configuration, whose isolation harness passed 23 of 23
checks. Both template transforms deploy and process a real document. The upgrade from 0.6.13
completed without a version effect on extracted values, and the 342-run release A/B shows
**0 regressions and 0 improvements**, with recall and cell accuracy identical on both sides
over the same 23,370 compared cells. All four security gates pass. The two RBAC counts that
moved are exactly the four tenant-administration operations this release adds.

**All 8 tiers have a result.** Tiers A–E, G and H and F1 are recorded here. Tier F's guidance
refresh (F2–F4) is reported in the sibling benchmark pull request, [#1823](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/pull/1823).
Six of its thirty lanes were killed by a host restart on 2026-11-07 and re-run in full, with
the fifteen lanes that had not started, from 2026-11-09 (see *Tier F*).

**The finding that matters most for a customer is in the upgrade path, and it is
environmental in trigger but not in effect.** The first `update-stack` attempt failed because
the container-image build in the multi-document-discovery nested stack did not finish within
its custom resource's time budget. The rollback then failed on the same resource, leaving the
stack in `UPDATE_ROLLBACK_FAILED` until `continue-update-rollback` was run by hand. The
second attempt, with CodeBuild dispatching normally, completed in 25 m 41 s. A customer whose
CodeBuild builds queue during an upgrade would reach the same state. Finding 1, filed as
[#1824](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1824).

**This release closes all five product defects the v0.6.13 record filed.** Per-section
Re-extract no longer rewrites every section's class (#1672). It ran correctly in the browser
review. The SDK's minimal configuration now validates (#1673), and the SDK integration suite
passes 13 of 13 where it failed 1 of 13 at v0.6.13. The packet-window (#1676), blank-page
(#1677) and confidence-step memory (#1678) fixes are measured by the benchmark refresh. This
record files two Test Studio defects: one introduced in this release (Finding 2, #1816), and
one whose first appearance was not checked against v0.6.13 (Finding 3, #1817).

## Findings, most important first

### 1. An upgrade whose container build does not finish in time fails, and so does its rollback (product robustness, environment-triggered)

Tier E's first `update-stack` started at 23:08 UTC. The `DockerBuildRun` custom resource in the
multi-document-discovery nested stack failed twice with `Build … did not complete within the
Lambda budget`. Its counterpart in the unified pattern stack was cancelled, then failed during
rollback with `build did not complete - status: [STOPPED]`. The parent reached
`UPDATE_ROLLBACK_FAILED` at 23:42 UTC. `continue-update-rollback` at 00:35 UTC returned it to
`UPDATE_ROLLBACK_COMPLETE` at 00:49 UTC, and the second attempt completed normally. The
hosting-private stack-test, created at the same time, failed on the same resource and reached
`ROLLBACK_FAILED`.

The trigger was environmental: the builds those resources start did not complete in time,
during a window in which the run's notes record CodeBuild builds in the account as not
dispatching. The logs here do not establish why, or whether the queueing was account-wide.
Once builds were dispatching again, both stacks deployed. The effect on a customer is not
environmental: an upgrade during a CodeBuild slowdown does not simply fail and roll back. It
leaves the stack needing a manual `continue-update-rollback`. The repository's
`test-upgrade` skill gives that command for a rollback deadlock, but no customer-facing page
described this case at this release. Filed as [#1824](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1824) and fixed in
[#1825](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/pull/1825), which also adds the recovery to
[Troubleshooting](../troubleshooting.md#container-based-lambda-deployment-issues). The
evidence is two occurrences in this pass, both on `DockerBuildRun` (tier E's first attempt and
the hosting-private stack-test's first attempt), and the cause of the stall is not established.

### 2. Test Studio's Re-extract offer after a class change is lost on reload, and a second change names the wrong class (product defect, this release)

Tier G, flow 6.2. After a section's class is changed with **Edit Page Grouping**, the editor
offers per-section **Re-extract** with the note "These fields were extracted as *class*". That
offer is held only in React state (`reclassified` in `test-set-editor-slots.tsx`). It is
lost on a page reload, although the section's fields still belong to the old class. It also
records the class from *before the latest* change rather than the class the fields came from.
A second change therefore names the wrong one: the note said "extracted as W2" for fields
extracted as Bank-checks. The per-section Re-extract that #1672 needed now works correctly when
it is offered. Filed as
[#1816](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1816).

### 3. A test set created from S3 files with no baselines fails after being reported created (product defect)

Tier G. The **From files in S3** wizard, pointed at documents with no baseline files, says on
one step that unlabeled documents will arrive and in a hint that they are skipped. It then
reports the set as created, and the set ends in `FAILED`. Adding documents is then refused
because the set is "not in COMPLETED status", so the only remedy is to delete and recreate it.
Whether v0.6.13 behaves the same way was not checked. Filed as
[#1817](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1817).

### 4. The upgrade changed no extracted value consistently; one post-upgrade run silently dropped two of three tax rows (measurement)

Across the two v0.6.13 runs and five v0.6.14 runs of `lending_package.pdf`, every value
difference is inconsistent within one version or the other:

| field | v0.6.13 (2 runs) | v0.6.14 (5 runs) |
|---|---|---|
| Payslip name and address fields, e.g. `EmployeeName.FirstName` | `"JOHN"` in 1, `"John"` in 1 | `"JOHN"` in 5 |
| Payslip `FederalTaxes` | 3 rows in both | 3 rows in 4, **1 row in 1** |
| Bank-checks `check_number` | `"0000000000"` in 1, `"0001379"` in 1 | `"0000000000"` in 4, `"0001379"` in 1 |
| Bank-Statement `account_holder_address.State` | null in both | null in 3, `"USA"` in 2 |
| driver's licence `ENDORSEMENTS` / `RESTRICTIONS` | `[]` in both | `[]` in 3, null or `["NONE"]` in 2 |

So there is no consistent version effect on this document. Two observations are worth naming:

- **One run returned a shortened list as a success.** The fifth v0.6.14 run returned one of
  the Payslip's three `FederalTaxes` rows (Social Security and Medicare are missing). Its
  section reported `Status: SUCCESS` with no processing issue, from a single traditional
  extraction pass on Claude Sonnet 5, the preset's extraction model. One run in seven is too few to
  attribute to the release, but the list loss itself was silent. Not filed. It fits the
  standing silent list-loss class that the benchmark paper's hazards section tracks, rather
  than a new defect.
- **The tax-amount signs are now stable.** All seven runs report the tax amounts as negative,
  where the v0.6.13 record saw one positive in five.

There is no ground-truth baseline for this sample in the repository, so which value is correct
was not scored.

### 5. The A/B asymmetry the v0.6.13 record left open recurred on v0.6.13 and not on v0.6.14 (improvement, inferred)

The v0.6.13 record found that two of three v0.6.13 runs of the `bedrock_llm` arm split
`longdesc_100`, a one-section document, into two sections, against none of three on v0.6.12.
It left open whether this was a release effect or OCR run-to-run variation. In this pass's
PREV side, v0.6.13 split it in **two of three runs again**, and v0.6.14 split it in **none
of three**. Both inconclusive rows in F1 follow from that: the arm's cost fell 45% and its
scalar accuracy rose to 1.000. Two independent v0.6.13 grids showing the same 2-of-3 split,
against 0-of-3 on the releases either side, points to a v0.6.13 behaviour that v0.6.14
removed. That reading is inferred from n = 3 per side, and no single change in this release
has been identified as the cause.

### 11. `make version` leaves the lockfile behind, so every version bump breaks the locked install (release tooling)

The fresh worktree at `v0.6.14` would not install until `lib/idp_common_pkg/uv.lock`'s own
project version was patched to 0.6.14. `make setup` runs `uv export --locked`, which refuses a
lockfile out of date with its `pyproject.toml`. PR #1808 fixed the instance on `develop` the
same day. The `version` target in the `Makefile` still does not touch the lockfile, so the
next bump will reproduce it. Filed as
[#1818](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1818).

- **A host restart killed six benchmark lanes** at 06:03 UTC on 2026-11-07. It was a scheduled
