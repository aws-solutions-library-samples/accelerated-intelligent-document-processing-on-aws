## Verdict

✅ **Ship, with two product defects in features this release adds that a maintainer should
fix in the next patch.** The published artifact deploys in all five shipped configurations,
both template transforms deploy and process a real document, the upgrade from 0.6.12 applies
without rollback, and the 342-run release A/B shows **0 regressions and 0 improvements**, with
recall and cell accuracy identical on both sides over the same 23,370 compared cells.

**All 8 tiers ran.** Tier G, the browser review, ran for the first time in any release record:
a headless Chromium driven through Playwright replaced the debug-Chrome connection whose absence
left it NOT RUN at v0.6.11 and v0.6.12. Tier H ran three suites rather than two, because this
pass added the SDK's own integration suite, which no earlier record ran.

**The two defects that matter most are both in this release's new surface, and neither is
visible in the A/B.**

- **Re-extracting one section in the Test Studio editor rewrites the class of every section in
  the document** ([#1672](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1672)).
  v0.6.13's edit screen offers *Re-extract* on the section whose class was changed, but the API
  it calls is document-scoped, so a six-section packet ends with all six sections relabelled
  and each keeping its own fields. That is silent damage to ground truth. Finding 1.
- **Packet-granularity classification with page images fails 18–20-page documents on the
  shipped classification model** ([#1676](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1676)).
  The packet window is a page count, and a 19-page window of full-resolution scans exceeds
  Nova 2 Lite's input, so the document fails rather than being split into smaller windows: 3 of
  20 DocSplit packets in every packet+images variant. The same measurement shows packet
  granularity reaching 0.71–0.82 boundary accuracy against the shipped page default's 0.45, at
  23–65% of its classification cost per page, so this is a defect in the configuration a reader
  of the new guidance is most likely to choose. Finding 2.

**One fix this release shipped holds only partly.** The separate confidence step still runs
out of memory after a successful extraction on the large single-table benchmark document:
**2 of 190 runs, down from 15 of 190 at v0.6.12** (14 failed and one was left in `EXTRACTING`) ([#1678](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1678),
following #1488). Finding 3.

**Tier F is complete**: F1, the release A/B, plus the F2–F4 guidance refresh, **31 scored
pipeline result sets, 3,368 scored rows, $2,077.09**, plus a 140-document classification-variant
benchmark that measures this release's headline classification changes for the first time.
Its unsuccessful rows fell from 26 of 3,248 (0.80%) at v0.6.12 to **15 of 3,368 (0.45%)**,
and every one of the 15 is attributed below.

## Findings, most important first

### 1. Re-extracting one section in the Test Studio editor rewrites the class of every section (product defect, this release)

Tier G, flow 6.2, on a test set built from `lending_package.pdf` (six sections). The reviewer
changed section 3's class in the Test Studio item editor and pressed that section's
*Re-extract*. All six `sections/*/result.json` files in the set's baseline were then rewritten,
within the same second, with the new class. Each section kept its own extracted fields, so
payslip fields ended up under `Bank-checks`.

The cause is confirmed in the code. `reextractTestSetDocument` takes `testSetId`,
`objectKey`, `documentClass` and `configVersion`, with no section id, and its schema comment
says `documentClass` is "written to the document's baseline sections". The v0.6.12 editor
called it the same way. What v0.6.13 changes is that the edit screen now offers Re-extract on
the individual section whose class was changed, so a control that reads as section-scoped
drives a document-wide write. The damage is silent: the editor shows the new labels as if
intended, and the only recovery is an earlier test-set version. Filed as
[#1672](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1672).

### 2. Packet classification with page images fails long packets on the shipped model (product defect, this release)

The classification-variant benchmark ran 20 DocSplit packets through each of seven granularity,
modality and strategy combinations on Nova 2 Lite, the shipped classification model.

The three variants that send page images at packet granularity are `packet-both`,
`packet-images` and `split-then-classify-packet`. All three failed the same three packets,
`packet_0011`, `0012` and `0019`, which are 18 to 20 pages of 2550×3301 scans. Each one failed
with `ValidationException: Input is too long for requested model` on its single packet window,
then `Packet classification produced no segments`, and the document failed. Every
page-granularity variant classified those three packets, and so did `packet-text`.

The window is `packet.window_pages`, a page count with a default of 20, and nothing sizes it
against the model's input limit or retries an oversized window as smaller ones. Filed as
[#1676](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1676).
This matters more than its 15% failure rate suggests. The same benchmark shows packet
granularity is the better choice on these documents, so it is the configuration the new
guidance points readers towards.

### 3. The separate confidence step still discards some large documents after the #1488 fix (product defect, pre-existing, much reduced)

In simple mode with `assessment: separate` on `large_narrow.pdf`, the configuration and document
#1488 was measured on, the confidence step ran out of memory after extraction succeeded in
**2 of 190 runs, against 15 of 190 at v0.6.12** (14 failed, 1 left in `EXTRACTING`). Both failures ended in `AssessmentStep` with
`Runtime.OutOfMemory`: one with `textract_tables` OCR and GPT-6 Astra extraction, one with
`textract_layout` OCR and Claude Haiku 5.5 extraction. The 1,200- and 1,600-row failures v0.6.12
recorded did not recur. #1488 is closed, so the residual is filed separately as
[#1678](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1678).

### 4. The upgrade changed no extracted value consistently; three fields vary from run to run on v0.6.13 (measurement)

Across the two v0.6.12 runs and five v0.6.13 runs of `lending_package.pdf`, every difference
the diff found is inconsistent within v0.6.13 itself:

| field | v0.6.12 (2 runs) | v0.6.13 (5 runs) |
|---|---|---|
| six Payslip tax amounts, e.g. `FederalTaxes[0].Period` | negative in both | negative in 4, **positive in 1** |
| driver's licence `ENDORSEMENTS[0]` | `"NONE"` in both | `"NONE"` in 2, null in 3 |
| Bank-checks `bank_name` | null in both | `"BANK NAME"` in 3, null in 2 |

So there is no consistent version effect on this document, and the most likely reading is
model run-to-run variation. Two runs are too few to call v0.6.12 deterministic, so a variation
present in both releases cannot be ruled out. The tax-amount sign is worth naming: the v0.6.12
record attributed a sign change in these same six fields to the 0.6.11 → 0.6.12 upgrade, from
three identical runs, and at v0.6.13 that sign is not stable from run to run. There is no
ground-truth baseline for this sample in the repository, so which sign is correct was not
scored.

### 5. Text-only page classification fails the whole document on one blank page (product defect, pre-existing)

In the classification-variant benchmark, the `page-text` variant failed 2 of 20 packets with
`Processing failed for 1 out of N sections: Error classifying page K: No content available for
classification`. In each, one page with no OCR text (page 10 in one, page 2 in the other) took
the whole document down. The same result-with-error exists at v0.6.12, but this release makes
text-only modality an ordinary picklist choice in the configuration editor rather than an
edited prompt. Filed as
[#1677](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1677).

### 6. The minimal configuration the SDK and CLI generate fails their own validation (product defect, pre-existing)

Tier H's SDK suite failed one test of 13, `test_config_management.py::test_upload_config`.
`config.create(features="min")`, and therefore `idp-cli config-create --features min`, writes
`# Uses system default prompt` into every prompt field. `config.validate` then refuses the file,
because the classification and extraction `task_prompt` carry no `{DOCUMENT_TEXT}` or
`{DOCUMENT_IMAGE}` placeholder, and `config.upload` refuses it too. Reproduced at v0.6.12
with the same two errors, so it predates this release. It was not seen earlier because no
earlier record ran the SDK's integration suite. Filed as
[#1673](https://github.com/aws-solutions-library-samples/accelerated-intelligent-document-processing-on-aws/issues/1673).

### 7. The browser review's usability findings (tier G, first run)

Beyond Finding 1, the review ranked these, most important first. Each was seen on a screenshot
of this build; none is filed as an issue in this pass.

1. **Machine output can become ground truth without a confirmation.** *Use As Evaluation
   Baseline* runs immediately and overwrites an existing baseline, and a test set then shows the
   unreviewed model output as green *Ground truth*. The Reviewer's Queues list also counts
   fully labelled sets as entirely pending, while a set's own queue page reports 0 pending.
2. **The same document reports two alert counts.** It shows 37 confidence alerts on its own
   page and "7 of 142 fields flagged" in the test set, and empty fields render as a red "0.0%"

3. **A human correction looks like model output.** An edited field still reads
   "Predicted … 100%", no banner marks a saved-but-unprocessed draft, and reviewed queue rows

4. **Annotator work is harder to reach than it should be.** An item routed for one alert opens
   on all 361 fields. An Annotator's queue page defaults to a filter that shows 0 documents
   while two are assigned to them.
5. **Copy points at names that do not exist.** For example, *Start annotating* (the button
   reads *Start editing*) and *My Work › Tasks* (the navigation reads *Home › Tasks*).
6. **Read-only configuration looks editable.** The managed `default` profile's fields accept
   typing; only Save is disabled.

The full ranked list, per-flow evidence and the screenshots are kept out of the repository, as
the review's privacy rule requires.
