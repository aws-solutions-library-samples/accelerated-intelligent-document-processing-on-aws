# Release Benchmark — v0.6.11 vs published v0.6.10

**Measured:** 2026-09-27 → 2026-09-28, `us-west-2`, commercial partition
**Commit measured:** `develop` `3ca2dcc4d`
**Grid:** `corefast` — 19 config cells × 3 documents (`tiny_form`, `small_narrow`,
`longdesc_100`) × 3 repeats = **171 runs per side, 342 total**
**Extraction model:** `sonnet46`, the shared cross-version control
**Results:** [`benchmarks/results/v0.6.11/corefast/`](../../../benchmarks/results/v0.6.11/corefast/)
(new side) and `corefast-prev0610/` (published-0.6.10 side)

## Headline

**0 regressions, 0 improvements, 0 cell-level regressions, 0 cell-level improvements.**
Three inconclusive movements, all on one cell, all inside run-to-run spread.

**That is the correct result for this release rather than a weak one, and the reason is the
size of the change.** `git diff v0.6.10..3ca2dcc4d` touches exactly two files of product code
— `idp_common/extraction/agentic_idp.py` and `idp_common/utils/bedrock_utils.py` — and **both
changes are on error paths**: a retried Advanced-mode extraction now resumes the conversation
the failed attempt started instead of re-sending the prompt, and the Bedrock backoff ladder
now stops when its allowance is spent instead of clamping every remaining sleep to zero. A
document that never hits a transient Bedrock error enters neither. `corefast` runs healthy
documents, so it should not move, and it does not.

The corollary matters for anyone reading this as evidence: **this grid does not exercise what
0.6.11 fixed.** Confirming the fixes themselves requires inducing throttling or a transient
error, which no suite in `benchmarks/` does.

## Failure census

| Side | Runs | `COMPLETED` | Other |
|---|---:|---:|---:|
| published v0.6.10 | 171 | **171** | 0 |
| v0.6.11 build | 171 | **171** | 0 |

Zero non-`COMPLETED` rows on either side. All 171 rows on **both** sides carry
`cells_compared`, so the "a null column scores 1.000" blind spot
(`benchmarks/matrices/METHODOLOGY.md` §4) does not apply to this comparison — the accuracy
figures are computed against populated columns on both sides.

## The three inconclusive movements

All on `core-llm-simple-sep`, the `bedrock_llm` OCR cell, which is the noisiest cell in this
grid across every release entry in this directory.

| Metric | Movement | Why it is not a finding |
|---|---|---|
| cost | −35% (0.143 ± 0.145 n9 → 0.093 ± 0.063 n9) | the standard deviation exceeds the shift on both sides |
| scalar accuracy | +0.278 (0.667 → 0.944) | paired per-document deltas over n=9 have spread ±0.441 |
| completeness recall | +0.042 (0.958 → 1.000) | paired per-document spread ±0.127 |

Two per-document notes from the same cell, also inconclusive:
`small_narrow` recall +0.127 against a spread of 0.380, and `longdesc_100` scalar accuracy
+0.667 against a spread of 1.000.

The direction is favourable in all three, and a favourable inconclusive is still inconclusive.
Resolving them needs repeats, not interpretation.

## ⚠️ Two limits on how far this entry can be read

**Cost is not comparable at cell level on this suite.** `corefast`'s cost CV is **0.50 to
1.02 across all 19 cells** at n=9 on both sides. That is variance across the *three different
documents* inside each cell — `tiny_form` and `longdesc_100` differ by more than an order of
magnitude — not run-to-run noise. A cell's cost mean here is an average over unlike documents.
Cost claims for this release would have to come from the `cost` suite (n ≥ 5 on one 400-row
document), and **that suite did not complete** in this pass.

**Wall-time is not comparable between the sides.** They ran on **different stacks**: the
0.6.10 side on an existing v0.6.10 stack, reused rather than newly deployed to conserve IAM
role headroom, and the 0.6.11 side on the stack the release-validation upgrade tier had just
upgraded in place. Accuracy, completeness and cost *are* comparable, because the configuration
was byte-identical — generated once by `make_configs.py` and not regenerated between sides,
with `--native-upload` bypassing `idp-cli`'s migration on both.

`baseline.json` is **deliberately not promoted.** Nothing moved, so there is nothing to
promote, and promoting a grid whose cost axis is unusable at cell level would make the next
release's `--compare` diff against a baseline this entry has told the reader not to trust.

## One standing hazard re-measured: integrated confidence

`intconf` — the suite that watches the integrated-confidence row-loss hazard — ran to
completion on the v0.6.11 stack and **reads clean**:

| Arm | Runs | `completeness_recall` | `cell_accuracy` | `cells_compared` | Confidence rows unscored |
|---|---:|---|---|---:|---|
| `core-tt-simple-int` (integrated) | 4 | 1.000 | 1.000 | 200 | **0 of 100** |
| `core-tt-simple-sep` (separate) | 4 | 1.000 | 1.000 | 200 | **0 of 100** |

The measure that matters for this hazard is the last column, because the failure mode is rows
silently arriving unscored rather than an accuracy drop. Zero unscored in both arms, over four
repeats each, says the hazard is closed at 0.6.11 on `longdesc_100`. It was open from v0.6.0
and first reported fixed at v0.6.6; this is a confirmation, not a new result.

Results: [`benchmarks/results/v0.6.11/intconf/`](../../../benchmarks/results/v0.6.11/intconf/).

## ⚠️ The guidance refresh did not run — this is an incomplete tier F

The release-validation battery plans a full guidance-paper refresh alongside the A/B, at
**2,148 runs**. This pass completed **the A/B (342) plus `intconf` (8)** and was then stopped.

| Lane | Planned | Outcome |
|---|---:|---|
| `intconf` | 8 | complete, scored, reported above |
| `core` (§2 configuration matrix and real-world accuracy) | 90 | 20 launched, stopped, **not scored** |
| `scaling` (§3 completeness cliffs) | 28 | 14 launched, stopped, **not scored** |
| `cost` (§4 cost level and variance) | 25 | 14 launched, stopped, **not scored** |
| `advverify`, the 7-value `extraction_model` sweep, `astravalue`, `astracap`, `opus55value`, the `classification_model` and `confidence_model` sweeps | 1,997 | not started |

The three partial lanes are **deliberately left unscored**. `aggregate.py` will score a
partial run and write a summary that looks complete, so leaving them unscored is the only
signal a later reader gets that they are partial.

**Consequence, stated by name: every paper under `docs/benchmarking/` still carries data from
an earlier release.** `config-guidance.md`, `index.md`, `classification-confidence.md`,
`prompt-caching.md` and `feature-multi-instance.md` were not regenerated, and
`config-guidance.md`'s header still names an earlier release. In particular there is **no
measured model-selection verdict for 0.6.11** — the premium and lightweight model sweeps did
not run, so the guide cannot say on this release which cheap model is at ceiling for a given
document profile or whether a premium model earns its price.

One part of the refresh would have been empty regardless: **0.6.11 changed no configuration
knob.** The §7 one-knob A/Bs had nothing to re-measure, and running them would have measured
nothing about this release.

## Reproduce

```bash
cd benchmarks
python3 harness/make_configs.py --suite corefast     # once; do not regenerate between sides
python3 harness/run_matrix.py --stack <0.6.10 stack> --suite corefast --native-upload --max-inflight 4
python3 harness/run_matrix.py --stack <0.6.11 stack> --suite corefast --native-upload --max-inflight 4
python3 harness/aggregate.py --run results/run-<prev> --out results/v0.6.11/corefast-prev0610
python3 harness/aggregate.py --run results/run-<new>  --out results/v0.6.11/corefast
python3 harness/aggregate.py --compare  results/v0.6.11/corefast/summary.json \
                             --baseline results/v0.6.11/corefast-prev0610/summary.json
```

Note that `--compare` pairs with `--baseline`; passing `--compare` alongside `--run` scores the
run and prints no comparison.
