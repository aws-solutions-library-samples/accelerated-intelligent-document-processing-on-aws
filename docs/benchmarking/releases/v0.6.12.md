# v0.6.12 vs v0.6.11 (published) — release benchmark audit

> ⚠️ **This entry carries the release A/B only. Tier F is incomplete for v0.6.12.** The
> guidance-paper refresh — the configuration matrix, the scaling study, the cost-variance
> runs, the standing-hazard suites and the model sweeps — **was not run**, so every other file
> under `docs/benchmarking/` still cites v0.6.11 measurements and no number in them describes
> this release. What that leaves unmeasured is listed at the bottom, and the release
> validation record repeats it as a finding. An entry with no refresh behind it is reported as
> an entry with no refresh behind it.

**Verdict: flat, with one arm inconclusive.** The release A/B over 342 runs reports
**0 regressions and 0 improvements**. Grid cost moved **+0.1%** and wall **−0.5%**, both
well inside run-to-run spread, and **18 of 19 cells are identical to three decimal places on
both completeness recall and cell accuracy**. Neither side had a single failed run.

The one cell that moved is `core-llm-simple-sep`, the `bedrock_llm` OCR arm: recall
1.000 → 0.958 and cell accuracy 1.000 → 0.993. Both are **inconclusive at n=9** — the paired
per-document deltas have a spread of ±0.127 on recall and ±0.417 on accuracy, so the
observed change is smaller than the arm's own variation. That arm is independently known to
perturb fixed-width identifiers, which is consistent with it being the noisiest of the
nineteen rather than with a change in this release.

**Flat is a defensible result for this release, but less obviously so than for 0.6.11.**
0.6.11's product changes were error-path fixes that only engage after a transient Bedrock
error, which `corefast` documents never hit — so flatness there was close to a prediction.
v0.6.12 does change code on the healthy path: `extraction/service.py` grew by 367 lines, the
row-shortfall check was re-derived, and truncation handling was added. The A/B says those
changes did not move accuracy or cost on this corpus. It does **not** say they moved nothing
anywhere: the corpus is three small documents (`tiny_form`, `small_narrow`, `longdesc_100`,
the largest being 100 rows over 4 pages), and the new row-shortfall and truncation signals are
by construction about **large** documents. The suite that would exercise them is the scaling
study, which was not run.

⚠️ **One change this release makes to extracted values is not visible in this A/B at all.**
The release validation record's Finding 1 reports that six Payslip statutory-tax amounts
change sign across the 0.6.11 → 0.6.12 upgrade, reproducibly over three runs. That document
(`samples/lending_package.pdf`) is not in this corpus, and this corpus has no payslip class,
so no cell here could have detected it. **A flat A/B is not evidence that extracted values are
unchanged** — it is evidence about the cells and documents in the grid.

The control model is `sonnet46` deliberately: it is the cross-version control, callable by
every release being compared. The **shipped default** is Sonnet 5, so no figure here is a
statement about the model a new deployment runs by default.

⚠️ **Configs are built from the current repository's defaults, so a fix that ships as default
configuration is present on both sides and cancels out.** `config_library/` changed between
these two tags only in `pricing.yaml`, `model_config_limits.yaml` and
`extensions-marketplace.yaml` — nothing in the `corefast` presets — so for this pair the two
sides differ in code alone, which is the cleanest form this comparison takes.

it was not run.

## Cost variance

Per-cell cost CV at n=9 runs 0.47–0.62 on the agentic cells on both sides, so cost movement
was read against each cell's own spread rather than against a flat percentage. The widest are
`split-disabled` (0.616), `core-tt-simple-off` (0.613), `split-llm` (0.609) and `enforce-off`
(0.599) on the new side. One per-document cost row, `core-tt-adv-sep|tiny_form.pdf` at +20%,
sits inside a 64% spread and is reported inconclusive.

With CVs that wide, **no cost delta below roughly 50% on a single cell is readable at n=9**.
The grid-total +0.1% is meaningful only because it pools 171 runs.

## Processing issues

Both sides recorded 10, and both carry `assessment_geometry_incomplete` on **9 of 9** runs of
`core-llm-simple-sep` (severity `info`) — standing behaviour of that arm, unchanged.

The remaining issue is one `assessment_truncated` warning, and it **moved cell**: it sat on
`core-tt-simple-sep` at 0.6.11 and on `enforce-escalate` at 0.6.12. Same severity, same code,
same count, different cell — the signature of nondeterminism rather than of a change.

## What tier F did not measure for v0.6.12

F1 above is the whole of this release's benchmark coverage. Unmeasured on this build:

- **the configuration matrix** (`coresynth` / `core`), so there is no cross-config grid, no
  labelled-corpus accuracy and no real-world accuracy figure for 0.6.12;
- **the scaling study**, so where each mode's completeness cliff sits on this release is
  unknown — and this release changed both of the signals that study reads
  (`extraction_output_truncated` is now reported rather than silently recorded, and
  `extraction_partial_row_shortfall` replaces a multiplicative tolerance with a 29-row
  additive one);
- **cost level and variance at the shipped default model**, Sonnet 5, which no figure in this
  entry describes;
- **the two standing list-loss hazards** (`intconf`, `advverify`), so this entry cannot say
  whether either is still open;
- **the model sweeps** — so every selectable model's row in the guide is a v0.6.11
  measurement, and ⚠️ **Claude Sonnet 5.5, which this release adds to every model-taking
  service, has no measured accuracy, completeness or cost figure of any kind.** Quote none.
  Its own changelog entry says the same.

Note for whoever runs the refresh: the `extraction_model` sweep axis in
`benchmarks/matrices/config_matrix.yaml` currently holds **eight** values (`nova_lite`,
`nova_pro`, `sonnet5`, `sonnet5_1m`, `opus5`, `opus55`, `astra`, `haiku55`). Read the axis
rather than any copy of it — a stale copy costs a model silently, since the sweep simply runs
one short.

## Reproduce

```bash
python benchmarks/harness/gen_corpus.py
python benchmarks/harness/make_configs.py --suite corefast
# PREV side FIRST, on the 0.6.11 stack, before update-stack
python benchmarks/harness/run_matrix.py --stack <stack> --suite corefast \
    --repeats 3 --native-upload --max-inflight 4
python benchmarks/harness/aggregate.py --run <run dir> --out benchmarks/results/v0.6.11-rvprev/corefast
# ... update-stack to 0.6.12, then repeat on the same stack ...
python benchmarks/harness/aggregate.py --run <run dir> --out benchmarks/results/v0.6.12/corefast
# NOTE the argument direction: --compare is the CURRENT side, --baseline the reference.
python benchmarks/harness/aggregate.py \
    --compare benchmarks/results/v0.6.12/corefast/summary.json \
    --baseline benchmarks/results/v0.6.11-rvprev/corefast/summary.json
```
