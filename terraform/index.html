Terraform Deployment (Experimental)

Section titled “Terraform Deployment (Experimental)”

The accelerator can be deployed with Terraform or OpenTofu as well as with CloudFormation. This page explains where the Terraform module comes from, how to deploy, change, upgrade and delete it, and how a Terraform deployment differs from a CloudFormation one. Terraform support is experimental: the module has been deployed end to end and has passed the integration suite, but it has had far less use than the CloudFormation templates, and some features are not yet available for it. Those are listed under Differences from CloudFormation and current limitations.

If you deploy the accelerator today with the separate awslabs/genai-idp-terraform repository, read Migrating from genai-idp-terraform as well. That repository is a different implementation, so its state cannot simply be moved onto this module; a new deployment of the module adopts its buckets, tables, KMS key and user pool instead, with idp-cli terraform migrate-from-genai-idp-terraform.

Demo video (about 3.5 minutes): deploying from the published module and from a local clone, updating, and planning a migration from genai-idp-terraform, all with idp-cli.

What it is

Section titled “What it is”

The Terraform module is generated from the accelerator’s CloudFormation templates, the same templates the Deployment Guide deploys. A translator in this repository reads the published main template and its nested templates and writes a Terraform module tree: a root module, plus one child module for each nested stack. A release publish (publish.py) generates it from the templates it has just published and uploads it beside them, unless run with --no-terraform, so a module and the CloudFormation templates of the same version deploy the same resources with the same settings. idp-cli publish does the same when given --terraform.

The generated module uses three providers:

  • hashicorp/aws, version 6, for most resources;
  • hashicorp/awscc, version 1, which manages resources through the AWS Cloud Control API, for the resource types that have no hashicorp/aws mapping in the translator;
  • hashicorp/time, for the short waits that let IAM changes propagate before they are used.

The exact version constraints are in the module’s versions.tf. The module requires Terraform 1.7 or later, or OpenTofu 1.7 or later.

CloudFormation custom resources, which run a Lambda function during a stack operation, are reproduced by a small bridge Lambda function that the module creates. It calls each handler the way CloudFormation would and passes the handler’s answer back to Terraform. You do not interact with it, but you will see it among the deployment’s resources.

Prerequisites

Section titled “Prerequisites”

You need the following before you deploy:

  • An AWS account and credentials with administrator-level permissions, as for a CloudFormation deployment (see the administrator access requirements). The awscc provider works through the Cloud Control API, so the credentials also need its actions (cloudformation:CreateResource, GetResource, UpdateResource, DeleteResource, ListResources and GetResourceRequestStatus) in addition to the permissions of the underlying services. The module also creates one CloudFormation stack (the label stack described below), which needs cloudformation:CreateStack and its related actions unless you turn the label off. When the deployment uses a customer-managed KMS key, the credentials also need kms:Decrypt and kms:GenerateDataKey on that key: the label stack’s template is stored in the custom-resource bridge’s bucket, which is encrypted with the key, and CloudFormation reads it with the caller’s credentials. A deploying role that is scoped rather than administrator-level is described under Deploying with a scoped role.
  • Terraform 1.7 or later, or OpenTofu 1.7 or later, on your path.
  • Access to the Amazon Bedrock models the solution uses, in the Region you deploy to. The models the shipped configuration defaults call are listed in the README, under the request-access note; the authoritative set is whatever lib/idp_common_pkg/idp_common/config/system_defaults/ names, plus any model your own configuration names.
  • Read access to the S3 bucket the module was published to. The module refers to the Lambda code and other artifacts that the CloudFormation publish uploaded beside it, exactly as the CloudFormation template does.
  • For the idp-cli route, idp-cli installed from a checkout of this repository, as described in IDP CLI.

Deploying with a scoped role

Section titled “Deploying with a scoped role”

A Terraform deployment has no CloudFormation service role: every call is made with the credentials Terraform runs with, so those credentials need everything a CloudFormation service role for the solution needs. A role modelled on the example in iam-roles/cloudformation-management/ needs the following:

  • The service-wide grants that role holds for the services the solution uses. The aws provider reads back more of each resource than CloudFormation does (every configuration of a bucket, for example), and a grant narrowed to the actions CloudFormation calls refuses those reads.
  • The Cloud Control actions listed above, which are in the cloudformation: namespace and so are covered by that role’s cloudformation:*.
  • IAM writes on the roles the module creates. Every role is named after the deployment, as CloudFormation names an unnamed role: <stack>-<LogicalId>-<hash>, cut to IAM’s 64 characters, and <stack>-CfnBridge-<hash> for the custom-resource bridge’s role. A role CloudFormation retains also ends in its creation time, so deploying the same stack name again after a delete does not collide with the role the delete kept. A grant of iam:CreateRole, iam:PassRole and the role-policy actions on role/<stack prefix>* therefore covers them, provided the stack name starts with that prefix.
  • If the role allows creating roles only with a given permissions boundary (the example role’s iam:PermissionsBoundary condition), pass that boundary as PermissionsBoundaryArn. The module applies it to every role it creates, the bridge’s role included, the way the template’s HasPermissionsBoundary condition does.

A complete deployment with such a role has not been run; the list above follows from what the module creates, not from a measured run.

Plan where Terraform state will live before the first apply. The state holds every setting you pass, including sensitive ones, and some of the module’s outputs are credentials (the MCP client secrets, for example). A remote backend with encryption and locking, such as the s3 backend, is the usual choice for a deployment you intend to keep.

Getting the module

Section titled “Getting the module”

Each release that includes the Terraform module publishes it as a zip archive in the same S3 bucket and under the same prefix as that release’s CloudFormation templates. For a release version <version>, the files are:

ObjectContent
<prefix>/<version>/terraform/idp-terraform-<version>.zipthe module tree
<prefix>/<version>/terraform/idp-terraform-<version>.zip.sha256the SHA-256 checksum of the archive
<prefix>/terraform/idp-terraform-versions.jsonthe versions index: every published version, its object key, checksum and date
<prefix>/terraform/idp-terraform-latest.json{"version", "moduleUrl", "sha256"} for the most recently published module

The headless and GovCloud template variants, when a publish produces them, are published as modules of their own beside the standard one, with the variant in each name: <prefix>/<version>/terraform/idp-terraform-<variant>-<version>.zip, its .zip.sha256, <prefix>/terraform/idp-terraform-<variant>-versions.json and <prefix>/terraform/idp-terraform-<variant>-latest.json, where <variant> is headless or govcloud. The headless module has no web UI, Cognito, agents or knowledge base, and so no admin_email variable; the GovCloud module keeps the UI, has no CloudFront resources, and serves the UI through API Gateway.

The module source URL is the HTTPS S3 URL of the zip, for example https://s3.us-west-2.amazonaws.com/<bucket>/<prefix>/<version>/terraform/idp-terraform-<version>.zip. Terraform accepts an HTTPS URL ending in .zip as a module source, downloads it at terraform init and extracts it. The public release is published to the same bucket and prefix as the Launch Stack templates of the Deployment Guide, so for a release <version> (for example 0.6.15) the module source in each Region is:

The newest module’s URL in a Region is the moduleUrl of the pointer beside it, .../artifacts/genai-idp/terraform/idp-terraform-latest.json in the same bucket. If that pointer is not present in your Region’s bucket, no Terraform module has been published there yet; you can build and publish one yourself with idp-cli publish --terraform (see IDP CLI).

You do not need a checkout of this repository to deploy a published module from your own root configuration. The module declares no provider blocks of its own, so it uses the aws and awscc providers your root configuration sets up (and the time provider, which needs no settings), as the example under Your own root configuration shows.

The published zip is the only form the module is distributed in. It has no public Terraform Registry entry, and it cannot be used as a git:: source, because the module is generated from the templates when a release is published and is not committed to the repository. To get version constraints in your own configuration, upload the zip to a private registry; see Publishing the module to a private registry.

A plain HTTPS module source is fetched without AWS credentials, so it works only for an object that is publicly readable. For a module you published to a private bucket, prefix the URL with s3:: and use the dash form of the S3 host (s3::https://s3-<region>.amazonaws.com/<bucket>/<key>), which makes Terraform fetch it with your AWS credentials. Terraform’s S3 getter reads the dotted form (s3.<region>.amazonaws.com) as a bucket named s3; idp-cli deploy --terraform writes the dash form for you.

The versions index

Section titled “The versions index”

idp-terraform-versions.json lists every module version published to that bucket and prefix, so you can find an older release without knowing its URL. The latest pointer names only the most recent publish and is overwritten by the next one; the index keeps every entry. It looks like this:

FieldMeaning
schemaVersion1. A reader refuses any other value instead of guessing at it
versionsone entry per version, ordered by the numeric X.Y.Z and then by the full version string, so 0.6.9 comes before 0.6.10
versionthe version the module was published as
moduleKeythe object key of that version’s zip, in the same bucket as the index. The module URL is https://s3.<region>.amazonaws.com/<bucket>/<moduleKey>
sha256the SHA-256 of the zip, the same value as its .zip.sha256 file
releaseDatethe UTC date the entry was written: the release’s publish date for a release version, the latest republish for a pre-release, and the last-modified date of the .zip.sha256 file for an entry the first index was seeded with

Entries record an object key rather than a full URL, so an index copied to a replicated bucket points at that bucket’s own copy of each zip. The index does not record a minimum idp-cli or SDK version. The module has no tested minimum, and a deploy --terraform from a newer CLI is how older modules are deployed today.

A release version (X.Y.Z, such as 0.6.15) is immutable. If you publish it a second time with a module whose checksum differs from the one in the index, the module publish is refused before any module object is written, so the zip, its checksum file, the index and the pointer stay as they were. The zip itself is also written conditionally (If-None-Match: *): if its key already holds different bytes, the publish is refused there, even when the index has no entry for the version (for example, a release published by an SDK that kept no index, or a publish that stopped after writing the zip). Republishing identical bytes succeeds. The module is published after the CloudFormation templates, so a refused republish has already replaced that version’s templates under <prefix>/<version>/. Re-cut the release as a new version rather than republishing it. A pre-release version (anything else, such as 0.6.16.dev1) can be republished with new contents, and its entry is replaced. Development builds work this way, because the source tree’s VERSION stays the same across many builds.

Publishing updates the index with an S3 conditional write. The write only succeeds if the object is still the one the publish read (If-Match on its ETag), or, for a new index, if no object exists yet (If-None-Match: *). If another publish changes the index in between, the write fails, and the publish reads the index again and retries, so two concurrent publishes cannot drop each other’s entries. A publish that keeps losing that race gives up after a few attempts and reports it. Conditional writes need a botocore whose S3 PutObject has both If-Match and If-None-Match. botocore 1.35.99 and later have both; 1.35.5 has only If-None-Match. With an older one the module publish is refused before it writes anything. The index is written before the latest pointer, so the pointer never names a version the index lacks.

The first publish to a bucket that has no index yet creates one. That first index also lists the versions already in the bucket, found from their .zip.sha256 files under <prefix>/<version>/terraform/, with the date each file was last modified.

The CLI looks the version up in the Region’s versions index (the headless or GovCloud index with --headless or --govcloud), downloads the zip at that entry’s key, and refuses to continue if the zip’s SHA-256 differs from the index entry. Tagging the deployment

Section titled “Tagging the deployment”

The module has a tags variable, a map(string) that is empty by default. It plays the role of CloudFormation stack tags. Set it on the module and give the same map to the aws provider’s default_tags:

Both halves are needed, because default_tags reaches only the aws resources. The hashicorp/awscc provider has no default_tags, so a tag set there does not reach any awscc resource: the alarms, queues, SSM parameters, state machines, the REST API and its stage, the KMS key and the others the module creates through Cloud Control. The module merges tags into each awscc resource that accepts tags instead, in that resource’s own tag shape. Which resources those are is read from the awscc provider schema when the module is generated, so a resource type gains the merge when the provider adds tags to it.

A tag key a template sets on a resource itself, such as Name on the Lambda security group, keeps the template’s value, as it does with default_tags. Keys starting with aws: are refused at plan, because AWS reserves them. OpenSearch Serverless collections accept tags only when they are created, so a collection gets the tags the module has when it is created, and a later change to tags does not change them, rather than replacing the collection and its vector index. With tags left empty, the module plans exactly what it did before it had the variable.

Two limits follow from how the tags are applied. default_tags also tags the module’s S3 objects (the label stack’s template and the resource directory), and S3 allows an object at most 10 tags, so keep the map to 10 tags; idp-cli refuses more. And emptying tags after it held some is not a reliable way to remove them from the awscc resources: a resource whose template sets no tags is then given null, which the awscc provider may treat as “keep what is there”. Removing a tag from the map does remove it, because the attribute then carries the remaining tags.

As with a CloudFormation deployment, the first apply sends a temporary password to admin_email, and a second email asks you to confirm the alerts subscription. Confirm it, or alarm notifications reach nobody (see Who receives the alerts).

A first apply of the full stack takes roughly half an hour. Terraform does not roll back a failed apply the way CloudFormation rolls back a failed stack: what was created stays in state. Fix the cause and run terraform apply again, or run terraform destroy.

Using the module beside your own resources

Section titled “Using the module beside your own resources”

Three things behave differently from an ordinary module when the module "idp" block shares a root configuration with your own resources.

Inputs that a template condition reads must be known at plan time. The templates’ conditions become count and for_each expressions, and Terraform must know those when it plans. An input such as reporting_bucket_name decides whether the module creates a bucket of its own, so setting it to an attribute that is not known until apply (reporting_bucket_name = aws_s3_bucket.analytics.id, for a bucket created in the same apply) leaves the condition unknown, and terraform plan fails with Invalid count argument or Invalid for_each argument.

The same holds for an input that only a nested module’s conditions read, which is easier to miss because no condition in the root module names it. log_level and waf_allowed_ipv4_ranges are in that position: they decide inside the API resolver stack whether the API’s access logs and its web ACL exist, so each must be known at plan time. The headless module has no API resolver stack, so neither applies there.

vpc_id can come from a VPC created in the same apply. The pattern stack asks only whether it is empty, and the template’s DeployInVPCRequiresParams rule (below) refuses an empty vpc_id whenever deploy_in_vpc = "true", so the module answers that question without the value: with deploy_in_vpc = "true" the pattern stack creates its VPC-only resources, and with "false" it creates none and is given an empty vpc_id whatever you set.

The other inputs that only nested conditions read, pattern2_custom_classification_model_arn, pattern2_custom_extraction_model_arn, enable_ecr_image_scanning and s3_vpc_endpoint_dns_name_override, decide only attribute values (a list in a policy or a schema, an image-scanning setting, an environment variable), not whether a resource exists. lambda_subnet_ids and lambda_security_group_id decide nothing and can come from resources created in the same apply. Create anything whose identifier feeds an input listed here in an earlier apply, or, for a value you choose yourself such as a bucket name, pass it to the module as a literal.

The template’s Rules are refused at plan. These are the cross-parameter checks CloudFormation applies when a stack is submitted, such as “VpcId is required when DeployInVPC=true” and “the S3 VPC endpoint’s id and DNS name are supplied together”. Each rule becomes a terraform_data resource in the root module’s rules.tf, named cfn_rule_<rule>, with one precondition per assertion, so a combination CloudFormation refuses fails terraform plan with that assertion’s description as the error, before anything is created:

Preconditions are used rather than variable validations because a validation that reads a second variable needs Terraform 1.9, and the module supports 1.7. A precondition whose inputs are not known at plan time, such as a vpc_id taken from a VPC created in the same apply, is checked during the apply instead. It still refuses an empty value then, but by that point resources that do not wait on the check may already have been created, so a value that could turn out empty at apply is better checked in your own configuration.

Do not put depends_on on the module "idp" block. The module reads the Region, partition and account from data sources, and several conditions compare them (whether the partition is GovCloud, for example), so those conditions also decide count. Terraform defers every data source inside a module that has depends_on until apply whenever what it depends on has changes to make, which on a first apply is always, so those conditions are unknown at plan time and the plan fails the same way. Pass the outputs or attributes of the resources the module needs as its inputs instead, within the rule above; Terraform orders the work by those references. The module’s provider constraints apply to the whole root configuration. Terraform installs one version of each provider for a root configuration, chosen to satisfy every constraint in it, so the aws and awscc constraints in the module’s versions.tf bind every resource in your root, not only the module’s. A root that pins aws to a major version outside the module’s range cannot run terraform init with the module. Deploy the module from a root configuration of its own in that case, and read its outputs from your other configurations with a terraform_remote_state data source.

With idp-cli deploy --terraform

Section titled “With idp-cli deploy --terraform”

idp-cli can write and apply a root configuration for you:

To deploy from your own checkout instead of a published release, add --from-code .: it builds and publishes the templates and the Terraform module to your artifact bucket first, exactly as idp-cli publish --source-dir . --terraform does, then deploys that module.

The command writes a directory, ./idp-terraform/<stack-name> by default, containing a main.tf with the aws and awscc providers configured for the Region and a module "idp" block, plus a terraform.tfvars holding your settings and an idp-cli-parameters.json recording them by CloudFormation parameter name. Both files can hold sensitive values and are created readable by their owner only. It then runs, in that directory:

  1. terraform init, with -upgrade only when the module source differs from the one the directory was last initialised with. Otherwise the providers stay at the versions recorded in .terraform.lock.hcl instead of moving to the newest release the module allows on every deploy.
  2. terraform plan -out=<file>, then terraform show -json on that plan.
  3. A check of the plan. If any change deletes or replaces a resource that holds data or that CloudFormation would have retained, the command stops, lists those addresses, and applies nothing. The module’s idp-terraform.json lists both, for the installed module and the new one: statefulAddresses is every bucket, table, user pool, KMS key, knowledge base and data source, OpenSearch Serverless collection, secret and vector-store resource, and retainedAddresses every resource with DeletionPolicy: Retain. Replacing one of these loses its data. The check is stricter than CloudFormation in one case: a parameter change that turns off a feature deletes that feature’s tables or buckets under CloudFormation, and is refused here until you confirm it. --terraform-allow-replace-stateful applies such a plan anyway.
  4. terraform apply of exactly that saved plan. The plan file is removed afterwards, because it holds your settings too.

Keeping the state in S3

Section titled “Keeping the state in S3”

idp-cli deploy --terraform --terraform-state s3 keeps the state in S3 instead of in the directory, so the deployment survives the loss of the directory and a second operator, whose credentials are in the same account, can deploy from another directory against the same state:

Before it writes anything into the directory, idp-cli makes sure two resources exist in the deployment’s Region and in the account of the credentials running it, creating them when they are missing:

  • The state bucket, idp-tf-<stack-name>-<account-id>-<region> (the stack name lowercased). A new bucket gets a public access block with all four settings on, versioning, SSE-S3 default encryption, and a bucket policy that denies every request not made over TLS, because the state holds the deployment’s settings and some of its outputs (the MCP client secrets, for example) in clear. The state object is <stack-name>/terraform.tfstate.
  • The lock table, a DynamoDB table named idp-tf-lock-<stack-name> with the LockID key the S3 backend uses, billed on demand.

idp-cli then writes backend.tf in the directory with bucket, key, region, encrypt = true and dynamodb_table, marked as written by idp-cli, and rewrites it on every deploy with --terraform-state s3.

The lock is the DynamoDB table rather than the S3 backend’s own use_lockfile, because use_lockfile needs Terraform or OpenTofu 1.10 and the module supports 1.7 and later; two operators whose binaries locked in different ways would not exclude each other, so every deploy uses the table. Terraform 1.11 and later print a deprecation warning for dynamodb_table; the lock still works.

A later deploy reuses both. The bucket must belong to your account: a bucket of that name in another account is refused and nothing is written to it. A reused bucket is never recreated or emptied. Of its four protective settings, a deploy applies only one the bucket lacks entirely, which finishes a creation an earlier deploy was interrupted in. A setting someone changed is left as it is, with a warning, for versioning (suspended), the public access block (any of its four settings off) and the bucket policy (one without a deny on non-TLS requests). Every call on the bucket names your account as its expected owner.

Two directory changes are refused rather than carried out. A directory that already holds a local terraform.tfstate cannot be switched to s3, because moving an existing state into S3 (terraform init -migrate-state) is not supported yet; it is planned as a follow-up. And a directory whose backend.tf idp-cli wrote must keep being deployed with --terraform-state s3. A deploy from a new directory with --terraform-state s3 and the same stack name uses the same bucket and state.

Parameters

Section titled “Parameters”

Each CloudFormation parameter of the main template is a variable of the root module, named in snake_case: AdminEmail is admin_email, MaxConcurrentWorkflows is max_concurrent_workflows, PermissionsBoundaryArn is permissions_boundary_arn. A run of capitals is one word, so WAFAllowedIPv4Ranges is waf_allowed_ipv4_ranges, ExternalIdPOIDCClientId is external_idp_oidc_client_id and CloudFrontPriceClass is cloudfront_price_class. The module’s variables.tf, and the parameters map in its idp-terraform.json, give every exact name. A CommaDelimitedList parameter is a list(string) variable, so LambdaSubnetIds is written lambda_subnet_ids = ["subnet-a", "subnet-b"]. A NoEcho parameter is a sensitive variable.

Each variable carries the CloudFormation parameter’s description and default, and its constraints as Terraform validation blocks: allowed values, allowed pattern, minimum and maximum value, with the parameter’s constraint description in the error message. A value CloudFormation would refuse is therefore refused at terraform plan, before anything is changed.

stack_name is the name of the deployment. It plays the role of the CloudFormation stack name: it is the value of AWS::StackName everywhere in the templates, the prefix of generated resource names, and the name of the label stack. It must start with a letter, contain only letters, digits and hyphens, and be at most 25 characters, the same limit the CloudFormation template enforces.

To change a setting, change the variable in your configuration (or in terraform.tfvars in the idp-cli directory), then run terraform plan and terraform apply. Do not change settings on the label stack: it does not deploy anything, and its parameters refuse any other value, as the next section explains.

The read-only label stack

Section titled “The read-only label stack”

Every Terraform deployment creates one small CloudFormation stack, named exactly like the deployment (stack_name). It is a label, not a deployment: it manages no resources, and Terraform is the only thing that writes to it. It exists for two reasons. It lets you find and cross-reference Terraform deployments of the accelerator, and their versions, from CloudFormation alongside CloudFormation deployments. And it is how idp-cli and the SDK find a Terraform deployment’s resources by --stack-name.

The label stack has:

  • A description made of the main template’s description, which carries the accelerator’s tracking marker and version (for example AWS GenAI IDP Accelerator (uksb-r8evguc4p9) (SO9027) (v<version>)), then (Terraform), then a notice that it is a read-only label updated only by Terraform. A search on the tracking marker finds both kinds of deployment; (Terraform) tells them apart.
  • The tags ManagedBy=Terraform, ReadOnly=true, and a Purpose tag saying to update it only with terraform apply.
  • One resource, an AWS::CloudFormation::WaitConditionHandle, which creates nothing and costs nothing. Its metadata records the version and that the deployment is managed by Terraform.
  • The deployment’s settings as parameters, under their CloudFormation names (AdminEmail, LogLevel, and so on), with the values Terraform applied, so the console’s Parameters tab shows them as it would for a CloudFormation stack. Each description starts with READ-ONLY, and the console groups them under a read-only heading. They are read-only by construction, not only by convention: each parameter’s allowed values are exactly its current value, so a CloudFormation update that tries another value is refused, with a message saying to change it in Terraform. NoEcho parameters are left out.
  • The main template’s outputs, plus TerraformResourceDirectory, which names an S3 object listing every resource of the deployment in CloudFormation’s shape (logical ID, type and physical ID, per module), and TerraformResourceDirectoryVersion, a hash of that object’s content.

The variable enable_cfn_stack_label controls the label. It defaults to true. Set it to false to skip the stack, for example where the deploying role may not use CloudFormation. Without the label, idp-cli and the SDK cannot address the deployment, and every operation on this page that takes --stack-name stops working for it.

What still uses CloudFormation

Section titled “What still uses CloudFormation”

A Terraform deployment does not deploy through CloudFormation, but it is not free of CloudFormation’s API either. Three things use it:

  • The label stack, the module’s one aws_cloudformation_stack resource, described in the previous section. It is created, updated and deleted with the credentials Terraform runs with, using the cloudformation: stack actions. Setting enable_cfn_stack_label = false removes it, and with it the ability of idp-cli and the SDK to address the deployment by --stack-name. Running idp-cli against a deployment that has the label also needs read access to it (cloudformation:DescribeStacks).
  • The Cloud Control API, through which the awscc provider manages the resources that have no hashicorp/aws mapping in the translator (queues, state machines, alarms, the KMS key and others; the module’s .tf files show which). Cloud Control creates no stacks, but its actions are in the cloudformation: IAM namespace (cloudformation:CreateResource, GetResource, UpdateResource, DeleteResource, ListResources and GetResourceRequestStatus), so they are needed for every deployment and cannot be turned off.
  • Feature-platform extensions (see Feature Platform), which install as CloudFormation stacks of their own. The extension templates in this repository read the main deployment’s values through CloudFormation exports (Fn::ImportValue of <stack name>-...), and the Terraform module creates no CloudFormation exports, so those imports have nothing to resolve to. Installing an extension on a Terraform deployment has not been tested. EnableFeaturePlatform set to false removes the platform.

The CloudFormation custom resources in the templates do not need CloudFormation: the module’s bridge function calls their handlers itself.

So the module cannot be deployed where every cloudformation: action is denied, because that denies Cloud Control as well. Where only the stack actions are denied and the Cloud Control actions are allowed, the module needs enable_cfn_stack_label = false, which leaves the deployment without idp-cli and SDK access by --stack-name and without extensions. Neither case has been tried.

Deleting

Section titled “Deleting”

To delete a deployment made with idp-cli, run:

Add --terraform-dir DIR if you deployed with a directory other than the default, and --force to skip the confirmation. A deployment applied with --terraform-assume-role-arn keeps that role in main.tf, so the delete uses it too; pass --terraform-assume-role-arn to the delete to set or change it, which rewrites the two provider blocks before init. The command empties the deployment’s buckets the way the CloudFormation delete path does, except the module’s custom-resource bridge buckets (cfn_bridge, created with force_destroy): those hold the physical ID of each custom resource, which the resource’s delete needs, and terraform destroy empties them itself after the custom resources are deleted. It then removes from Terraform state every resource whose CloudFormation DeletionPolicy keeps it (Retain or RetainExceptOnCreate), and then runs terraform destroy. Removing a resource from state means Terraform forgets it without deleting it, so the resources CloudFormation would retain are retained here too: the logging bucket, the data buckets, the KMS key that encrypts them, and the other resources the templates mark that way. The command reports which retained resources were left, as the CloudFormation path does, naming the Region-wide API Gateway account setting and the KMS key for what they are rather than by their identifiers. For the key it also prints the aws kms schedule-key-deletion command to run once none of the retained data is needed; the key costs about $1 a month until then. See The retained KMS key.

It also lists the log groups AWS services created on the deployment’s behalf, which neither terraform destroy nor a CloudFormation stack delete removes, because neither created them: the /aws/lambda/<function> group of each function that logs to Lambda’s default group (the custom-resource handlers), the /aws/codebuild/<project> group of a build project that logs to CodeBuild’s default, and the Glue crawler’s log streams. Each group exists only if its resource ran, and the service creates it with no retention. The crawler writes to /aws-glue/crawlers, which every crawler in the Region shares, so delete only the streams named after this deployment’s crawler, not the group.

Upgrading

Section titled “Upgrading”

To upgrade, point the module at the new release’s URL and apply:

  1. Change source in the module "idp" block to the new version’s zip URL.
  2. Run terraform init, which downloads the new module. Terraform refuses to plan with a changed module source until you do.
  3. Run terraform plan and read it. Replacements of stateful resources (buckets, tables, the user pool, keys, the knowledge base) deserve a close look before you apply; jq -r '.statefulAddresses[]' .terraform/modules/idp/idp-terraform.json lists them.
  4. Run terraform apply.

The label stack’s description and metadata move to the new version in the same apply. With idp-cli, run idp-cli deploy --terraform again with the same --stack-name and --terraform-dir, and the new --terraform-module-url (or none, for the latest). You do not need to repeat the --parameters you passed before: as a CloudFormation update does, the upgrade keeps the value the deployment has for every parameter you do not pass, whether you set it or it took the default, and applies the parameters you pass now over them. A parameter that is new in the release takes its default.

The values come from the deployment’s label stack, whose parameters Terraform writes at every apply with each parameter’s value in effect. The label stack lives with the deployment rather than in your directory, so a second operator who deploys from another directory against the same state backend gets the deployment’s current settings rather than the module’s defaults. It is also what lets a deployment made with an earlier idp-cli, which recorded only the values that were passed, keep its defaulted values on its first upgrade: in particular, release 0.6.15 changed the default of EnableMCP from true to false, and a deployment that never passed it keeps EnableMCP=true. The label stack leaves NoEcho parameters out, so their values come only from the directory’s idp-cli-parameters.json; a second operator must pass any that the deployment set. If the label stack and the directory disagree (another operator changed a setting since), the label stack’s value is used, because it is the value last applied.

After each apply, idp-cli-parameters.json records every parameter’s value in effect, defaulted ones included, so a later upgrade from that directory keeps them even where the label stack cannot be read. Before the plan, the output lists the values the upgrade kept that differ from the new module’s defaults, and the new parameters that took their defaults. A parameter no longer in the new module is dropped with a message.

⚠️ Without a label stack (enable_cfn_stack_label = false), a deployment whose directory has only the passed values, as an earlier idp-cli wrote it, falls back to those: every parameter never passed takes the new module’s default. The deploy then prints a warning naming each such parameter whose default differs between the installed module and the new one, so you can pass the old value with --parameters. A second operator in a fresh directory without the label stack gets the module’s defaults with no warning, because nothing distinguishes that from a first deploy; pass every setting the deployment has.

Your own root configuration does not get this: a variable you do not set takes the new module’s default, so read the release’s CHANGELOG.md for changed defaults before upgrading it. The idp-cli deploy runs init -upgrade because the module source changed, and refuses the plan if it would delete or replace a stateful or retained resource (see With idp-cli deploy --terraform).

What keeps an upgrade from replacing a resource

Section titled “What keeps an upgrade from replacing a resource”

Three things in the module do what CloudFormation does implicitly on an update:

  • moved blocks. When a release renames a resource or moves it between nested stacks, its Terraform address changes, and without help Terraform would destroy the old resource and create a new one. Each release’s module carries a moved.tf with a block for every address that changed since the previous release, and for every earlier release, so an upgrade that skips releases is covered too. Terraform applies them as part of the plan; there is nothing to run.
  • Generated names are kept. A name the module chose (a table’s, a bucket’s prefix, a role’s) is kept for the life of the resource, as CloudFormation keeps a name it generated, so a later release that would derive it differently does not replace the resource.
  • Values that only a custom resource knows. Some properties are filled from a custom resource’s result, which Terraform cannot know until apply whenever that custom resource’s inputs change. For a property that cannot change in place, such as the knowledge base id of the knowledge base’s data source, Terraform would plan a replacement where CloudFormation, which sees the result, changes nothing. Where the result is known to be stable, the module keeps the stored value and replaces the resource only when one of its other inputs changes, which is when CloudFormation would.

The plan check in idp-cli deploy --terraform is the backstop for anything these miss. If you deploy the module from your own configuration, read the plan for deletions of the addresses in statefulAddresses before applying.

A role the template leaves unnamed keeps the name it was created with for the life of the deployment, as CloudFormation keeps a name it generated. So a deployment created from a module that predates stack-prefixed role names keeps its terraform-<timestamp> role names across upgrades; only a new deployment gets names a scoped deploying role can create (see Deploying with a scoped role). Replacing a role is not contained to the role: custom resources that take its ARN are updated, and their results are unknown until apply, which is the case the previous section’s third item handles.

In release 0.6.15 and earlier, any upgrade that changed the CloudFront security-headers policy (its Content-Security-Policy, for example) stopped part way through the apply at awscc_cloudfront_response_headers_policy.security_headers_policy, with a Cloud Control ValidationException naming XSSProtection: the provider sent back the empty object it had stored for that unset header. The policy now sets X-XSS-Protection: 0 explicitly, so upgrading to a release with the fix updates the policy in place, including on a deployment that an earlier failure left part way, and so do later changes to it. CloudFormation deployments were never affected.

The two Lambda asynchronous-invocation settings (awscc_lambda_event_invoke_config, for the queue sender and the reporting rollup function) failed the same way on any upgrade that changed their retry count, event age or destination: Lambda reports an unset success or failure destination as an empty object, and Cloud Control refuses an in-place update while one is present. No value avoids that, since any destination changes where results go, so the module now replaces these two resources instead of updating them: a change to any of their settings deletes the configuration and creates it again in the same apply, and the plan shows it as replaced “due to changes in replace_triggered_by”. Between the delete and the create, asynchronous invocations of that function use Lambda’s defaults. Whether the first upgrade to a module with this change replaces them depends on the binary: measured with the releases make terraform-check pins, OpenTofu 1.13 replaces them once, and Terraform 1.7 and 1.17 and OpenTofu 1.7 do not.

Read the release’s CHANGELOG.md entries and any migration guide for the release before upgrading, as for a CloudFormation stack: configuration changes and upgrade actions apply to both.

Security scanner findings on the module

Section titled “Security scanner findings on the module”

The CloudFormation templates record the scanner findings that were reviewed and accepted, either as a # checkov:skip=<rule>: <reason> comment inside a resource or as a cfn_nag rules_to_suppress entry in its Metadata. The module carries a checkov suppression over as #checkov:skip=<rule>:<reason> inside every Terraform resource block generated from that CloudFormation resource, with the same reason, when checkov’s Terraform rule inspects the same setting and fails in the same cases as its CloudFormation rule. That covers the Lambda dead-letter, concurrency and VPC rules, the ECR, DynamoDB, CloudWatch Logs, CloudFront, WAF and S3 access-logging rules the templates suppress, and the IAM write-access rule, which checkov numbers CKV_AWS_111 for CloudFormation and CKV_AWS_290 for Terraform. The list of rules, and the reason each pair is the same rule, is SUPPRESSION_EQUIVALENTS in the translator.

  • the suppressions in the table below, which are not carried. cfn_nag has no Terraform rules, and a checkov rule whose Terraform version fails in cases its CloudFormation version passes is not carried, because the recorded review did not consider those cases. Differences from CloudFormation and current limitations

Section titled “Differences from CloudFormation and current limitations”

A Terraform deployment runs the same functions with the same configuration as a CloudFormation deployment of the same version, but these things differ:

  • The feature-platform extensions (see Feature Platform) still install as their own CloudFormation stacks, beside the Terraform deployment.
  • A headless or GovCloud module is published only by a publish that also produced that template variant (idp-cli publish --terraform --headless --govcloud). If idp-terraform-<variant>-latest.json is not present in your Region’s bucket, that variant has not been published there as a module.
  • aws cloudformation list-stack-resources --stack-name <name> shows only the label’s one resource. The translation to the deployment’s real resources is done by the SDK’s hook, not by AWS, so the AWS CLI, the CloudFormation console’s Resources tab and any tool that does not import idp_sdk see only the label. Use terraform state list, or the resource directory named by TerraformResourceDirectory.
  • The reporting data-mart rollup function looks the deployment’s stacks up through CloudFormation from inside the deployment, and finds its functions by a stack-name tag. In a Terraform deployment the module gives that function the resource directory’s location (IDP_TF_RESOURCE_DIRECTORY) and read access to that one object, idp_common answers its stack lookups from it, and every function carries an idp:stack-name tag in place of CloudFormation’s reserved aws:cloudformation:stack-name. A CloudFormation deployment never sets that variable and is unaffected.
  • Physical names differ. CloudFormation generates names like <stack>-<LogicalId>-<random>; the module generates <stack>-<LogicalId>-<hash> for most resources, and Cloud Control generates its own names for awscc resources the template leaves unnamed.
  • The module adds resources of its own: the custom-resource bridge (a Lambda function named <stack>-cfn-bridge, its role, log group and an S3 bucket), the label stack with its template and resource directory in that bucket, and the IAM-propagation waits.
  • A failed apply is not rolled back, as described under Deploying.
  • The template’s Rules are checked at plan rather than at submit, and a rule whose inputs are not known until apply is checked during the apply; see Using the module beside your own resources.
  • The full stack has been applied, re-planned with no changes, and destroyed with both Terraform and OpenTofu, in a development account. The standard module has also been applied with DeployInVPC=true into a VPC with private subnets, NAT egress and an execute-api interface endpoint, in us-east-1 with Terraform: it re-planned with no changes, processed a sample document end to end with the pipeline’s functions in the VPC, and was destroyed. The headless and GovCloud modules are validated offline on every pull request, but neither has been applied.
  • terraform validate and plan print deprecation warnings for hash_key and range_key on the DynamoDB tables. They are warnings from version 6 of the aws provider and do not affect the deployment.
