v0.6.15 → v0.6.16 Migration

Section titled “v0.6.15 → v0.6.16 Migration”

v0.6.16 adds review routing (routing rules that decide whether a document is reviewed, in which review queue and with which reason for the reviewer) and gives every processing run a run plan that says at which step the run starts and which steps it leaves out. Both change the processing workflow: a Review Routing step is added after policy rule validation, a run after a completed review starts at a new step that applies the review, and several states of the workflow have new names.

You do not need to edit a configuration to keep processing documents on a stack you update. An update leaves the Review Routing switch (hitl.enabled) of every profile as it is, and a profile that has no routing rules of its own holds the documents it held before: a document with confidence alerts or missing required fields goes to the Default review queue when Review Routing is on. It holds one more: a document with a section whose extraction failed without failing the document, which v0.6.15 let complete unreviewed (see Where a failed section shows up). Every other document is not reviewed. A stack you create with v0.6.16 turns Review Routing on; see New stacks turn Review Routing on. This page lists what behaves differently, what to check if you integrate with the workflow, the API, the SDK or the review status object, and what a rollback does. The other changes in this release that an upgrade makes visible (document deletion, status filters, prefix mappings, prompts, Quick Start, the stack’s KMS key, new stack parameters and Terraform upgrades) are in Other behaviour changes in this release.

What stays the same

Section titled “What stays the same”
  • Statuses, the tracking table’s keys, the S3 layout of results and the review queue item states are unchanged.
  • Documents in review when the stack is updated can be completed, rejected or removed afterwards (see During the upgrade).
  • Step Functions execution names are built as before, so a redelivered message still cannot start a second execution.
  • A document reviewed from the document page while the Default review queue is disabled (see Human Review) is processed as before: it is not held, and it runs again from the beginning when its review is completed.
  • Configuration profiles need no conversion. A profile, or a revision a document is pinned to, that has no routing section takes the table the default profile holds: the built-in routing rules, until an Admin changes default’s.
  • The Review Routing switch of an existing profile. A stack update writes no value for hitl.enabled: a profile that has it off stays off, and one that has it on stays on. Only a preset or a custom configuration that sets hitl.enabled itself is applied on an update, as for every other setting.

Processing changes

Section titled “Processing changes”

A run starts at the step it needs

Section titled “A run starts at the step it needs”

Every message that starts a run carries a run plan: the kind of run (a new upload, a reprocess, saved edits, a completed review, a rejected review, a review that was removed or skipped, a send-back, a restart of a failed run), the step it starts at, and the optional steps it skips. The first state of the workflow, CheckRunPlan, sends the run to that step.

Runv0.6.15v0.6.16
New uploadevery stepevery step
After a completed reviewfrom the beginning, with each step detecting that its work existsstarts at Apply Review Changes, then policy rule validation, Review Routing, summarization, evaluation. When the reviewer changed the page grouping (Pipeline mode), the sections that were added or whose pages changed are extracted first, and the review is applied to the new values
After a rejected reviewfrom the beginning, ending at the review checkends the document as REJECTED without invoking a Lambda function
After a review is removed or skippedfrom the beginningstarts at policy rule validation
After a review is sent back (new)—starts at classification, or at the beginning in BDA mode; the review’s corrections are discarded
Reprocessfrom the beginning, or from classification or extraction with the SDKfrom any step, on every surface (web UI, SDK, CLI, MCP)
Process Changes after editsfrom the beginning, with each step detecting that its work existsstarts at the first step the edits affect: policy rule validation when only field values were edited

A run that starts later does not repeat the steps before it, so it is faster and costs less. The Processing Flow viewer shows the steps a run left out as Skipped.

A reviewer chooses no step. Where the run after a review starts is decided by the system, from the document as it is when the review ends. The dialog that finishes a review (Process Changes on a queue item) and the confirmation of Process Changes on a document outside a review both list the steps the run will do, each marked as running, skipped or not enabled, before you confirm. See How a review ends.

The run plan is in the execution input, as runPlan. A message with no plan (one queued before the update) runs every step, as before.

Review Routing step

Section titled “Review Routing step”

The new RoutingStep (Review Routing) runs after policy rule validation in both modes and decides whether the document is held. In v0.6.15 the decision was made by the step that assembles the document’s results, before policy rule validation. A document it holds carries the routing rule that placed it, a reason for the reviewer and the policy rules it failed. See Review Routing.

New stacks turn Review Routing on

Section titled “New stacks turn Review Routing on”

Whether documents are held for review is the Review Routing switch of each configuration profile (hitl.enabled).

StackReview Routing after the deployment
A stack updated to v0.6.16Unchanged in every profile. A managed profile that the update adds takes the value of default
A stack created with v0.6.16On in default and in the managed profiles the stack creates, unless the preset or the custom configuration sets hitl.enabled itself
A headless deployment, created or updatedOff: it has no review queues

On a new stack, a document with a failed section, a confidence alert or a missing required field therefore waits in the Default review queue, with status HITL_IN_PROGRESS, until a person finishes its review. In v0.6.15 a new stack came up with the switch off, unless the configuration it was deployed with turned it on.

If nobody reviews the documents (a batch job, a load test, an integration that waits for every document to reach COMPLETED), turn Review Routing off in the profile the documents are processed with:

  • In the web UI: Configuration › Processing Settings › Review Routing (Optional), switch Review Routing off, and save.

  • With the CLI, upload a file that holds only the switch; every other setting keeps its value:

  • For a stack that should come up with it off, set hitl.enabled: false in the configuration the stack is deployed with (CustomConfigPath, or idp-cli deploy --custom-config).

The cases are listed in The Review Routing switch.

Policy rule validation and review

Section titled “Policy rule validation and review”

Because routing can read policy rule verdicts, policy rule validation runs before a document is held. When the review is completed, it runs again on the corrected values. A document that is reviewed therefore runs policy rule validation twice, where v0.6.15 ran it once, after the review. If you use both features, expect the Bedrock cost of policy rule validation to double for reviewed documents; documents that are not reviewed are unaffected.

Two further changes to policy rule validation:

  • Every policy rule has a stable id, policy_type.rule_key, and every result a normalised verdict (pass, fail, not_found, unknown) beside its recommendation text. Both are in consolidated_summary.json and in the Markdown report.
  • The verdict pass runs for every document, including a document with one section, which previously got facts and no verdict. It makes one model call per policy rule the symbolic engine did not decide.

See Rule Validation.

The rule-validation preset is now a bank statement review

Section titled “The rule-validation preset is now a bank statement review”

The rule-validation preset no longer holds the healthcare prior-authorization configuration. It holds the policy rules of samples/rule-validation/bank-statement-review-policy.pdf and validates samples/bank-statement-multipage.pdf, so rule validation, Policy Discovery and the review routing showcase share one sample domain. The healthcare samples medicare_respiratory_pa_packet.pdf and NCCI Medicare Policy Manual.pdf are removed from samples/rule-validation/.

A stack deployed with Configuration Preset rule-validation takes the bank statement configuration as its default profile on its next update, replacing the prior-authorization classes, policy classes and policy rules default held. Another profile keeps every setting it saved, and takes the new default’s value for any setting it does not hold.

⚠️ Action: if you process prior-authorization documents with default on such a stack, copy it into a profile of your own before you upgrade (Create profile in the Configuration Profiles table) and make that profile active. The Health Insurance Review sample feature keeps the prior-authorization classes and policy rules in its own configuration preset, but ships no sample document.

Hooks

Section titled “Hooks”

Pipeline hooks fire for the steps a run does. A run that starts at a later step does not fire the hooks of the steps before it, and a step the run plan skips does not fire its hook. A step that the configuration turns off still fires its hook, as before.

What this changes for a hook:

  • preprocessing, postOcr, postClassification and postExtraction fire on the run that does those steps, and not on the run after a completed review, which starts after them. In v0.6.15 they fired on both. The one exception is postExtraction, which fires on that run for each section it extracts again because the reviewer changed the page grouping.
  • postRuleValidation fires before a document is held for review, and again on the run after the review is completed. In v0.6.15 it fired after the review only.
  • postSummarization and postprocessing fire on a run that reaches those steps. A run that ends by holding the document in a review queue does not reach them, so they do not fire while a document waits in a queue.

To let a hook tell the runs apart, the payload has three new top-level fields:

FieldValue
runKindnew_upload, reprocess, saved_edits, review_completed, review_rejected, review_skipped, sent_back, restart_failed or legacy_review; unplanned for a run with no run plan
startStepThe step the run started at, for example beginning, extraction or apply_review_changes
reviewedtrue when the document’s review was completed and this run does not extract again

A hook that needs the values no review will change should use postSummarization or postprocessing: a run reaches them only when the document is not held. A postRuleValidation hook sees the values before a possible review, and sees them again, with reviewed: true, on the run after a completed review. When that run extracts sections again first, it carries runKind review_completed with startStep extraction and reviewed: false, because the newly extracted values are not confirmed by a reviewer; test reviewed, not runKind, to act on confirmed values. The existing payload fields are unchanged. The Health Insurance Review sample feature (0.2.3) stores reviewed and runKind with each claim status. See Feature Platform developer guide.

Review status object: schema version 1.1

Section titled “Review status object: schema version 1.1”

review/status.json moves from schema version 1.0 to 1.1. The change is additive:

  • schema_version is "1.1".
  • A new optional property routed_by holds the routing rule that placed the document and what its reviewer is told: table_id, rule_id, rule_label, placed_queue, fallback_reason, reason, reason_source, policy_failures (each with rule_id, policy, name, reason and pages) and policy_failure_count. It is null for an item no routing rule placed (for example one created by Send to review). reason can hold extracted values, so treat the object as document content.
  • The reason kind values now include missing_required and extraction_failed in the schema.

A consumer that checks for schema_version == "1.0" exactly has to accept "1.1". A consumer that ignores unknown properties needs no change. See Review status for downstream consumers.

API changes

Section titled “API changes”

Two operations of the UI API return a different shape:

Operationv0.6.15v0.6.16
reprocessDocumentBooleanReprocessResult: queued, and for each document status (QUEUED, REFUSED or FAILED), startStep, reason and message. It also takes startStep and skipSteps
listReviewQueuesa list of queue definitionsa page: items and nextToken. It takes limit and nextToken

processChanges keeps its arguments, and its answer gains startStep and steps: the step the run it queued starts at, and every step with its state.

New operations: getReprocessOptions, sendBackReviewItem, getReviewCompletionPlan, getProcessChangesPlan, testRoutingTable, getReviewQueueReferences and convertRoutingDmn. sendBackReviewItem takes the document, the review cycle and an optional note, and no start step: the run starts at classification, or at the beginning in BDA mode. The two plan operations read what finishing a review, and what Process Changes, would run, and start nothing. Review items gain queueName, routedBy (with reason, policyFailures and policyFailureCount) and processingMode, and documents gain ReviewQueue, ReviewQueueName and ReviewRoutedBy. updateConfiguration answers with warnings when a save leaves a routing rule that reads a policy rule result while policy rule validation does not run. The groups each operation admits are in RBAC.

Reload the web UI after the update. A browser tab loaded before the update runs the previous UI, which expects the previous shapes of these two operations.

SDK, CLI and MCP

Section titled “SDK, CLI and MCP”

Reprocessing is done by the stack, not by the client. The SDK and the CLI invoke the stack’s reprocess function, so every surface applies the same rules: which steps a document can start at, what is cleared first, and what is refused.

  • Permissions. The caller’s credentials need lambda:InvokeFunction on the stack’s reprocess resolver function (and on the review queues resolver function for client.review_queues and idp-cli review-queues), and cloudformation:DescribeStackResources and cloudformation:DescribeStacks to find them through the nested API resolver stack. In v0.6.15 a reprocess needed access to the tracking table, the buckets and the document queue instead.
  • SDK. client.document.reprocess(document_id, step=…, skip=…) and client.batch.reprocess(…) take any step, and return each document’s status, reason and message. rerun() remains as a deprecated alias. client.document.reprocess_options(…) lists the steps a document can start at.
  • CLI. idp-cli reprocess --step <step> [--skip <step> …]; rerun-inference remains as an alias. The step names are beginning (alias ocr), classification, extraction, assessment, policy_rule_validation, summarization, evaluation, and resume for a failed document.
  • MCP. The reprocess tool keeps its name; step accepts the same steps and skip is new.
  • A stack that has not been updated does not have the functions. The v0.6.16 SDK and CLI say so and name the release; update the stack, or use the v0.6.15 client with it.

A document a reprocess refuses is a result, not an error: the call succeeds and that document’s status is REFUSED with a reason code such as RUN_IN_PROGRESS, OUTPUT_MISSING or STEP_NOT_IN_MODE. See IDP SDK and IDP CLI.

Names in the web UI

Section titled “Names in the web UI”

The configuration keys are unchanged. On Configuration › Processing Settings the sections for the two steps have these names, and are in the order the pipeline runs the steps:

SectionHoldsKey
Policy Rule Validation (Optional)Whether policy rule validation runs, and its settings. The policy rules are on the Policy Schema tabrule_validation
Review Routing (Optional)The Review Routing switch, the confidence threshold, whether a missing required field is reviewed, and the Inbox and bulk-skip settingshitl

The routing rules are on the new Routing Rules tab, after Policy Schema (key routing). The report of a document’s policy rule results is the Policy Rule Validation Summary, on the document page’s and the edit page’s Reports menu, and the pipeline steps are named Policy Rule Validation, Review Routing and Apply Review Changes wherever a step is listed.

Reporting

Section titled “Reporting”
  • The rule_validation_details table gains the columns rule_id and verdict.
  • document_reviews.top_reason_kind is routing_rule for a document that a routing rule placed with no confidence alert, no missing required field and no failed section, and extraction_failed for a document whose first review reason is a section whose extraction failed.
  • document_reviews gains the column routing_reason: the reason of the routing rule that placed the document, as written, with its placeholders unfilled. See Reporting Database.

Other behaviour changes in this release

Section titled “Other behaviour changes in this release”

These changes are not part of Review Routing or run plans, but an upgrade makes each of them visible. The CHANGELOG has the full entry for each.

Deleting a document purges every version of its upload

Section titled “Deleting a document purges every version of its upload”

The input bucket is versioned. Deleting a document (web UI, idp-cli delete-documents, the SDK, or the PII Anonymizer’s redact copy and stop mode) now deletes every version and delete marker of the document’s upload, so a deleted document’s upload can no longer be restored from the input bucket’s noncurrent versions. A CLI or SDK caller needs s3:ListBucketVersions and s3:DeleteObjectVersion on the input bucket in its own IAM policy; without them the current object is still removed, but the document is reported as failed, naming the input bucket, because the versions remain. See delete-documents.

Status filters select documents, and accept only real statuses

Section titled “Status filters select documents, and accept only real statuses”

idp-cli delete-documents --status-filter and the SDK’s client.batch.delete_documents(status_filter=...) used to match no document at all, so a script that passed a filter deleted nothing. They now match the status the pipeline records, so the same script now deletes the documents it names. Check such scripts before you run them against an updated stack.

The CLI’s status options (delete-documents --status-filter, status --object-status) and the SDK’s status_filter accept only the statuses a document can be recorded with, and refuse anything else, including PROCESSING; the SDK raises IDPConfigurationError. Use the step status you mean, such as RUNNING, OCR or EXTRACTING. idp-cli status --batch-id with no --object-status now also finds documents at a processing step, aborted, rejected or waiting for review. See status and batch.delete_documents().

Prefix mappings

Section titled “Prefix mappings”
  • A prefix mapping that names a configuration profile which does not exist now refuses the document: it is recorded as Failed with a reason naming the mapping and the missing profile, where it used to be processed under the profile its upload named or the active one. See A mapping whose profile does not exist.
  • Only test-studio and pii-anonymizer, the submission-source values Test Studio and the PII Anonymizer write, exempt an object from prefix mappings. An object carrying any other value is mapped like an ordinary upload. See Documents this deployment submits itself are exempt.

A prompt with more than one {DOCUMENT_IMAGE} fails the document

Section titled “A prompt with more than one {DOCUMENT_IMAGE} fails the document”

A classification or extraction prompt that contains {DOCUMENT_IMAGE} more than once used to be accepted with a log warning; a document sent with it now fails with found N occurrences, but exactly 1 is required. Run idp-cli config-validate on your profiles, which reports these prompts, and remove the extra placeholders. See Image placement.

A content-filter block fails only its section

Section titled “A content-filter block fails only its section”

When Amazon Bedrock’s content filter withholds the extraction model’s reply for one section, that section is shown as Failed with an extraction_failed issue and the rest of the document completes, where the whole document used to fail. With Review Routing on, such a document is held for review (see Where a failed section shows up).

EU profiles saved before this release keep a us. model id

Section titled “EU profiles saved before this release keep a us. model id”

A model setting that a configuration leaves out now takes the stack’s Region’s inference profile, so an EU stack gets the eu. profile. A configuration profile you created in an EU stack before this release stored the us. id it was given as an explicit value, and keeps it; the update rewrites only the profiles the deployment itself provides. In such a profile, choose the model again (or restore it from the default) for each step that fails with an invalid model identifier. See EU Region Model Support.

Quick Start is Admin-only

Section titled “Quick Start is Admin-only”

Only Admins see Quick Start and only Admins can send it a message; both chat routes refuse a Quick Start message from any other group. On a stack deployed with EnableQuickStartWidget=false, the chat routes also refuse every Quick Start message, where the parameter used to hide Quick Start in the web UI only. See Quick Start.

Deleting the stack keeps its KMS key

Section titled “Deleting the stack keeps its KMS key”

The KMS key the stack creates now carries DeletionPolicy: Retain, so the retained buckets it encrypts stay readable after the stack is deleted. The key is billed until you schedule it for deletion; idp-cli delete names it and prints the command. See The retained KMS key.

New stack parameters

Section titled “New stack parameters”

All three default to the previous behaviour.

  • TenantSelection (default Disabled) lets a user whom the identity provider grants two or more tenants choose the active one. It requires TenantGrantSource=IdpClaim. See Letting a user choose among their tenants.
  • ManageApiGatewayAccountSettings (default true) decides whether the stack sets the Region’s API Gateway CloudWatch logging role. Set it to false on every deployment in a Region but one. See Monitoring.
  • CustomerManagedKmsKeyArn (default empty) uses a KMS key of your own instead of the one the stack creates. It can be set only when a stack is created; an update that sets, clears or changes it is refused and rolled back. See Customer Managed KMS Key.

Document attribute sidecars

Section titled “Document attribute sidecars”

A JSON sidecar of document attributes must be stored at the document’s own key plus .idp-attributes.json. An object whose key ends in .idp-attributes.json is treated as a sidecar and not processed. See S3 upload: a JSON sidecar.

Terraform upgrades keep the deployment’s parameter values

Section titled “Terraform upgrades keep the deployment’s parameter values”

An idp-cli deploy --terraform upgrade now keeps the value the deployment has for every parameter you do not pass, as a CloudFormation update does, reading it from the deployment’s label stack. It used to keep only the parameters passed to earlier deploys from the same directory, so a parameter never passed took the new release’s default. A parameter new in this release takes its default. See Upgrading.

Node.js 26 to publish or build from source

Section titled “Node.js 26 to publish or build from source”

Building the web UI from a checkout, and so idp-cli publish, publish.py and make setup-node, needs Node.js 26 or later. A stack update builds the web UI in CodeBuild with Node.js 26 and needs nothing from you. See Deployment.

numpy 2 and pyarrow 26

Section titled “numpy 2 and pyarrow 26”

idp_common’s ocr, multi_document_discovery and all extras pin numpy 2, and its reporting, test and all extras pin pyarrow 26, as do the Lambda layers and images built from them. The solution’s results and Parquet files are unchanged. A pipeline hook or extension that installs idp_common with those extras, or imports numpy or pyarrow from the reporting layer, gets the new major versions and should be tested against them.

During the upgrade

Section titled “During the upgrade”

Runs in progress. An execution that is running when the state machine is updated finishes on the definition it started with. If it ends by holding the document for review, the document is in the Default queue and can be reviewed after the update like any other. Executions started after the update use the new definition.

Documents in review. A document held before the update is completed, rejected or removed after it with the new behaviour: completing it starts a run at Apply Review Changes (or at extraction, for a section that has no extracted values), rejecting it ends it as REJECTED without a Lambda invocation, and removing it starts a run at policy rule validation. Its review record gets no routed_by, since no routing rule placed it, so its Review Reason panel shows the alerts and no routing notice.

The Review Routing switch. The update changes it in no profile (see New stacks turn Review Routing on).

Messages already queued. A message queued before the update has no run plan and starts a run of every step, in which each step detects work that exists, as in v0.6.15.

Rollback

Section titled “Rollback”

Rolling the stack back to v0.6.15 is possible, with these effects:

  • Runs started on the v0.6.16 definition that are in progress during the rollback finish on that definition and call functions the rollback removes, so they fail at the routing step. Reprocess those documents afterwards.
  • Profiles saved by v0.6.15 lose their routing section, because that release does not know the section and writes the profile without it. Export the routing tables first (see DMN XML export and import) if you intend to update again.
  • Review queues other than Default stay in the review table. v0.6.15 routes every held document to the Default queue and its web UI cannot create a queue, but it lists the existing queues and their documents can be worked.
  • Review items keep the fields v0.6.16 wrote (routed_by with its reason and failed policy rules, the placement count, the processing mode, the page layout recorded at placement and the start of the run after the review). v0.6.15 ignores them.
  • review/status.json objects written by v0.6.16 keep schema version 1.1 until the document is reviewed again.
