Verdict

Section titled “Verdict”

✅ Ship — the published artifact deploys in every shipped configuration, upgrades cleanly from 0.6.10 without changing extracted values, and shows no accuracy or cost regression. 7 of 8 tiers pass; tier G (browser UX) is NOT RUN, for want of a browser on the validation host. No finding is attributable to this release.

Tier G’s scope is the whole web UI, not one flow. git diff v0.6.10..64e95c7d2 -- src/ui/ is 28 files, +1,902 / −356: Test Studio’s sortable columns and classification-errors panel, the Document panel’s cost calculation, the configuration revision-history panel, and the issue-form links. The compensating coverage is the UI unit suite — 105 files, 1,215 tests, all passing — which runs in neither make test nor make lint-cicd and was invoked separately (make ui-test). Unit coverage is not a person completing a flow.

The release’s own changes are error-path fixes, so the healthy-document benchmark correctly shows no movement: the A/B over 342 runs reports 0 regressions and 0 improvements, grid cost +0.4% and wall −2.9%. A release that fixes what happens after a transient Bedrock error should not move accuracy on documents that never hit one, and it does not. Step 8 of the nightly SDLC suite — agentic extraction with large tables, the path #1310/#1014 repair — passed on the byte-identical tree, which is the end-to-end confirmation the A/B cannot give.

Eighteen findings, none introduced by 0.6.11. Four are in shipped product code and all four pre-date this release (Findings 1, 2, 11, 12). The rest are gate, test, harness or documentation issues — including three controls that exist but do not run where it matters (Finding 13), two reporting limits that make a published figure unsafe (Findings 15, 16), and a vacuous pass that a completion count hides (Finding 14). Findings 11–18 are from the published-artifact pass; 1–10 are the prerelease pass’s, retained unchanged.

Two findings from the first validation are fixed in the released code: the library integration tier went from 15 failures of 23 selected to 1 of 19. Commit 5310684a3 added credential reconciliation to tests/conftest.py, corrected the wrong assert "output" in response assertions rather than deleting them, and re-homed the MagicMock test to tests/unit/. The one remaining failure reproduces identically at v0.6.10.

Effect of the upgrade on extracted values: none detected

Section titled “Effect of the upgrade on extracted values: none detected”

Fresh stack from the published 0.6.10 template → document → update-stack with UsePreviousValue on all 90 parameters → same document. UPDATE_COMPLETE, zero ROLLBACK/FAILED events, and both UpdateSchemaConfig and UpdateDefaultConfig custom resources returned SUCCESS — the step where upgrades deadlock.

Parameter-set diff: 90 both sides, 0 added, 0 removed, 0 newly required, 0 default changes. One AllowedValues narrowing: KnowledgeBaseModelId drops the two Sonnet 4 entries. The default is unchanged (us.amazon.nova-pro-v1:0) and this stack held it, so the rejection the CHANGELOG warns about was not triggered; a stack explicitly pinned to Sonnet 4 is refused before any resource changes.

Output diff: 1,934 leaf fields over 6 sections, 76 value differences — of which only 8 are extracted business data (inference_result); 33 are explainability_info, 29 metadata or timings, 6 processing_report.

A same-version control settles those 8 as noise. Running the identical document a third time on the already-upgraded stack gives 15 inference_result differences — more than the upgrade produced — and flips the same Payslip tax Period fields back. So the upgrade changed nothing detectable; the 8 sit below a measured noise floor of 15. Product observation, present at 0.6.10 too: those Period fields hold a monetary amount whose sign is bistable across repeat runs of identical code, and casing is unstable (JOHN / John).

3. Orphaned CloudFront policies accumulate until they block deploys (product defect, pre-existing)

Section titled “3. Orphaned CloudFront policies accumulate until they block deploys (product defect, pre-existing)”

Tier C’s Jobs API variant rolled back on:

The quota is L-CF0D4FC5, 20 per account, adjustable, and the account sits at exactly 20. (The MaxItems: 100 in the list-response-headers-policies reply is the page size, not the quota — easy to misread as headroom.) Thirteen of the twenty are IDP <stack>-security-headers-policy entries, several belonging to stacks long deleted. The variants that passed all set WebUIHosting=APIGateway and create no CloudFront distribution; Jobs API uses the default CloudFront hosting and so hit the wall.

Why they accumulate — lib/idp_sdk/idp_sdk/_core/stack.py:2199 calls

with no IfMatch=. CloudFront requires the current ETag there, so every call fails InvalidIfMatchVersion and the failure is swallowed into a logger.warning. That teardown path has therefore never deleted a single orphaned policy; one run logged twelve such warnings. The sibling implementation is correct — lib/idp_sdk/idp_sdk/_core/cleanup_orphaned.py:880-889 does get_response_headers_policy → read ETag → delete_response_headers_policy(Id, IfMatch=etag).

And the test cannot catch it. The teardown suite’s fake is tests/unit/test_stack_deployer_teardown.py:2110, "delete_response_headers_policy": lambda Id, **_k: — a signature that accepts the missing IfMatch silently. The orphaned-cleanup suite’s fake declares delete_response_headers_policy(self, Id: str, IfMatch: str) and would have failed.

A quota increase to 100 was requested rather than deleting policies, because three of the twenty belong to unrelated stacks in the same account.

11. A whole-document request over about 300 seconds always fails (product defect, pre-existing)

Section titled “11. A whole-document request over about 300 seconds always fails (product defect, pre-existing)”

Non-streaming converse runs with read_timeout = CONFIDENCE_READ_TIMEOUT_SECONDS = 300.0 and DEFAULT_MAX_RETRIES = 7, inside a 900 s Lambda, and nothing checks the remaining invocation before starting an attempt — grep finds no pre-attempt budget check in bedrock/client.py, and the deadline logic that does exist says in its own comment that it “CLAMPS a sleep; it never converts one into a failure”. Measured: attempt 1 dies at ~300 s, attempt 2 at ~606 s, attempt 3 starts at +610.8 s with 289 s left and is killed at 900 s; Step Functions retries once and the ProcessSections map discards the document.

Pre-existing, not 0.6.11. The constant is unchanged at v0.6.10; 0.6.11 raised the streamed agentic read timeout to 600 s and added a ladder guard on that path only.

16. Accuracy for the real-document corpora was recorded but not reported (benchmark harness)

Section titled “16. Accuracy for the real-document corpora was recorded but not reported (benchmark harness)”

All 2,280 corpus rows (realkie 1,140, ocr_bench 1,140, 20 documents each at 3 repeats) reached COMPLETED with 0 failures, and carry cost ($0.1932 and $0.0395 per document), latency and accuracy: weighted_accuracy is populated on 2,280 of 2,280 rows (realkie mean 0.796, ocr_bench 0.996) with class_accuracy 1.000, scored by the product’s own evaluation against the corpus labels.

What is 0 and nan is the exact-key family — cells_compared, cell_accuracy, scalar_accuracy, completeness_recall — and it does not apply to these rows at all. A reference corpus is a labelled test set on the stack, so there is no local per-cell truth file to compare against; aggregate.score_reference_run hands analyze.score_doc no truth, and the row comes from score_reference rather than score_synthetic. The two scorers emit disjoint families, and the absence is symmetric: on this same grid the 380 completed synthetic rows carry no weighted_accuracy either, by the identical mechanism. So the nan is a property of which column was read, not of the runs.

The defect was that nothing said so. The row recorded neither which scorer produced it nor which column held its accuracy, the four exact-key columns were simply absent from the CSV, and the notice write_summary prints for exactly this case was gated on docs_missing_truth — which run_matrix populates only with synthetic documents whose local truth file is missing, so it never fired for a reference corpus. Closed by #1364: every scored row now carries scored_against and, where the exact-key family does not apply, exact_truth_unavailable naming the substitute columns; cells_compared reaches the CSV beside cell_accuracy; cell_stats carries the per-scorer denominators; and aggregate.py --reference-tables renders the per-corpus per-cell table from a committed summary.

config-guidance.md §2c keeps the v0.6.8 two-model pair, which is a deliberate trade rather than a consequence of this: v0.6.11 ran the corpora at the control only, so refreshing one arm would turn that section’s model comparison into a cross-release one. The v0.6.11 control figures are quoted in §2c with the command that renders them.
