Release Validation: v0.6.9

Release Validation Record — v0.6.9

Section titled “Release Validation Record — v0.6.9”

Release: v0.6.9 (VERSION = 0.6.9, CHANGELOG.md section cut at 1c67405ab) Validated: 2026-09-18 → 2026-09-19, us-west-2 (seller tier us-east-1), commercial partition Artifact under test: a self-published build of the release commit — s3://<PRIVATE_BUCKET>/idp069/idp-main.yaml, Description (v0.6.9), built with publish.py … --clean-build from develop 08b1ed242.

⚠️ This is a pre-publish validation, and that is a real difference from every previous record in this directory. idp-main_0.6.9.yaml was not present in any of the three public aws-ml-blog-* buckets while this ran (HTTP 403 in all three; idp-main_0.6.8.yaml returns 200). Earlier records validate the published object. This one validates a build of the same commit, published to a private bucket. The nested-stack TemplateURLs therefore point at that private prefix, so what is proven is the template content, not the public objects’ presence or permissions. Re-run the tier-C and tier-D rows against the public URLs once the release is published, per docs/release-runbook.md.

The v0.6.8 side of every comparison below is the published idp-main_0.6.8.yaml.

Verdict

Section titled “Verdict”

✅ Ship — with one qualification that is unusual enough to state before the tier table.

11 of 12 tiers pass. Tier G (browser UX review) is NOT RUN: this session had no browser MCP server (the chrome-devtools server the ux-test skill requires is not registered, and the browsermcp server that is registered reported CONNECTION_CLOSED). It is not reported as passing and it is not dropped.

The qualification: the release as first committed could not be deployed at all by anyone using the optional CloudFormation service role, and this validation is what found that. The #927 service-role hardening shipped with iam:PassRole scoped by an iam:PassedToService list that omitted cloudformation itself — so the first nested stack the parent creates (DOCUMENTKB) was denied and every deploy rolled back. Two independent stacks reproduced it. Fixed in b249ebf71, after which all five deploy variants and both transforms passed. The commit that fix landed on is the one validated here, and the fix is not in the document-processing path.

No regression was found in the document-processing path. The upgrade tier extracted more data after the upgrade than before (172 leaf fields vs 166, identical classifications, nothing lost). The one genuine accuracy movement in the benchmark A/B is confined to the bedrock_llm OCR backend on a single scalar field (Finding 2) and is a second instance of a hazard already documented for that backend.

The customer path on a fresh throwaway stack IDPUpg068to069, created from the published idp-main_0.6.8.yaml, document processed, then update-stack to the v0.6.9 build with UsePreviousValue=true on every existing parameter.

  • UPDATE_COMPLETE, no rollback, no FAILED events. Description now (v0.6.9).
  • Parameter set: 88 → 89 — one added, none removed, none newly required.
  • UpdateDefaultConfig / UpdateConfigurationFunction logged no error, no migration failure and no rollback path. (This is where upgrades deadlock, so it was tailed during the update.)
  • Document processed 1/1 on both sides. S3 outputs were pulled before teardown.

Per-section diff of the same lending_package.pdf — 6 sections both sides, identical classifications (Payslip, US-drivers-licenses, Bank-checks, Bank-Statement, W2, Homeowners-Insurance-Application):

Measure0.6.80.6.9

The 6 new keys are FederalTaxes[1] and [2] on the Payslip section (ItemDescription, Period, YTD each). The payslip lists six statutory deductions, so a three-entry FederalTaxes list is more complete than the one-entry list 0.6.8 returned; that is also why the null count rose by one. Nothing was lost — every key present on 0.6.8 is present on 0.6.9.

The 2 value differences are both on the Bank-checks section, and the page text supports either reading, so both are recorded as behaviour changes rather than wins or losses:

  1. check_number: 0000000000 → 0001379. The check carries both a labelled field (Payroll check number: 0000000000, a placeholder on this VOID sample) and a MICR line (⑈001379⑈ ⑆122000496⑆). 0.6.8 returned the labelled field; 0.6.9 returned the MICR value, zero-padded to seven characters. Neither is wrong on this document — but a customer keying off the labelled field would see the value change.
  2. bank_name: "BANK NAME" → null. The page literally contains the text BANK NAME, the placeholder where a real check prints the bank. 0.6.8 returned the literal string; 0.6.9 abstained. This is consistent with the release’s nullable-scalar-leaf transport change (an agent that cannot answer returns null rather than echoing a placeholder), and it is the one difference that could hide a real loss on a document where the bank name is genuinely present. Not reproduced on any other field or section here.

No extracted number changed.

Release benchmark A/B (published v0.6.8 → the v0.6.9 build)

corefast, 19 cells × 3 docs × 3 repeats = 171 runs per side, 342 total, 0 failures on either side. Same stack IDPUpg068to069: the 0.6.8 side ran before update-stack, the 0.6.9 side after, so the only difference is the code. --native-upload, byte-identical configs, same pricing table (pricing.yaml sha256 a8897364… both sides), both sides scored by the same aggregate.py.

aggregate.py --compare: 2 flagged regressions, 0 improvements, 0 cell-level regressions, 8 inconclusive. One flagged regression is real, one is noise; full treatment in docs/benchmarking/releases/v0.6.9.md.

  • Real — core-llm-simple-sep | small_narrow.pdf: scalar_accuracy 1.000 → 0.500, deterministic 3/3 each side. See Finding 2. Everything else on that cell is unchanged and perfect (completeness_recall 1.000, rows_extracted 100/100, cell_accuracy 1.000 over cells_compared = 200).
  • Noise — core-tl-adv-sep | longdesc_100.pdf: cost +22% (n=3 each side) inside a cell whose own cost CV is 0.50–0.62, and −46% at the cell level. --compare reports 0 cell-level regressions.

⚠️ No cost claim should be drawn from this A/B, in either direction. 0.6.9 changes the cost instrument: it fixes long-context (:1m) models being reported at up to double their real cost, and fixes cache tokens being mispriced by substring match. The per-run cost comes from the stack’s own metering, so the 0.6.9 side measures with a corrected ruler. Eight cells show large cost decreases (−23% to −53%); part of every one of those is the fix rather than a behaviour change, and this grid cannot separate the two. Quote the single-release cost suites re-measured on 0.6.9 in the guidance paper instead.

The same caveat applies to accuracy in the other direction: stickler-eval 0.5.0 → 1.0.0 now infers evaluation comparators per field. Both sides here were scored by the same (new) scorer, so this A/B is internally consistent — but its 0.6.8 numbers are not the ones in the published v0.6.8 benchmark entry, which were scored with the old comparators.

baseline.json is deliberately not promoted, because the cost half of the comparison measures a changed instrument and would mislead the next release’s gate.

Findings

Section titled “Findings”

Two findings in the shipped solution, both fixed or fully characterised before this record was written, ordered by how much they matter. The first is the reason this validation was worth running: it would have stopped a customer deploying.

Defects found in the project’s own test and build tooling are tracked in the issue tracker rather than here. This record is about the release.

Finding 1: the hardened CloudFormation service role could not deploy the solution (PRODUCT, ship-blocking)

Section titled “Finding 1: the hardened CloudFormation service role could not deploy the solution (PRODUCT, ship-blocking)”

Two coupled defects from the #927 service-role hardening, both fixed.

1a — the required parameter was never passed. iam-roles/cloudformation-management/IDP-Cloudformation-Service-Role.yaml gained a required, no-default CreatedRolePermissionsBoundaryArn. create_iam_resources() in scripts/sdlc/codebuild_deployment.py created that stack with no Parameters at all, so every caller died before deploying anything:

Callers: all four stacktest-* variants, both transform-deploy-test-* tiers, and the SDLC pipeline’s own step 0. Nothing in the repository ever deployed a stack through this role, so the hardening shipped with every deployer that uses it broken. Fixed in fd4acecba, which creates the boundary policy first, passes CreatedRolePermissionsBoundaryArn and ManagedStackNamePrefix explicitly, wires the same ARN into the IDP stack’s PermissionsBoundaryArn, and adds test_script_deployed_template_parameters.py.

1b — the service role could not pass itself to its own nested stacks. With 1a fixed, the deploy still rolled back:

The PassStackRolesToStackServices statement granted iam:PassRole under StringEqualsIfExists { iam:PassedToService: [...] }, and that list of 14 services did not include cloudformation. When the parent stack creates a nested stack, CloudFormation propagates the parent’s service role to the child — an iam:PassRole whose iam:PassedToService is cloudformation. The Resource matched (role/idp*); the condition did not, so no Allow applied. No explicit Deny was involved.

This is easy to miss because a PassServiceRoleToCloudFormationOnly statement with exactly this grant does exist — in a separate managed policy, <StackName>-PassRolePolicy, documented for an administrator to attach to the deploying human. It is not attached to the service role, so it does nothing for the role passing itself.

Impact before the fix: any customer using the optional CloudFormation service role could not deploy at all. The solution is nested-stack-based, so DOCUMENTKB is reached every time. Observed live on two independent stacks. Fixed in b249ebf71; adding cloudformation.${AWS::URLSuffix} to the list is what took both stacks to CREATE_COMPLETE, which is also what confirms the diagnosis.

Why nothing caught it: validate_service_role_permissions.py reasons about the policy’s shape — wildcards, boundary conditions, PassedToService presence — and a condition that is present but missing one required value passes every such check. Only deploying through the role finds this, and no tier did until this one.

Finding 2: the bedrock_llm OCR backend now emits markdown emphasis, and one extracted scalar changed with it (PRODUCT, narrow)

Section titled “Finding 2: the bedrock_llm OCR backend now emits markdown emphasis, and one extracted scalar changed with it (PRODUCT, narrow)”

core-llm-simple-sep | small_narrow.pdf, deterministic on 3/3 runs each side:

0.6.8 (3/3)0.6.9 (3/3)
Account Number (truth 000123456789)000123456789 ✓000123456789 ✓
Statement Period (truth 01/01/2024 - 12/31/2024)01/01/2024 - 12/31/2024 ✓January 2024 - December 2024 ✗
OCR text for that lineStatement Period: 01/01/2024 - 12/31/2024**Statement Period:** 01/01/2024 - 12/31/2024

The OCR still contains the literal date range on both sides. What changed is that 0.6.9’s bedrock_llm OCR wraps field labels in markdown bold; given that input the extraction returned a re-worded range instead of copying the value through.

Scope, measured: only the bedrock_llm backend. The same field on the same document reads 01/01/2024 - 12/31/2024 on both releases under textract_tables, textract_layout and bda. Inferred, not proven: that the emphasis markup caused the re-wording — it is the only input difference, but no controlled with/without-bold probe was run. Unverified: whether other scalar fields or documents are affected; this was the only cell/document pair in 171 runs whose scalar accuracy moved.

Also visible on both sides, so not a regression: bedrock_llm transcribes the account number as 00012345678 (11 digits) where the document has 12, and the extractor returned the correct 12-digit value anyway on both releases. That is the known LLM-OCR digit-fidelity hazard, confirmed still open — and the second time this cell has produced a scoring artefact that first looked like a code regression.

What was NOT validated

Section titled “What was NOT validated”

Stated explicitly so this record is not read as broader than it is.

  • The published public artifact. See the warning at the top: every tier ran against a self-published build of the release commit, because idp-main_0.6.9.yaml was not in the public buckets. Tier C and tier D should be re-run against the public URLs after publish.
  • The browser UX review (tier G) — NOT RUN, no browser MCP server available. Nothing here evidences the web UI’s usability or flow behaviour on this release.
  • Real GovCloud. The --govcloud tier ran in a commercial account. See the warning above.
  • The Knowledge Base path in --govcloud — disabled by default in that runner.
  • The seller service’s positive path (a token actually issued and verified). The probe covers refusals only and says so.
  • Cost as a release-over-release delta. 0.6.9 changed the cost instrument; see the A/B section. Single-release cost numbers in the guidance paper are the ones to quote.
  • Accuracy against the published v0.6.8 benchmark numbers. stickler-eval 1.0.0 changed the comparators, so this A/B’s 0.6.8 column is not comparable with the v0.6.8 entry.
  • Documents above 100 rows, and real (non-synthetic) corpora, in the A/B itself — the A/B is corefast by design. Both are covered by the guidance-paper refresh.
  • The release’s new features beyond deployability. Every stack here deployed them; none was driven with feature-specific inputs. That is feature testing, which this record does not claim.
