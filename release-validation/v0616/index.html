Release Validation Record — v0.6.16

Section titled “Release Validation Record — v0.6.16”

Release: v0.6.16 (CHANGELOG.md section [0.6.16]; VERSION at the tag reads 0.6.16) Validated: 2026-11-25 to 2026-11-26, us-west-2 (seller tier us-east-1), commercial partition Commit measured: 689e2b4df, the commit tag v0.6.16 points to. Every offline figure in this record was measured in a dedicated git worktree at that commit, and the build, transform, stack-test and Terraform tiers ran from a second worktree at the same commit, so no other session’s work and no build output could move the tree under the gates. Artifact under test: the published object https://s3.us-west-2.amazonaws.com/aws-ml-blog-us-west-2/artifacts/genai-idp/idp-main_0.6.16.yaml, Description AWS GenAI IDP Accelerator (uksb-r8evguc4p9) (SO9027) (v0.6.16), and the published Terraform module 0.6.16/terraform/idp-terraform-0.6.16.zip beside it. Every CloudFormation stack in tiers B, C and E was created from that template (or, for tier E, from the published v0.6.15 template and then updated to it). Tier D publishes from source at the tag to apply its transforms, and tier A’s build row is a local publish.py --clean-build. Account <ACCOUNT_ID>. PREV = v0.6.15. No validation record was published for v0.6.15, so every “vs PREV” comparison of a recorded figure below is against the v0.6.14 record and spans two releases; the tier E upgrade and the tier F1 A/B measured v0.6.15 directly.

Verdict

Section titled “Verdict”

⚠️ Ship with two product defects to fix in a patch release, both in paths this release adds or changes. The published artifact deploys in all six shipped configurations, both template transforms deploy and process a real document, the CloudFormation upgrade from 0.6.15 completes with no consistent change in extracted values, all four security gates pass, and the 342-run release A/B shows 0 regressions with recall and cell accuracy identical over the same 23,370 compared cells. Advanced-mode extraction is markedly cheaper on this release (Finding 3).

The two defects:

  1. A document sent back from review, or reprocessed from a step, is scored at 100% confidence and completes without review (Finding 1). The tracking table does not persist each page’s OCR-confidence location, so a document rebuilt from it for a rerun reaches assessment with no OCR confidence data. In the browser review a document that had raised six confidence alerts on its first run came back from Send back with every non-empty field at exactly 100.0% and no alert, and completed. Send back and Reprocess-from-a-step are both new in this release, and Review Routing is now on by default for new stacks, so the path that is meant to keep a document under review is the one that releases it.
  2. An in-place Terraform upgrade from 0.6.15 leaves the state machine’s role without one of its inline policies until a second terraform apply (Finding 2). The module names inline policies by position; a renumbered policy is replaced, and the replacement’s late destroy deletes the newly created policy of the same name. The missing grant is lambda:InvokeFunction on the pipeline-hooks dispatcher.

Every tier has a result. Tiers B, D, E, F1, H and J pass. Tier A passes except make test, which fails on five story-catalogue tests that also fail on develop (Finding 4); the same five take the scripts tree out of the coverage ratchet. Tier C passes five of six variants; the tenant-isolation harness passed 22 of 23 checks, and its one failure is the harness’s, which does not accept a document held for review (Finding 5). Tier G passed 15 flows, failed one (Finding 1) and was blocked on one. Tier K failed (Finding 2). Tier I reached no verdict, because the parity tool’s normalisation does not cover most of what it reported (Finding 7). Tier F’s guidance refresh (F2–F4) measured every suite but regenerated the guidance paper only in part; it is carried by #2265.

Several test-tooling defects were found and are recorded separately from the product findings (Findings 4–8). Three of them blocked a tier until patched locally, uncommitted, in the validation worktree; each patch is described where it was used, and none touches shipped code.

Tier C — the six deploy variants

Section titled “Tier C — the six deploy variants”

Every variant self-deployed its own throwaway stack from the published template, ran its assertions, and tore down:

  • hosting-global: a regional REST API serves the web UI.
  • WAF: the WebACL is associated with the API.
  • hosting-private: a private REST API with its resource policy, in the purpose-built stack-test VPC (<VPC_ID>, two private subnets, an execute-api interface endpoint).
  • Jobs API: deployed into the same VPC.
  • tenant isolation: a TenantIsolationMode=Strict stack with the verify-tenant-isolation harness: 22 of 23 checks pass. Every cross-tenant read is refused (HTTP 403), a document outside every tenant’s prefixes is refused at ingest, a cross-tenant prefix mapping and an overlapping tenant are refused, and the access-point uploader cannot write under the other tenant. The failing row and why it is the harness’s is Finding 5. No idp-tiv-uploader-* role was left behind.
  • seller: the unsigned-request and unentitled-account refusals (both 403, with no internal detail leaked), and 15 hostile payloads refused with no 5xx, in us-east-1.

As in every earlier record, the seller tier asserts refusals only; no token was issued and verified, and its teardown leaves the signing KMS key scheduled for deletion on a 7-day window. After the VPC tiers, four orphaned Lambda network interfaces were swept from the stack-test VPC, two from the hosting-private stack and two from the Jobs API stack, after confirming both stacks were deleted.

Tier D — template transforms, and the limits of a commercial-region run

Section titled “Tier D — template transforms, and the limits of a commercial-region run”

Both transforms deployed from source at the tag and processed samples/lending_package.pdf end to end: the expected address string was found, 17 of 22 fields were populated and the document was classified Payslip, the same as at v0.6.14.

  • --headless: the transform removed 116 of 378 resources (UI, Cognito and CloudFront) and 16 of 59 conditions, removed the six policy statements that referenced removed resources, and disabled the Knowledge Base. 257 resources deployed.
  • --govcloud: the result contains no AWS::CloudFront::* or AWS::Lambda::Url resource, the LWA chat-stream family is removed (#677), and the UI is retained and hosted on API Gateway. 341 resources deployed.

⚠️ The --govcloud result is a commercial-partition result. It proves the CloudFront-free, API-Gateway-hosted template deploys and processes documents. It proves nothing about partition ARNs, GovCloud model availability or the BDA project rejection (#676/#677 were invisible to a commercial run). The Knowledge Base was disabled in the --govcloud run, which is the runner’s default.

The transform runner turns Review Routing off in the stack’s default profile before its document test, because v0.6.16 turns it on for new stacks and a held document would never complete. So neither transform run exercised the new default (Finding 9).

Tier E — in-place upgrade, and what it did to extracted values

Section titled “Tier E — in-place upgrade, and what it did to extracted values”

A fresh stack, IDPUpg0615to0616, was created from the published v0.6.15 template and processed three copies of lending_package.pdf. It was then updated to the published v0.6.16 template with UsePreviousValue=true on all 96 existing parameters, and processed the same three copies again.

  • The update started at 22:26 UTC on 2026-11-25 and reached UPDATE_COMPLETE at 22:51 UTC, with no failed event and no rollback. The UpdateConfiguration custom resource’s log holds no error, warning or migration line.
  • The parameter set gained three entries, each with a default that keeps the existing behaviour: CustomerManagedKmsKeyArn, ManageApiGatewayAccountSettings and TenantSelection. Nothing was removed or newly required.
  • The upgraded stack did not turn Review Routing on: all three post-upgrade documents completed with none awaiting review. The new default applies to new stacks only, as the CHANGELOG says.

All six runs found the same six sections with the same classes (Payslip, US-drivers-licenses, Bank-checks, Bank-Statement, W2, Homeowners-Insurance-Application). Comparing field values pairwise, about 170 fields per run:

No field differed in all nine pre/post pairs, so the upgrade changed no extracted value consistently: the pre/post differences are the size of the same-version variation on this document.

The first run crashed before comparing anything (Finding 7). The tool’s gate therefore fails. No difference was shown to be a configuration the two deployments actually store differently, but the 166 were not triaged one by one, so that is not established either. By property path:

1. A document sent back from review, or reprocessed from a step, is scored at 100% confidence and completes unreviewed (product defect, this release)

Section titled “1. A document sent back from review, or reprocessed from a step, is scored at 100% confidence and completes unreviewed (product defect, this release)”

Measured in the browser (tier G). lending_package.pdf under a profile with Review Routing on raised six confidence alerts on its first run and was held in the Default queue. As Reviewer, the document was claimed, one field corrected, and Send back for reprocessing chosen; separately, as Admin, Reprocess › Start at Assessment was run on the same document. Both runs ended COMPLETED with 0 alerts and Review Status N/A. In section 1 every non-empty field scored exactly 100.0% and every empty field 0.0%, after both runs; a normal first run of the same file scored 23 fields at 100.0%, 9 at 99.0% and the rest between 55% and 94%. The Processing Flow shows the assessment step succeeding on every section, in 2–7 seconds each.

Measured in the logs. The assessment function logged Failed to generate text confidence data for page N: No module named 'pypdfium2' exactly six times — once per page — in each of the two reprocessing windows, and never in the document’s first run or in two windows in which only the benchmark battery was running. The log lines do not name the document.

Read in the code at the tag. idp_common/dynamodb/service.py writes each page of the tracking record with ImageUri, TextUri and OcrPageDataUri but not TextConfidenceUri, while the reader that rebuilds a Document from the record reads TextConfidenceUri (always absent) and sets the page’s raw text location to TextUri, the parsed text. The reprocess resolver rebuilds the document through that reader. AssessmentService._get_text_confidence_data therefore finds no confidence file and falls back to regenerating it through OcrService, an import that needs pypdfium2, which the assessment function’s [assessment] extra does not install; the fallback returns an empty confidence block. Even with the module present, the fallback would be handed parsed text rather than the raw OCR response.

Inferred, not traced: that an assessment prompt with an empty OCR-confidence block is what yields the uniform 100% scores.

Why it matters. Send back exists to put a document back under review, and the dialog says the document “can return to a review queue afterwards”. Instead it comes back with perfect scores and completes, and nothing on the page says assessment had no data. Review Routing is on by default for new stacks in this release, so this is the default review path. Filed as #2258.

2. An in-place Terraform upgrade from 0.6.15 drops one inline policy from the state machine’s role (product defect, Terraform module)

Section titled “2. An in-place Terraform upgrade from 0.6.15 drops one inline policy from the state machine’s role (product defect, Terraform module)”

Measured (tier K). After terraform apply of the 0.6.16 module over a 0.6.15 deployment, the next plan wanted to create module.idp.module.patternstack.aws_iam_role_policy.document_processing_state_machine_role_15, named DocumentProcessingStateMachineRolePolicy15, granting lambda:InvokeFunction on the pipeline-hooks dispatcher function.

Read in the apply log. The upgrade plan renamed the existing ..._role_14 policy from DocumentProcessingStateMachineRolePolicy15 to ...Policy14, which forces replacement, and added ..._role_15 under the name ...Policy15. The apply created ..._role_15 first and destroyed the deposed ..._role_14 object afterwards. An inline policy is identified by role and name, so destroying the deposed object deleted the policy ..._role_15 had just created. The role then lacks the grant until a second apply recreates it.

Inferred, not measured: what this does to processing between the two applies. A workflow that calls the pipeline-hooks dispatcher would be refused; the tier K driver stops at the non-converging plan, so no document was processed on the upgraded deployment. The same position numbering applies to every role with several inline policies, so any release that inserts a policy ahead of others can do this to other roles. Filed as #2259.

3. Advanced-mode extraction costs about half as much on 100-row documents (improvement, cause inferred)

Section titled “3. Advanced-mode extraction costs about half as much on 100-row documents (improvement, cause inferred)”

In the F1 A/B, the configurations were byte-identical on both sides, so the change is the code’s. Every advanced-mode cell cost 45–52% less on the two 100-row documents, with per-run ranges that do not overlap: core-tt-adv-sep on longdesc_100 cost $0.248–$0.288 a run on v0.6.15 and $0.113–$0.153 on v0.6.16; core-bda-adv-sep on small_narrow $0.173–$0.207 and $0.089–$0.121. The single-page tiny_form cost the same on both. Recall and cell accuracy were identical.

The CHANGELOG’s fix “Agentic table extraction no longer counts a table’s header rows as data on some runs” also changed the table tool to parse the section’s own OCR text, so the agent no longer spends output tokens reproducing the table. That is the likely cause; the token split per call was not examined. aggregate.py --compare labels these cells inconclusive (Finding 8 explains why it cannot see a consistent per-document change).
