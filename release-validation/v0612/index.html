Verdict

Section titled “Verdict”

✅ Ship, with four product findings a maintainer should read before the next release — the published artifact deploys in all five shipped configurations, both template transforms deploy and process a real document, the upgrade from 0.6.11 applies without rollback, and the 342-run release A/B shows 0 regressions and 0 improvements.

7 of 8 tiers ran and passed. Tier G (browser UX) is the only tier NOT RUN — no Chrome or Chromium on the validation host, nothing on 127.0.0.1:9222, and the browsermcp MCP server disconnected mid-session rather than being absent. Tier H passed on one of its two suites: idp_common is 19 of 19, while idp_cli selected 0 of 1,494 tests, which is an empty suite rather than a pass (Finding 16).

Tier F is complete. F1, the release A/B, plus the F2–F4 guidance refresh: 29 scored result sets — 3,248 scored rows from 2,488 runs, $1,970.55 — measured 2026-10-17 23:37 → 2026-10-18 06:22 UTC in one session on the upgraded reference stack, with all 28 lanes exiting at their planned run count. The configuration matrix, both reference corpora, the scaling study, the cost-variance runs, the two standing list-loss hazards, all nine extraction-model arms, the classification and confidence sweeps and all three premium head-to-heads ran. Five of §7’s knob A/Bs and §2c’s second model arm did not, and are named in Finding 7.

The refresh produced the most consequential product finding in this record, and it is not a regression in this release. 17 of the 2,488 runs (0.68%) lost a document whose extraction had already succeeded: in simple mode with assessment: separate, the separate confidence pass exhausts its Lambda’s memory or its 900 s wall clock after every row has been extracted, validated, scored and persisted, and the whole document is then discarded (#1488). This is the same defect shape as #1363, which this release fixed for the integrated confidence path only. It is a configuration hazard rather than a blocker — advanced mode completed every size in the scaling grid, and the integrated path is clean at 8/8 — but it is marginal rather than rare at the sizes a customer is most likely to hit. See Finding 3.

The tier-E finding is the one the aggregate numbers hide. Diffing the document processed before and after the upgrade gives 38 differing leaves of 1,852, while two same-version control runs differ from each other on 56 of 1,860 — so by totals alone the upgrade moved less than the model’s own run-to-run variation, and “no change” is the conclusion the numbers invite. Two groups of differences are nonetheless identical across all three 0.6.12 runs and differ from 0.6.11, which is a version effect rather than noise: six Payslip statutory-tax amounts changed sign, and the driver’s-licence section populates one field fewer. Neither is in the CHANGELOG. See Finding 1.

Four results are improvements on 0.6.11, three of them closing items that record raised. Both standing list-loss hazards — intconf (integrated confidence with simple extraction) and advverify — measure clean at 8/8 with recall 1.000 and 100 of 100 rows on every run, which the v0.6.11 record could not say either way; the curated security snapshot now reads PASS on all four gates where 0.6.11 published SRT — FAIL ❌; the idp_common integration suite went from 1 failure of 19 to 19 of 19; and the coverage registry grew from 9 trees to 11, which moved the lowest-covered tree.

29 scored result sets, 3,248 scored rows from 2,488 runs, $1,970.55, run as 28 lanes (6 concurrent, --max-inflight 4) between 2026-10-17 23:37 and 2026-10-18 06:22 UTC on the same upgraded reference stack every other live tier used, at v0.6.12, priced from config_library/pricing.yaml at sha256 44a79aa06c15…. The per-section tables are in docs/benchmarking/config-guidance.md and the A/B entry is docs/benchmarking/releases/v0.6.12.md, both carried by the sibling benchmark pull request; what follows is the part that belongs to this record.

Why the 23 unsuccessful runs failed

Section titled “Why the 23 unsuccessful runs failed”

0.92% of 2,488 runs did not succeed. A single percentage is the wrong summary, because the 23 behind it divide into a defect, a correct refusal, and an artefact of the measuring harness, and only the first is a product problem:

runssharewhereattributionwhat it means
170.68%large_narrow.pdf ×15, scale_1200 ×1, scale_1600 ×115 Runtime.OutOfMemory, 2 Sandbox.Timedout, all in AssessmentStep after ExtractionStep had succeededthe #1488 defect: a complete extraction, and the document discarded. Every one scores completeness_recall 1.000 with every row extracted — Finding 3
50.20%scale_3200.pdf — 1 in scaling, 4 in astracapExtractionInputTooLargeby design and correct: a named, up-front refusal with nothing attempted. In astracap, the 66-page ceiling study, this is the measured outcome rather than a failure of it
10.04%coresynth__extraction-model-opus5 / core-llm-simple-sep / large_narrownot a product failure — a harness polling timeoutscored EXTRACTING, rows_extracted 0, wall_s None, while the tracking table says that document reached COMPLETED / SUCCEEDED. The harness stopped waiting and recorded a non-success for a document that then succeeded

Separately, 4 of the 760 (cell, corpus, document) triples on the reference corpora produced no score at all — SCORE_ERROR on ocr_bench in four different cells. That is a scoring failure rather than a processing one: those documents processed and the scorer returned no figure for them, which is why four cells read 19 of 20 scored rather than 20. It is counted in neither the 23 above nor the accuracy figures below.

⚠️ The memory failure is marginal, not deterministic, which is what makes it hard to see. large_narrow.pdf ran 318 executions across the refresh: 303 succeeded and 15 ran out of memory, about 5%. So it is a memory-pressure boundary at that document’s size and shape, not a size threshold — an 800-row document with a plainer layout completes every time, and a customer hitting this sees intermittent loss rather than a reproducible limit.

2. Published completeness figures for the bedrock_llm OCR backend were wrong for nine releases (benchmark harness, pre-existing)

Section titled “2. Published completeness figures for the bedrock_llm OCR backend were wrong for nine releases (benchmark harness, pre-existing)”

The benchmark harness does not count rows. benchmarks/harness/analyze.py sets rows_extracted to len(set(int(m) for m in SEQ.findall(blob))) against SEQ = re.compile(r"SEQ(\d{5})"), so it counts distinct recognisable five-digit SEQ identifiers in the result. The bedrock_llm OCR backend is independently known to insert a digit into fixed-width zero-padded identifiers, page-scoped rather than uniform — SEQ00042 becomes SEQ000042, which the pattern reads as int("00004") and collapses onto row 4. The distinct count falls and no row is missing.

So every completeness figure this arm has published is a reading of identifier fidelity, not of row loss. 105 runs across 16 (cell, document, shape) groups, from v0.5.16 to v0.6.12, all correct to completeness_recall 1.000. The arm was published between 0.5644 and 0.9796 mean recall over that span, correcting to 1.0000 on 31 of the 40 affected (grid, cell) means; the worst figure ever published for it, v0.6.6/corefast at 0.5644, was a complete extraction.

It reached cell_accuracy as well, and worse. The value join keys on the same identifier, so a perturbed id pairs one row’s values against another row’s truth and reports a value error that is an artefact of the join. cells_compared is exactly 2 × rows_extracted on all 90 affected runs, so accuracy was computed over 92.3% of the rows actually returned while being published as if over all of them.

Three independent confirmations rather than one, because a metric correcting itself upward is the direction that deserves the most scepticism:

  • Reproduced by probe. A blob containing every row, with ids corrupted at the observed rate, recovers all seven committed figure-shapes byte for byte.
  • An identifier-free field disagrees with it. conf_rows_expected is derived from the extracted list’s own length and uses no identifier at all. It reads the full truth row count on all 75 affected runs that record it — med_narrow carries rows_extracted: 362 beside conf_rows_expected: 400, conf_rows_scored: 400.
  • The two readings are separable in data the analysis already had. Genuine tail truncation gives dups: 0 and a truncation_prefix equal to the kept count; scattered id corruption gives a large dups and a truncation_prefix near zero. Every affected run has the second signature.

⚠️ The standing narrative that this backend is “the noisiest of the nineteen” was therefore an instrument reading, and every release entry that treated its movement as a product signal was reporting the same defect. The v0.6.6 entry had already root-caused the behaviour to identifier corruption — the metric was simply never corrected for it, which is how it resurfaced as a fresh finding in each release since, including as the one “moved” cell of this release’s own A/B. A defect that is diagnosed and not fixed in the instrument is one the next pass pays for again.

One residual, stated rather than smoothed: core-tt-adv-sep / scale_1600 returned 1,698 identifiers for 1,600 truth rows, so it carries genuine duplication as well and its corrected figure is an upper bound. The other 104 affected runs returned exactly the truth count of identifiers.

Tracked as #1500; the fix canonicalises each identifier against the truth id set and records rows_id_repaired, so a future grid cannot report this as row loss.

3. The separate confidence step discards fully extracted large documents (product defect, pre-existing)

Section titled “3. The separate confidence step discards fully extracted large documents (product defect, pre-existing)”

17 of the refresh’s 2,488 runs (0.68%) threw away a document whose extraction had already succeeded. Fifteen were Runtime.OutOfMemory and two Sandbox.Timedout, and all seventeen failed in the same place. Step Functions history for one of each — large_narrow for the memory failure, scale_1200 for the timeout — shows an identical sequence: ExtractionStep exits successfully, PostExtractionHook succeeds, AssessmentStep is entered, its Lambda fails (once retried), then MapIterationFailed → MapStateFailed → ExecutionFailed. So in simple mode with assessment: separate, the separate confidence pass is a single point of failure on large documents, and it fails after every row has been extracted, validated, confidence-scored and persisted to S3. Two different resource limits — the 900 s Lambda wall clock and Lambda memory — in one step. Filed as #1488.

This is the same defect shape as #1363, which this release fixed for the integrated confidence path only. The separate path still discards the document. The 25-row default confidence batch cap is part of the mechanism: 1,600 rows is roughly 64 serial scoring calls inside one 900 s invocation.

⚠️ The failure is invisible in the accuracy metrics, which is the part to carry forward. Every one of the seventeen scores completeness_recall 1.000 with every row present, because the harness reads extraction output from S3 and that output is complete. A table built from recall rather than from status reports this configuration as flawless at 1,600 rows.

It is not a row threshold, and it is not deterministic. scale_800 (800 rows) completes in simple mode, while large_narrow — also 800 rows, but 17 pages and about 203,000 estimated input tokens — ran 318 executions across the refresh and lost 15 of them, about 5%, in three different cells. So the boundary is a resource limit at a particular size and shape, and a customer meeting it sees intermittent loss rather than a reproducible ceiling. It sits at exactly the document sizes a customer is most likely to hit.

Two configurations measured clean against it on this build, which is the practical remedy until the defect is fixed: advanced mode completed every size in the scaling grid including 3,200 rows, and the integrated confidence path (intconf) is 8/8 with recall 1.000 and 100 of 100 rows on every run.

5. A list with no OCR evidence is reported as complete instead of unverifiable (product defect, pre-existing)

Section titled “5. A list with no OCR evidence is reported as complete instead of unverifiable (product defect, pre-existing)”

The six completeness signals that exist to make a short extraction visible — extraction_rows_below_ocr_estimate, extraction_partial_row_shortfall, extraction_output_truncated, extraction_incomplete, extraction_validation_failed, extraction_sparse — fire on nearly every lossy run on three OCR backends and on about half of them on bedrock_llm. Taking a lossy run to be one whose extracted rows are under 95% of ground truth, over 607 scored runs: 48 of 49 flagged on textract_tables, 9 of 9 on bda, 8 of 8 on textract_layout, and 9 of 17 on bedrock_llm.

⚠️ Seven of those eight silent runs lost no rows — they are Finding 2’s identifier corruption, which is why that finding is ordered above this one. Of the eight, seven carry dups of 38–45 with truncation_prefix of 5–86 (the corruption signature) and one, longdesc_100 on the nova_lite arm, carries dups: 0 with prefix: 64 against 66 of 100 rows, which is genuine truncation that reported nothing. A detection rate is the wrong instrument for this question and it is quoted here only because it is what first exposed the mechanism; the finding that survives is structural rather than statistical.

The structural half is measured, on a 3-property item schema. _expected_rows_for_width sums rows only from OCR tables whose column count equals the item schema’s property count, and evidence reaches zero by two distinct routes, not one:

Rendering_ocr_tables_expected_rows_for_width(3, …)
textractor TABLES form, 3 columns[{'rows': 41, 'cols': 3}]41
GitHub-legal pipe table, no leading pipes[]0
same table with a 4th column the schema lacks[{'rows': 41, 'cols': 4}]0
same table with an added row-number column[{'rows': 41, 'cols': 4}]0
rendered as a bulleted list[]0

For the two four-column rows the width match is what rejects it — a table is found, and _expected_rows_for_width(4, …) returns 41 against the same text. For the no-leading-pipe and bulleted renderings _ocr_tables recognises no table at all, upstream of any width question. Both land in the same place, and at zero evidence expected < _OCR_ROW_ESTIMATE_MIN holds for every extracted count and every document size — so the two OCR-grounded checks are not merely quiet, they are unreachable. bedrock_llm renders its own Markdown rather than emitting Textract table blocks, which is why it is the backend most exposed to this.

What is not established is that this is what happened on the one genuinely truncated run. That needs _ocr_tables output captured from it; the stacks are gone and no OCR page artifact for those runs survives, so the link between the measured mechanism and the observed silence is unverified.

Tracked as #1489. The remedy taken is the one that is correct under either reading of the detection rate: report explicitly when a list came back with no usable evidence, so “could not check” stops being indistinguishable from “checked and found complete” — which is what a user currently sees. The exact-width match is deliberately left alone, including as a fallback reachable only when the exact-width evidence is empty: “empty” is the ordinary state for an item schema with a derived property, so such a fallback would be reachable on textract_tables too and would let a two-column key/value block report a shortfall against a three-column list.

lib/idp_sdk/tests/unit/test_multi_doc_discovery_source_zip.py writes a ~7 MB .aws-sam/multi-doc-discovery-source.zip into the repository root while it runs. Any make srt-scan ordered after make test therefore reports 1 .aws-sam build directory present and drops into its degraded mode, emitting phantom LOCAL-ONLY findings and risking a checkov crash on the largest templates.

The scan segregated them correctly, so the gate verdict held — but the preflight rule in .claude/skills/release-validation.md is “scan before publish.py”, and that is not sufficient: it has to be before make test too. Either the test should write to a temporary directory, or the preflight rule should say so.

Tracked as #1491. The remedy taken is the first option, plus a suite-wide control: the test writes to a temporary checkout and asserts the real tree is unchanged, and a shared guard reuses the SRT scanner’s own **/.aws-sam predicate so any suite that starts writing build output into the tree fails rather than being discovered by the next scan’s degraded mode.
