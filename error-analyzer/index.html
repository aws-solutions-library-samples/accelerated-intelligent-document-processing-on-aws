Error Analyzer (Troubleshooting Tool) - PREVIEW

Error Analyzer (Troubleshooting Tool) - PREVIEW

Section titled “Error Analyzer (Troubleshooting Tool) - PREVIEW”

Overview

Section titled “Overview”

The Error Analyzer is an intelligent AI-powered troubleshooting tool that helps diagnose and resolve document processing failures in the GenAI IDP Accelerator. It uses a configurable Amazon Bedrock model — Claude Sonnet 4.6 by default — with the Strands agent framework to automatically analyze CloudWatch logs, DynamoDB tracking data, Step Functions execution history and X-Ray traces to identify root causes and provide actionable recommendations.

This tool is not yet mature - we expect to refine and improve the capabilities in successive releases. Try it, and give us feedback via GitHub Issues.

Key Capabilities

Section titled “Key Capabilities”
  • Automatic Failure Diagnosis: AI agent automatically investigates document processing failures
  • Intelligent Tool Selection: Distinguishes between document-specific and system-wide analysis and picks its own tools accordingly
  • Multi-Source Analysis: Correlates data from CloudWatch Logs, DynamoDB, Step Functions and X-Ray
  • Contextual Recommendations: Provides specific guidance for configuration, operational, or code issues
  • Real-Time Updates: Live job status with progress tracking and resumption capability
  • Evidence-Based Analysis: Shows detailed log evidence supporting diagnostic conclusions

When to Use the Error Analyzer

Section titled “When to Use the Error Analyzer”
  • Document Processing Failures: Investigate why a specific document failed to process
  • Recurring Error Patterns: Identify systemic issues affecting multiple documents
  • Performance Investigation: Analyze timeout errors and processing bottlenecks
  • System Health Checks: Review recent errors across the entire system
  • Troubleshooting Support: Generate detailed error reports for support escalation

Tool Ecosystem

Section titled “Tool Ecosystem”

The Error Analyzer uses a set of specialized tools organized in a modular architecture. These include CloudWatch log search, DynamoDB document-record lookup, Step Functions execution analysis, X-Ray tracing, and fetch_pipeline_configuration — which returns the Bedrock model ID configured for each pipeline stage of a document’s config version. The last is what lets the agent name the exact model behind a retired/unavailable-model error (the Bedrock error text itself does not name the model):

The agent is a Strands agent constructed in lib/idp_common_pkg/idp_common/agents/error_analyzer/agent.py, which registers these tools and lets the model choose among them directly. There is no dispatching router tool between the model and the tools.

Tool Descriptions:

  1. search_cloudwatch_logs (CloudWatch)

    • Searches log groups for errors and failures
    • Given a document_id, performs a targeted search using the document’s processing timestamps and Lambda request IDs; without one, searches recent logs across the stack
    • Arguments: document_id, filter_pattern, hours_back, max_log_events, max_log_groups

  2. search_performance_issues (CloudWatch)

    • Searches for throttling, timeout, capacity and concurrency problems
    • Arguments: issue_type, hours_back, max_log_events

  3. fetch_document_record (DynamoDB)

    • Retrieves the complete tracking-table record for one document, including status, timestamps, ConfigVersion and execution information
    • Argument: object_key

  4. fetch_recent_records (DynamoDB)

    • Fetches records for documents processed within a time window, using time-based partition scanning
    • Arguments: date, hours_back, limit

  5. fetch_pipeline_configuration (Configuration)

    • Returns the Bedrock model ID configured for each pipeline stage of a configuration version, plus whether summarization is enabled
    • This is what lets the agent name the exact model behind a retired-or-unavailable-model error, since the Bedrock error text does not name the model
    • Argument: config_version (empty reads the active version)

  6. retrieve_document_context (Lambda)

    • Invokes the lookup Lambda named by LOOKUP_FUNCTION_NAME to gather execution context, timing and Step Functions details
    • Extracts Lambda request IDs for correlating CloudWatch log searches
    • Argument: document_id

  7. analyze_workflow_execution (Step Functions)

    • Retrieves execution history, analyzes state transitions and identifies the failure point in the workflow
    • Argument: document_id

  8. analyze_document_trace (X-Ray)

    • Analyzes the X-Ray trace for one document for errors, bottlenecks and service timeline
    • Argument: document_id

  9. analyze_system_performance (X-Ray)

    • Analyzes stack-specific traces first, then general infrastructure, to find system-wide performance degradation
    • Arguments: stack_name, hours_back

Accessing the Troubleshoot Modal

Section titled “Accessing the Troubleshoot Modal”
  1. Open the document: In the GenAI IDP Web UI’s document list, open the document to analyze (typically one with FAILED status) to reach its document page
  2. Click Troubleshoot: Choose Troubleshoot in the document page’s action bar to open the TroubleshootModal. It is offered to the Admin, Author and Viewer roles
  3. Automatic Analysis: Agent immediately begins analyzing the failure

Understanding the Interface

Section titled “Understanding the Interface”

The TroubleshootModal displays:

  • Document Information: Shows the ObjectKey being analyzed
  • Status Indicator:
    • PENDING: Job submitted, waiting to start
    • PROCESSING: Agent actively analyzing with real-time messages
    • COMPLETED: Analysis finished, results available
    • FAILED: Analysis encountered an error
  • Agent Messages: Live progress updates during processing
  • Results Display: Formatted analysis with collapsible sections
  • Last result: Reopening Troubleshoot on the same document shows the last analysis (or the one still running); Run again starts a new analysis

Reporting an Issue from the Modal

Section titled “Reporting an Issue from the Modal”

When the analysis job reaches a terminal state (COMPLETED or FAILED), the Troubleshoot modal footer offers two additional actions:

  • Report this issue on GitHub — opens a pre-filled GitHub bug-report form in a new tab, populated with the deployment environment (Region, Processing Mode, Version/Build/Stack), the document context (object key, status, config version, execution ARN, and any job error), and the agent’s Markdown findings.
  • Copy full details — copies the complete environment + findings text to your clipboard, for pasting content that the pre-filled URL can’t carry (the issue link length-caps the findings; the full transcript is not embedded in the URL).

Privacy note: GitHub issues on the public repository are visible to everyone, and the findings can quote OCR’d document content. Nothing is submitted automatically — review the pre-filled form and redact any sensitive data before submitting. See Feedback & Issue Reporting.

The modal stays open until you press Close (an outside click or Esc no longer dismisses it, so a running analysis — which can take ~30 seconds — is not interrupted). Use Minimize to collapse it to a restore chip while the analysis finishes in the background. When the Error Analyzer is run from the Agent Companion Chat instead, a Create GitHub issue button appears under the answer with the same bug/feature options.

Section titled “Agent Configuration in template.yaml”

The Error Analyzer’s editable settings are declared in the ConfigSchema of patterns/unified/template.yaml, under the agents section. The schema is what drives the UI Configuration panel, and it declares three properties:

The enum is long — it carries us., global. and eu. inference-profile variants of each supported model — so read it from the template rather than from a list here. Two things about it are worth knowing before you pick a value: Claude Haiku models are not in it, and a value outside the enum is rejected, so the model must support tool use.

There is no parameters object in the schema. The agents.error_analyzer.parameters block described below is accepted by the configuration model and can be set in a configuration YAML, but it is not surfaced in the UI Configuration panel.

Configuration Parameters

Section titled “Configuration Parameters”

model_id

Section titled “model_id”

Purpose: Selects the Bedrock model for error analysis

Recommended: us.anthropic.claude-sonnet-4-6

  • Superior reasoning for complex error diagnosis
  • Better structured output formatting
  • More accurate root cause identification

Alternative Options:

  • us.amazon.nova-pro-v1:0: AWS-native option
  • us.anthropic.claude-sonnet-4-5-20250929-v1:0: Good balance of cost and capability, but AWS has moved it to legacy (end of life 2027-04-08) and it takes no further Service Quota increases

Claude Haiku models are not selectable for this agent. The enum does not include them, so a configuration naming one is rejected.

lookback_hours

Section titled “lookback_hours”

Purpose: The default search window, in hours, for the two CloudWatch log tools.

Default: 24 hours

search_cloudwatch_logs (in its system-wide mode, without a document_id) and search_performance_issues each take an hours_back argument. When the model omits it, the tool searches the last lookback_hours hours. When the model passes it — because the query asked for a window, as in “errors in the last hour” or “what failed yesterday” — the model’s value is used instead. Both tools tell the model to omit the argument unless the user asked for a window. A configured value above 168 hours, the maximum the tools advertise, is treated as 168.

Three things lookback_hours does not control. A document-specific search_cloudwatch_logs call searches a window derived from the document’s tracking record, whatever this is set to: a few minutes either side of the completion time for a failed document, the processing run from start to completion for one that finished, the 30 minutes before completion for one that finished with no recorded start time, and the last 30 minutes for one still in progress or with no completion time. fetch_recent_records counts its hours_back back from the end of the requested date rather than from now, and keeps its own 24-hour default. analyze_system_performance keeps its own 1-hour default, because the X-Ray service graph it reads is bounded separately (see xray_analysis_hours below).

system_prompt

Section titled “system_prompt”

Purpose: Defines agent behavior and response formatting

The shipped default is in lib/idp_common_pkg/idp_common/config/system_defaults/base-agents.yaml, under agents.error_analyzer.system_prompt. It is long, and it is the authoritative copy — read it there rather than from an excerpt, which goes stale silently. It covers:

  • the pipeline stages and the AWS services behind each, so the agent can map a failing stage to the log group that holds its errors
  • an investigation workflow and a “5 whys” instruction to keep the agent from stopping at the first error message it finds
  • the distinction between a stage Lambda’s generic wrapper message and the underlying exception, which is the single most common way an analysis goes shallow
  • a tool-usage section that names each of the agent’s tools by its registered name (listed under Tool Ecosystem), says when to use it and which arguments to pass, split by document-specific, system-wide, workflow, configuration and X-Ray questions
  • a catalogue of recurring error patterns (throttling, timeout, configuration, permissions, input quality, BDA-specific, Bedrock model errors, and retired or unavailable models) with the likely cause and what to check for each
  • the required output format: a ## Root Cause section opening with a confidence rating, a ## Recommendations section capped at three items, and a collapsible HTML <details> Evidence section
  • recommendation guidelines that differ by issue class — for a code defect the agent is told not to propose code changes, because a user cannot change Lambda code, and to describe the error well enough to report it instead

If you replace the prompt, keep the three-section output format: the UI parses it to render the result, and the Evidence panel depends on the <details> block.

Name tools by the names the agent registers, which are the function names in idp_common/agents/error_analyzer/tools/. The model is given only those tools, so a prompt that directs it to any other name sends it after a tool it does not have. tests/unit/agents/error_analyzer/test_prompt_tool_names.py in the idp_common package checks every shipped copy of the prompt against the registered set in both directions.

⚠️ A configuration profile you created keeps the prompt it was saved with. Every profile is saved as a full, independent snapshot, and an upgrade re-seeds only default and the stack-managed profiles. So a profile created before this release carries the earlier prompt whether or not anyone edited it, and that prompt directs the model to tools that never existed (cloudwatch_document_logs, dynamodb_status, cloudwatch_logs, dynamodb_query, stepfunction_details, lambda_lookup, xray_trace, xray_performance_analysis). To update one, open the profile in the Configuration panel, use Restore default on the Error Analysis Agent’s system_prompt field and save. If the prompt was customised on purpose, rewrite its tool-usage section against the registered tools instead, so the customisation is kept.

Advanced parameters (config-file only)

Section titled “Advanced parameters (config-file only)”

agents.error_analyzer.parameters is accepted by the configuration model but is absent from the template’s ConfigSchema, so it can only be set in a configuration YAML — it does not appear in the UI Configuration panel. The full field list is ErrorAnalyzerParameters in lib/idp_common_pkg/idp_common/config/models.py.

These take effect as written:

FieldDefaultEffect
max_log_message_length400Individual log messages longer than this are truncated
settings_cache_ttl_seconds300TTL for the SSM settings cache
max_stepfunction_timeline_events50Timeline events included from an execution history
max_stepfunction_error_length400Truncation length for a Step Functions error message
max_stepfunction_history_pages10Pages of execution history fetched
xray_slow_segment_threshold_ms5000Segment duration treated as slow
xray_response_time_threshold_ms10000Response time treated as slow
xray_analysis_hours3Window for X-Ray service-graph analysis (max 6)
xray_error_rate_threshold0.05Error rate treated as significant
max_log_groups20Log groups search_cloudwatch_logs searches when the model passes no max_log_groups; a value the model passes is used instead. A configured value above 50, the maximum the tool advertises, is treated as 50
max_log_events10Events per log group that search_cloudwatch_logs and search_performance_issues return when the model passes no max_log_events, or passes a count below 1, which CloudWatch Logs would reject; a count of 1 or more that the model passes is used instead. A configured value above 50, the maximum the tools advertise, is treated as 50

⚠️ A configuration saved before configuration format 0.10 that stores max_log_events: 5 is read as 10. Until format 0.10 the tools ignored this setting and returned up to 10 events per log group, while the setting’s own default was 5, and every saved configuration profile and revision stores a full snapshot, so they all store that 5. Read as written, each would drop to 5 events per log group. The configuration migration therefore reads a stored 5 in a configuration stamped older than 0.10 (or carrying no config_format_version at all) as 10, so the number of events a deployment receives is unchanged by the upgrade. The stored data cannot tell the untouched default from a 5 someone chose, so a deliberate 5 is read as 10 too. To use 5, set it again after upgrading, either in the JSON or YAML view of the Configuration editor or with idp-cli config-upload. A value you save that way is used as written, unless what you save was written for an earlier format: a file that carries a config_format_version older than 0.10 (or one that cannot be read), or that carries a setting an earlier format used, has a 5 read as 10. A file downloaded from an earlier release is one of those (releases before v0.6 wrote no stamp, but their downloads carry the retired assessment block), so set its stamp to "0.10", or upload it and then set 5 again. The stack’s CustomConfigPath file is also read as older than 0.10 when it carries no stamp, so add config_format_version: "0.10" to it to keep a 5; idp-cli config-validate reads an unstamped file the same way, so its preview shows 10 for a 5 that config-upload would keep. Any other stored value, and any value in a configuration stamped 0.10 or later, is used as written. The rewrite is applied as the configuration is read; a pinned revision’s stored body is never rewritten.

time_range_hours_default is an unused alias. The configuration model declares and validates it, so saved configurations that carry it still load, but nothing in the agent or its tools reads it. Set the default window with lookback_hours, described above.

Intelligent Query Classification

Section titled “Intelligent Query Classification”

Nothing parses the query before the model sees it. The model reads it and decides which tools to call and what to pass them, so the split between document-specific and system-wide analysis is a consequence of whether it supplies a document_id:

search_cloudwatch_logs then branches on that argument: with a document_id it looks up the document’s processing window and Lambda request IDs and searches only the relevant log groups; without one it searches recent logs across the stack. Writing document: in front of a filename is a convention that helps the model pick the filename out of the sentence — it is not a required syntax, and a query that names a file plainly works too.

Multi-Pattern Error Detection

Section titled “Multi-Pattern Error Detection”

System-wide analysis uses prioritized pattern matching:

Prioritization Strategy:

  1. ERROR: Highest priority, captures 5 events
  2. Exception: Important errors, captures 3 events
  3. ValidationException: Specific validation issues, 2 events
  4. Failed: General failures, 2 events
  5. Timeout: Performance issues, 1 event

Context Management:

  • Respects max_log_events parameter as total limit
  • Uses adaptive sampling across patterns
  • Deduplicates similar error messages
  • Truncates long messages at 200 characters

Error Categorization

Section titled “Error Categorization”

System-wide analysis categorizes errors for pattern identification:

Category Definitions:

  1. validation_errors

    • Keywords: “validation”, “invalid”
    • Indicates data quality or format issues
    • Often fixable through configuration

  2. processing_errors

    • Keywords: “exception”, “error”
    • Core processing failures
    • May require code fixes

  3. timeout_errors

    • Keywords: “timeout”
    • Performance/resource issues
    • Adjustable through memory/timeout settings

  4. access_errors

    • Keywords: “access”, “denied”
    • Permission problems
    • Requires IAM policy updates

  5. system_errors

    • Catch-all for other errors
    • Infrastructure or service issues

Job Resumption

Section titled “Job Resumption”

The Web UI maintains job state for seamless resumption:

How It Works:

  1. Job Creation: Modal creates job with unique jobId
  2. Parent Tracking: Component stores job state in parent
  3. Modal Close: Job continues running in background
  4. Modal Reopen: Automatically resumes displaying existing job
  5. Status Updates: TroubleshootModal.tsx polls getAgentJobStatus every 2 seconds until the job reaches a terminal state; GraphQL subscriptions are not used (subscribeToJobCompletion is a retained no-op that returns null)

User Experience:

  • Users can close modal without losing analysis
  • Reopening shows current progress or final results
  • No need to re-submit for in-progress or completed jobs
  • New jobs only created when previous job is COMPLETED/FAILED

search_cloudwatch_logs

Section titled “search_cloudwatch_logs”

The one tool with two distinct modes, selected by whether document_id is supplied:

  • With a document_id it calls _search_document_logs, which first resolves the document’s processing window and Lambda request IDs (via _get_document_context, which reuses fetch_document_record) and then filters only the log groups that window implicates. This is the targeted path, and it is much cheaper than a stack-wide sweep.
  • Without one it calls _search_stack_logs, which searches recent logs across the stack’s log groups for the given filter_pattern.

Both paths truncate individual messages at max_log_message_length and cap the number of log groups searched. An omitted hours_back resolves to the configured lookback_hours, an omitted max_log_groups to parameters.max_log_groups, and an omitted max_log_events to parameters.max_log_events.

retrieve_document_context

Section titled “retrieve_document_context”

Invokes a separate lookup Lambda rather than reading AWS APIs directly. The function name comes from the LOOKUP_FUNCTION_NAME environment variable, and the tool raises if it is unset — which is the first thing to check if this tool alone is failing.

fetch_pipeline_configuration

Section titled “fetch_pipeline_configuration”

Loads a configuration version through idp_common.config.get_config and walks it for every stage that references a Bedrock model, returning stage_models as a list of {"stage": <dotted path>, "model": <model_id>} plus whether summarization is enabled.

This is the tool that resolves retired-model failures. A Bedrock ResourceNotFoundException does not name the model that was rejected, so the chain is: fetch_document_record for the document’s ConfigVersion, then fetch_pipeline_configuration with that version, then match the failing stage to its configured model ID.

Performance Considerations

Section titled “Performance Considerations”

CloudWatch Logs Queries:

  • Each query scans specified time range across log groups
  • Longer time ranges increase query latency
  • Max 10,000 events per FilterLogEvents call

Cost Optimization:

Token Usage:

  • System prompt: ~800 tokens
  • Log events: ~100-200 tokens each
  • Analysis response: ~500-1000 tokens
  • Total per query: ~2000-4000 tokens average

How does the Error Analyzer differ from CloudWatch Insights?

Section titled “How does the Error Analyzer differ from CloudWatch Insights?”

Error Analyzer:

  • AI-powered root cause identification
  • Automated correlation across services
  • Natural language query interface
  • Actionable recommendations

CloudWatch Insights:

  • Manual query writing required
  • Single log group analysis
  • Technical query language
  • Raw log data output
  • Generic AWS service

Can I customize the system prompt?

Section titled “Can I customize the system prompt?”

Yes, the system prompt is fully customizable in the configuration:

  1. Navigate to Configuration panel in Web UI
  2. Expand “Agent Configuration” section
  3. Edit “Error Analysis Agent” → “system_prompt”
  4. Save configuration

Caution: Modifying the system prompt may affect output formatting and quality.

How many concurrent analysis jobs can run?

Section titled “How many concurrent analysis jobs can run?”

The Error Analyzer supports:

  • Multiple users: Each can have active jobs
  • Job per document: One active job per user per document
  • System-wide queries: Unlimited concurrent queries
  • Resource limits: Subject to Lambda concurrency and Bedrock quotas

What happens if analysis times out?

Section titled “What happens if analysis times out?”

Timeout Handling:

  1. Lambda has 15-minute timeout
  2. Job status set to FAILED
  3. Partial results (if any) are saved
  4. User can retry with narrower scope:
    • Reduce time_range_hours
    • Reduce max_log_events
    • Use document-specific query

Can I export analysis results?

Section titled “Can I export analysis results?”

Export Options:

  1. Copy full details: The Troubleshoot modal footer has a Copy full details button that copies the environment + findings as formatted text
  2. Report this issue on GitHub: Opens a pre-filled bug-report form with the findings and document context (see Reporting an Issue from the Modal)
  3. Copy from UI: Select and copy formatted text
  4. API Access: Use getAgentJobStatus query
  5. CloudWatch Logs: Agent logs contain full results

How long are analysis results retained?

Section titled “How long are analysis results retained?”

Retention Policy:

  • In-memory: Active jobs only
  • DynamoDB: Not persisted (stateless)
  • CloudWatch Logs: Per log group retention (default: 7-90 days)
  • Recommendation: Screenshot or copy important analyses

Does the analyzer work with custom Lambda functions?

Section titled “Does the analyzer work with custom Lambda functions?”

Yes, if custom Lambda functions:

  1. Write to CloudWatch Logs with stack-based log group names
  2. Include ObjectKey in log messages
  3. Follow standard error logging patterns

The analyzer will automatically discover and search these logs.

Limitations

Section titled “Limitations”

Current Limitations

Section titled “Current Limitations”
  1. Single Agent: Only Error-Analyzer-Agent-v1 supported
  2. English Only: Optimized for English log messages
  3. AWS Services: CloudWatch and DynamoDB only (no external logs)
  4. Pattern Matching: Regex-based classification may miss edge cases
  5. Context Window: Limited by Bedrock model token limits

Known Issues

Section titled “Known Issues”
  1. Long Document IDs: ObjectKeys >200 characters may be truncated
  2. Special Characters: Some Unicode in logs may cause parsing issues
  3. High Volume: Systems with >1000 errors/hour may hit throttling
  4. Multi-Region: Analyzer only searches current region

Summary

Section titled “Summary”

The Error Analyzer is a powerful AI-driven troubleshooting tool that:

✓ Automates failure diagnosis with AI-powered analysis
✓ Accelerates root cause identification from hours to minutes
✓ Correlates data across CloudWatch, DynamoDB, and Step Functions
✓ Provides actionable, context-specific recommendations
✓ Integrates seamlessly with the Web UI workflow
✓ Supports both document-specific and system-wide analysis

For optimal results:

  • Use Claude Sonnet 4 model for complex errors
  • Be specific with document IDs in queries
  • Focus on root causes, not symptoms
  • Verify recommendations with evidence
  • Adjust configuration based on deployment patterns

The Error Analyzer significantly reduces troubleshooting time and improves operational efficiency for GenAI IDP deployments.
